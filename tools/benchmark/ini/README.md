# Стенды сравнения контейнера INI

Эталонные стенды для отчёта
[benchmark/codec/ini/COMPARISON.md](../../../benchmark/codec/ini/COMPARISON.md).
Каждый стенд прогоняет одни и те же эталонные тексты настроек через свою
реализацию разбора и выдаёт пропускную способность.

## Как получить и собрать

Исходные тексты сравниваемых реализаций взяты подмодулями, а не выкачиванием:

```sh
git submodule update --init submodules/inih submodules/iniparser \
    submodules/simpleini submodules/mINI
```

```sh
# сборка библиотеки AWH с оптимизацией, если она ещё не собрана
cmake -B ../../../build-release -DCMAKE_BUILD_TYPE=Release ../../..
make -C ../../../build-release awh

# сборка всех семи стендов
./build.sh
```

Собранные стенды складываются в `/tmp/rival-ini`; каталог задаётся первым
параметром `build.sh`, каталог сборки библиотеки — вторым. Стенд, чьих исходных
текстов нет, пропускается с указанием причины, а не роняет сборку.

GLib берётся у системы: `brew install glib` на macOS, `pkg install glib` на
FreeBSD, `apt install libglib2.0-dev` на Linux. Обнаруживается она через
`pkg-config`.

## Как запускать

```sh
# все сценарии одного стенда
/tmp/rival-ini/awh

# один сценарий
/tmp/rival-ini/inih --filter=service

# цена каждой возможности чтения по отдельности
/tmp/rival-ini/ablation

# проверка эквивалентности выполненной работы
/tmp/rival-ini/simpleini --checksum
```

## Состав стендов

| Стенд | Реализация | Что представляет |
|---|---|---|
| `awh` | `awh::codec::ini::reader_t` | Потоковое чтение событиями — прямой соперник `inih` |
| `awh-tree` | `awh::codec::ini::document_t` | Сборка дерева с поиском — соперник прочих четырёх |
| `inih` | benhoyt/inih | Разбор с обратным вызовом на каждое свойство, дерева не строит |
| `iniparser` | ndevilla/iniparser | Разбор в словарь с поиском по склейке «раздел:свойство» |
| `simpleini` | brofield/simpleini | Дерево с многозначностью свойств и сохранением примечаний |
| `mini` | metayeti/mINI | Дерево с сохранением оформления при перезаписи |
| `gkeyfile` | GLib `GKeyFile` | Образцовая реализация записи файлов описания рабочего места |
| `ablation` | `awh::codec::ini::reader_t` | Не соперник, а разбор своего чтения: тот же текст читается несколько раз, и всякий раз снимается одна из возможностей, которых у соперников нет. Разница между прогонами и есть цена снятой возможности |

## Чем стенды неизбежно расходятся

Сравнение честно лишь тогда, когда расхождения названы прямо.

**Подача текста.** `awh`, `awh-tree`, `inih`, `simpleini` и `gkeyfile` разбирают
текст прямо из памяти. `iniparser` умеет только открытый файл — ему текст
подаётся через `fmemopen`, и он несёт на себе издержки `stdio`. `mINI` не
предлагает и того: он открывает путь на файловой системе, и стенд кладёт текст
во временный файл однажды, а все прогоны читают его из страничного кэша. Это не
помеха замеру, а часть цены решения работать с файлом, а не с памятью.

**Примечания.** У `awh` выдача примечаний событиями **отключена**: сличаемые
реализации их не выдают, и оставлять её включённой значило бы сравнивать разный
объём работы. Чего стоят примечания, показывает набор `benchmark/codec/ini` —
там они включены. У `gkeyfile` сохранение примечаний, наоборот, включено
признаком `G_KEY_FILE_KEEP_COMMENTS`: без него он их отбрасывает, и работа
вышла бы меньше, чем у прочих.

**Наречия.** Эталонный текст `repository` написан по образцу настроек Git.
Правильно прочесть его умеет лишь `awh`: прочие возьмут имя раздела
`remote "origin"` целиком, не разобрав его на раздел и подраздел, и оставят
кавычки в значении. Объём работы при этом у всех один и тот же — разбирается
один и тот же текст, — и для сравнения пропускной способности того довольно, но
столбец этот следует читать как «скорость на таком тексте», а не как «умение его
прочесть».

**Строгость.** `GKeyFile` признаёт из знаков примечания лишь решётку и на
точке с запятой отвечает отказом. Сценарии, где такие примечания есть,
он пропускает — это его свойство, а не изъян стенда.

## Про равенство выполненной работы

Каждый стенд обязан прочитать имя раздела, имя свойства и его значение: без
этого часть реализаций работу по их выдаче не выполнит вовсе, а компилятор
вправе устранить измеряемый разбор целиком. Значения складываются в контрольную
сумму, имена — в отдельный приёмник.

Имена в контрольную сумму не входят намеренно: реализации выдают их
по-разному — именем раздела целиком, парой из раздела и подраздела, склейкой
«раздел:свойство». Это разница моделей разбора, а не разный объём работы.
Сличать поэтому следует **количество свойств**, а не сумму: расхождение в нём
означает, что стенды прочли разное.
