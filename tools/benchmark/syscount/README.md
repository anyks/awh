# Счётчик системных вызовов

Подставная библиотека, внедряемая загрузчиком в измеряемый процесс. Считает
обращения к ядру, снимает время в них и умеет выключать отдельные пути движка,
чтобы измерить их стоимость разностью двух прогонов.

## Зачем это нужно

Профилировщик выборок отвечает на вопрос «где время». На нагрузке сетевого
движка ответ звучит так: время в ядре, а собственная работа движка размазана по
пути данных. Дальше профилировщик бессилен — он не говорит ни сколько вызовов
приходится на одну операцию, ни что изменится, если убрать конкретный путь.

Оба отставания движка, найденные в
[отчёте о производительности](../../../benchmark/net/io/README.md), нашлись
именно счётчиком:

* обмен короткими сообщениями выполняет **четыре** `recv` на обмен вместо двух —
  движок узнаёт об отсутствии данных повторным чтением, возвращающим ошибку;
* установление соединения выполняет **два** `socket`, **два** `connect` и
  **три** `close` вместо одного, одного и двух — на каждое создание клиентского
  события движок опрашивает конфигурацию сети.

Ни одно из двух не видно в профиле выборок, и оба видны в счётчике сразу.

## Почему счётчик годится в порог, а время — нет

Время на незанятой машине расходится между прогонами на единицы процентов, на
рабочей — на десятки. Порог по времени приходится задавать с многократным
запасом, и он пропускает всё, кроме катастрофы: пороги набора по скорости стоят
в двух-трёх кратном отрыве от измеренного и не заметили бы удвоения числа
системных вызовов.

Счётчик вызовов на той же нагрузке совпадает от прогона к прогону вплоть до
единиц — `8.00` на обмен, `30.41` на подключение, `2.20` на блок. Порог можно
поставить вплотную, и лишнее обращение к ядру он заметит в тот же день, когда
оно появилось.

## Сборка

Собирается вместе с набором бенчмарков, отдельных действий не требует:

```sh
cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release -DCMAKE_BUILD_BENCHMARKS=YES
cmake --build build-release --target awh_BENCHMARK_net -j 8
```

Готовая библиотека оказывается рядом с набором: `build-release/benchmarks/libsyscount.dylib`.

## Прогон

Готовая цель сборки — набор со счётом системных вызовов:

```sh
cmake --build build-release --target benchmark-net-syscalls
```

Вручную, для отдельного сценария либо для эталонного стенда конкурента:

```sh
DYLD_INSERT_LIBRARIES=build-release/benchmarks/libsyscount.dylib \
	./build-release/benchmarks/net --filter=accept --relaxed

DYLD_INSERT_LIBRARIES=build-release/benchmarks/libsyscount.dylib \
	/tmp/bench-libevent --filter=net/io/echo/single
```

Набор бенчмарков AWH находит счётчик сам и включает учёт ровно вокруг замера,
поэтому показатели в его выводе относятся к замеру, а не ко всему процессу.
Эталонные стенды о счётчике не знают, поэтому для них итоги выводятся в поток
ошибок при завершении процесса и охватывают весь прогон целиком.

Без внедрённой библиотеки показатели по количеству вызовов выводятся как
пропущенные, а код выхода набора от них не зависит:

```
net/io/echo/syscalls-per-round                -           9.00   ПРОПУСК  (вызовов)
                                  нет счётчика системных вызовов - см. tools/benchmark/syscount/README.md
```

> **Внедрение замедляет прогон.** Каждый перехваченный вызов обрастает двумя
> обращениями к часам, и на сценарии с сотнями тысяч вызовов это видно: обмен на
> одном подключении даёт около 15.5 мкс без счётчика и около 17 мкс с ним.
> Поэтому показатели по времени снимаются обычным прогоном, а по количеству
> вызовов — прогоном со счётчиком, и смешивать их в одной таблице нельзя.

## Измерение стоимости пути

Выключение пути подменяет подлинный вызов отказом. Это не исправление: поведение
процесса меняется, и показатели такого прогона нельзя приводить как показатели
движка. Приём годится ровно для одного — измерить стоимость пути разностью двух
прогонов.

```sh
# опрос своего адреса пробным подключением к DNS-серверу
AWH_SYSCOUNT_DISABLE=udp-probe ...

# обращения к маршрутной таблице и перечисление сетевых интерфейсов
AWH_SYSCOUNT_DISABLE=route-sysctl ...

# повторное чтение из сокета после короткого
AWH_SYSCOUNT_DISABLE=read-drain ...

# несколько путей сразу
AWH_SYSCOUNT_DISABLE=udp-probe,route-sysctl ...
```

Прогон с выключенным путём помечает себя в выводе сам:

```
ВНИМАНИЕ: пути выключены, показатели прогона недостоверны
```

| Путь | Что подменяется | Что измеряет |
|---|---|---|
| `udp-probe` | Создание дейтаграммного сокета с протоколом по умолчанию | Опрос своего исходящего адреса на каждое создание клиентского события: пробное подключение к публичному DNS-серверу и два перечисления интерфейсов |
| `route-sysctl` | Запросы к ядру по семейству `PF_ROUTE` | Выгрузку таблицы соседей на каждое принятое подключение и перечисление интерфейсов, которое идёт тем же семейством запросов |
| `read-drain` | Повторное чтение с дескриптора после короткого | Пустое чтение в конце цикла слива, то есть выигрыш от использования объёма доступных данных из готового события |

Замеры, снятые этим способом, приведены в отчёте: опрос конфигурации сети
обходится в 48–63 мкс из 92–106 на подключение, пустое чтение — в 0.56 мкс из
0.86 мкс разрыва на обмен.

## Устройство

| Файл | Содержимое |
|---|---|
| `syscount.h` | Двоичный контракт: состав счётчиков и способ их получения. На чистом C без зависимостей, подключается и подставной библиотекой, и набором — расхождение между ними становится ошибкой сборки |
| `syscount.c` | Перехватчики и учёт |

Названия разновидностей вызовов в выводе платформенно-нейтральны: `poll` — это
ожидание готовности событий, то есть `kevent` на macOS и `epoll_wait` там, где
появится второй бэкенд. Счётчик изменений подписки считает записи, переданные
ядру вместе с этим ожиданием.

Набор отыскивает точку входа счётчика во время выполнения и сверяет версию
контракта: подставная библиотека собирается отдельно и может оказаться собранной
из другой редакции исходного текста. При несовпадении показатели выводятся как
пропущенные с указанием причины.

Три подробности устройства, каждая из которых стоила отдельной отладки:

* **Учитывается только самый внешний вызов.** Часть библиотечных функций
  реализована через другие перехватываемые: `send` вызывает `sendto`, `recv`
  вызывает `recvfrom`, `getifaddrs` выполняет два `sysctl`. Без учёта вложенности
  один вызов попадал бы в счётчики дважды, а сумма времени по счётчикам
  превышала бы время прогона. Первая редакция отчёта эту ошибку и содержала:
  время `sysctl` внутри `getifaddrs` было посчитано двумя строками таблицы.
* **Учёт включается конструктором, а не начальным значением.** Подмена начинает
  действовать с момента применения раздела `__interpose`, то есть раньше, чем
  загрузчик подготовит окружение времени выполнения. Обращения самого загрузчика
  к перехваченным функциям в этот момент приводят к падению процесса.
* **Счётчик вложенности не является потоко-локальным.** По той же причине:
  хранилище потока в подставной библиотеке до окончания загрузки образа
  недоступно. Сценарии набора односоставны по потокам, поэтому общего счётчика
  им достаточно.

## Поддержка платформ

Перехват выполняется разделом `__interpose` загрузчика dyld, то есть работает на
macOS. Остальные системы подменяют символы совпадением имени при загрузке через
`LD_PRELOAD` — для них потребуется отдельная реализация точек перехвата;
двоичный контракт и сторона набора при этом не меняются. Заводить её до
появления самого движка под эти системы нечего: сетевой движок сейчас существует
только в реализации на kqueue.
