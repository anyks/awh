# Сравнение контейнера JSON со сторонними реализациями

Стенды разбирают одни и те же эталонные документы и обходят собранное дерево целиком.
Работа, выполненная стендом, сверяется контрольной суммой: без такой сверки реализация
с отложенным разбором, оставляющая дерево непрочитанным, выглядела бы быстрее прочих,
ничего для того не сделав.

Оттого замер ведётся по разбору **вместе с полным обходом**: в обиходе разобранный
документ читают, а не оставляют лежать. У реализаций с отложенным разбором стоимость
и вовсе переносится с разбора на обход, и разделять их означало бы сличать несличимое.

## Сравниваемые реализации

| стенд | реализация | устройство |
|---|---|---|
| `awh` | `awh::codec::json` | сплошной перечень узлов, одно хранилище знаков, запись числа хранится как есть |
| `yyjson` | [ibireme/yyjson](https://github.com/ibireme/yyjson) | сплошной перечень узлов по 16 байтов, язык C |
| `simdjson` | [simdjson/simdjson](https://github.com/simdjson/simdjson) | разбор словами процессора, дерево строится по мере обхода |
| `rapidjson` | [Tencent/rapidjson](https://github.com/Tencent/rapidjson) | дерево значений, однонаправленный распределитель |
| `boost` | [Boost.JSON](https://github.com/boostorg/json) | дерево значений, однонаправленный распределитель |
| `nlohmann` | [nlohmann/json](https://github.com/nlohmann/json) | дерево на `std::map` и `std::vector`, всё на заголовках |

Реализация Boost.JSON берётся из установленной библиотеки, а не из подмодуля: подмодуль
Boost сложен из подмодулей поменьше, и один лишь Boost.JSON из него не собирается — за
ним тянется два десятка иных частей библиотеки. Путь к установленной библиотеке задаётся
переменной `BOOST_ROOT`, умолчанием служит `/opt/homebrew`.

## Сценарии

| сценарий | размер | содержимое |
|---|---|---|
| `objects` | 16 МБ | массив однородных объектов о шести полях — вид, обиходный у служб |
| `numbers` | 8 МБ | массив чисел: целые, отрицательные, дробные и дробные с порядком |
| `strings` | 8 МБ | массив строк: простые, с отменяющими записями, с кириллицей и иероглифами, с записями `\uXXXX` |
| `nested` | 8 МБ | вложенность в 24 уровня — работа приходится на строение, а не на значения |
| `small` | 120 байт | документ размером с ответ службы, 200 000 прогонов |

Сценарий `small` меряет не разбор содержимого, а стоимость заведения самого разбора: на
нём расходятся реализации, выделяющие память и заводящие состояние на всякий разбор.

Наибольшая допустимая глубина вложенности у Boost.JSON поднята стендом с умолчания в
тридцать два: эталонный документ с вложенностью глубже, и умолчание сличало бы не
скорость разбора, а настройку.

## Сборка и запуск

```sh
cmake -B build-release -DCMAKE_BUILD_TYPE=Release && make -C build-release awh
./tools/benchmark/json/build.sh
for STAND in awh yyjson simdjson rapidjson boost nlohmann; do
	echo "=== $STAND"; /tmp/rival-json/$STAND
done
```

Отбор сценария задаётся ключом `--filter=`, а сверка выполненной работы — ключом
`--checksum`:

```sh
for STAND in awh yyjson simdjson rapidjson boost nlohmann; do
	printf '%-10s ' "$STAND"; /tmp/rival-json/$STAND --filter=numbers --checksum | tail -1
done
```

Контрольные суммы всех стендов обязаны совпасть на всяком сценарии. Расхождение означает,
что стенды прочитали разное, и сличать их скорость до устранения расхождения бессмысленно.
