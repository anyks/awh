# Эталонные стенды сравнения контейнера HTTP-заголовков

Показатель контейнера сам по себе ничего не значит, пока рядом нет числа,
снятого на той же машине, тем же компилятором и на той же нагрузке. Пороги
в `benchmark/proto/headers` ловят обвал в разы; отставание в десять-пятнадцать
процентов им по устройству незаметно, а именно оно и накапливается правками.
Ловит его доля от соперника.

## Соперники

| Стенд | Реализация | Что хранит |
|---|---|---|
| `awh.cpp` | `awh::http::headers_t` | порядок, кратность, поиск без учёта регистра, канонический регистр названий, сборка сообщения |
| `beast.cpp` | [Boost.Beast](https://www.boost.org/doc/libs/release/libs/beast/) `http::fields` | порядок, кратность, поиск без учёта регистра, сборка сообщения |
| `multimap.cpp` | `std::multimap` с регистронезависимым сравнением | кратность, поиск без учёта регистра |

Boost.Beast выбран прямым ровесником по задаче: у его `http::fields` тот же
набор обязанностей, а не выборка из него. Мультикарта стандартной библиотеки
отвечает на другой вопрос — что вообще даёт отдельный контейнер по сравнению
с самой распространённой самоделкой; так устроены заголовки в cpp-httplib
и в доброй половине служб, написанных без готовой библиотеки HTTP.

> **Мультикарта порядок полей не сохраняет**, а он несёт смысл (RFC 9110 §5.3):
> собрать по ней сообщение обратно нельзя. Её сценарий сборки поэтому измеряет
> меньшую работу, чем остальные, и доля по нему сравнением равного с равным
> не является. Читать её следует как «во столько раз обходится сохранение
> порядка», а не как отставание.

## Сценарии

Образцы полей и количества повторений лежат в [scenarios.hpp](scenarios.hpp),
обвязка замера — в [driver.hpp](driver.hpp). И то и другое общее у всех трёх
стендов: заведи их каждый у себя, и сравнение начнёт мерить разницу стендов,
а не разницу реализаций.

| Сценарий | Что измеряет |
|---|---|
| `headers/build/request` | заведение контейнера и укладка в него десяти полей обычного запроса обозревателя |
| `headers/lookup/hit` | поиск поля по названию без учёта регистра, названия чередуются |
| `headers/serialize/request` | сборка сообщения в виде, пригодном для передачи |
| `headers/replace/existing` | замена значения существующего поля |

Образец несёт два одноимённых поля `Set-Cookie` намеренно: кратность контейнер
обязан сохранять, и реализация, хранящая поля картой, теряет на ней либо
значение, либо порядок.

Отыскиваемое название чередуется по кругу, а не задано одно: с одним названием
оптимизатор вправе вычислить поиск однажды и умножить итог на число повторений —
замер мерил бы пустой цикл.

## Сборка и прогон

```
cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release
cmake --build build-release --target awh -j 8
bash tools/benchmark/headers/build.sh /tmp/rival-headers
```

Boost необязателен: без него собирается один стенд мультикарты, а недостающая
доля помечается пропуском. Обрывать из-за отсутствующего системного пакета всю
проверку значило бы лишить машину и тех сторожей, что собрались.

```
/tmp/rival-headers/awh
/tmp/rival-headers/beast --filter=headers/lookup
```

Прогоны реализаций следует чередовать, а не гнать группами: тепловой дрейф
машины за время замера достигает нескольких процентов, и группами он пришёлся
бы на одну реализацию целиком. Именно так их и гоняет `sh/verify_performance.sh`.
