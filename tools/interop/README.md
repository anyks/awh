# Сверка с внешними реализациями

Проверки протокольных модулей AWH против чужих реализаций тех же RFC. Смысл в том,
чего не даёт ни один собственный тест: обе стороны обмена написаны разными людьми
по одному и тому же документу, поэтому расхождение в прочтении спецификации видно
только так.

* **QUIC** — против [ngtcp2](https://github.com/ngtcp2/ngtcp2), см. ниже.
* **HTTP/2** — против [nghttp2](https://nghttp2.org) и набора конформных проверок
  [h2spec](https://github.com/summerwind/h2spec), см. раздел в конце.

---

# Сверка QUIC с внешней реализацией

Два минимальных эндпоинта на основе [ngtcp2](https://github.com/ngtcp2/ngtcp2)
для проверки транспорта QUIC модуля AWH против чужой реализации. Клиент и сервер
переведены на бэкенд boringssl из состава проекта и на `poll()`, поэтому кроме
подмодулей проекта им ничего не требуется.

## Сборка

Библиотеки ngtcp2 собираются из подмодуля. Наличие поддержки QUIC в boringssl
ngtcp2 проверяет через `check_cxx_symbol_exists(SSL_set_quic_early_data_context)`,
и проверка не проходит по двум причинам, ни одна из которых к самому символу
отношения не имеет: `openssl/ssl.h` тянет `openssl/span.h`, требующий C++17,
а статические архивы boringssl написаны на C++ и без `libc++` не линкуются.
Символ в нашей ревизии boringssl присутствует, и обе помехи снимаются
параметрами сборки.

```sh
ROOT=$(pwd)
cmake -S submodules/ngtcp2 -B build-ngtcp2 -DCMAKE_BUILD_TYPE=Release \
	-DCMAKE_CXX_FLAGS=-std=c++17 \
	-DENABLE_BORINGSSL=ON -DENABLE_STATIC_LIB=ON -DENABLE_SHARED_LIB=OFF \
	-DBORINGSSL_INCLUDE_DIR=$ROOT/submodules/boringssl/include \
	-DBORINGSSL_LIBRARIES="$ROOT/submodules/boringssl/build/libssl.a;$ROOT/submodules/boringssl/build/libcrypto.a;c++"
cmake --build build-ngtcp2 -j8

for NAME in ngtcp2-client ngtcp2-server; do
	cc -O1 -g -Wall -Wextra -o build-ngtcp2/$NAME tools/interop/$NAME.c \
		-I submodules/ngtcp2/lib/includes -I build-ngtcp2/lib/includes \
		-I submodules/ngtcp2/crypto/includes -I submodules/boringssl/include \
		build-ngtcp2/crypto/boringssl/libngtcp2_crypto_boringssl.a build-ngtcp2/lib/libngtcp2.a \
		submodules/boringssl/build/libssl.a submodules/boringssl/build/libcrypto.a -lc++
done
```

Если полная сборка ngtcp2 не нужна, проверку можно обойти флагом
`-DENABLE_LIB_ONLY=ON`: библиотека и крипто-бэкенд соберутся, а примеры,
которым всё равно нужны libev и nghttp3, собираться не будут.

## Прогон

Оба эндпоинта запускаются из каталога `build`: пути к тестовым сертификатам
заданы относительно него, как и в семплах.

Клиент ngtcp2 против сервера AWH:

```sh
./samples/proto/quic/proto-quic-server &
../build-ngtcp2/ngtcp2-client --size 4194304          # передача с побайтовой сверкой эха
../build-ngtcp2/ngtcp2-client --datagram              # датаграммы приложения (RFC 9221)
../build-ngtcp2/ngtcp2-client --size 2097152 --key-update  # обновление ключей (RFC 9001 §6)
../build-ngtcp2/ngtcp2-client --size 2097152 --migrate     # миграция пути (RFC 9000 §9)
../build-ngtcp2/ngtcp2-client --version 0x6b3343cf    # согласование версии (RFC 9000 §6)
../build-ngtcp2/ngtcp2-client --state /tmp/ng.st      # возобновление сессии и ранние данные
```

Клиент стенда с `--state` сохраняет билет возобновления и транспортные параметры
сервера, а на следующем запуске подставляет их и открывает поток **до**
рукопожатия, отправляя запрос ранними данными. Против сервера стенда это даёт
`ранние данные: приняты`; против сервера AWH сейчас `ОТКЛОНЕНЫ`, и причина
разобрана ниже.

Клиент AWH против сервера ngtcp2:

```sh
../build-ngtcp2/ngtcp2-server &
./samples/proto/quic/proto-quic-client

../build-ngtcp2/ngtcp2-server --retry &               # проверка адреса пакетом Retry
../build-ngtcp2/ngtcp2-server --broken-retry ocid &   # искажён original_destination_connection_id
../build-ngtcp2/ngtcp2-server --broken-retry noscid & # опущен retry_source_connection_id
../build-ngtcp2/ngtcp2-server --broken-retry scid &   # искажён retry_source_connection_id
../build-ngtcp2/ngtcp2-server --alpn hq-interop &     # несовпадение ALPN
../build-ngtcp2/ngtcp2-server --vneg other &          # согласование без версии клиента
../build-ngtcp2/ngtcp2-server --vneg same &           # согласование с версией клиента
../build-ngtcp2/ngtcp2-server --vneg badcid &         # согласование с чужими идентификаторами
```

Передача объёма и возобновление сессии проверяются параметрами семпла клиента:

```sh
./samples/proto/quic/proto-quic-client --size 4194304        # блок с побайтовой сверкой эха
./samples/proto/quic/proto-quic-client --state /tmp/quic.st  # сохранение и подстановка билета
```

Второй запуск с тем же `--state` возобновляет сессию и отправляет запрос
ранними данными: клиент сообщает `ранние данные=приняты`, сервер стенда -
`возобновление=да, ранние данные=да`. Чтобы это было воспроизводимо, стенд
задаёт постоянный ключ шифрования билетов и контекст ранних данных: со
случайным ключом билет прошлого запуска расшифровать было бы нечем, а без
контекста boringssl ранние данные для QUIC не предлагает вовсе.

Отрицательные прогоны `--vneg` проверяют защиту от понижения версии
(RFC 9000 §6.2): согласование, где предложена версия, которую клиент уже
использует, либо где не совпадают идентификаторы соединения, обязано быть
отброшено, а рукопожатие - продолжено повторной отправкой Initial.

Отрицательные прогоны `--broken-retry` проверяют, что клиент AWH выполняет
сверку идентификаторов после Retry (RFC 9000 §7.3) и рвёт соединение с
`TRANSPORT_PARAMETER_ERROR`, а не продолжает рукопожатие.

Каждый эндпоинт печатает итог сверки и возвращает ненулевой код при сбое,
поэтому прогоны годятся для запуска из скрипта.

## Диагностика согласования групп

Клиент стенда печатает выбранную группу обмена ключами и признак
HelloRetryRequest, а `--group p256|p384|x25519` сужает список предлагаемых
групп до одной - так проверяется совместимость со старыми клиентами:

```sh
../build-ngtcp2/ngtcp2-client --group p256
```

HelloRetryRequest стоит лишнего кругового обхода на каждом соединении и
запрещает ранние данные (RFC 8446 §4.2.10), поэтому его появление в выводе -
повод разобраться с настройкой контекста безопасности. Причина отказа в
ранних данных на стороне сервера устанавливается выводом
`SSL_early_data_reason_string(SSL_get_early_data_reason(ssl))`
в `Handshake::process()` при завершении рукопожатия.

# Сверка HTTP/2 с внешней реализацией

Три проверки [парсера HTTP/2](../../src/proto/http/parser/http2) против nghttp2.
В отличие от QUIC-стенда сеть здесь не нужна: сессии обмениваются байтами
через память, поэтому прогон занимает секунды.

Первый же запуск нашёл дефект, невидимый изнутри: сервер анонсировал
`SETTINGS_ENABLE_PUSH`, отправлять который серверу запрещено (RFC 9113 §6.5.2).
Собственные тесты это принимали, потому что обе стороны в них — наш же парсер,
а любой конформный клиент оборвал бы соединение на первом же кадре.

| Файл | Проверка |
|---|---|
| `nghttp2-hpack.cpp` | Наш HPACK-кодер против распаковщика nghttp2 и упаковщик nghttp2 против нашего декодера — на общей последовательности блоков, то есть с накопленным состоянием динамических таблиц |
| `nghttp2-server.cpp` | Наш серверный парсер против клиентской сессии nghttp2: рукопожатие, тело запроса и ответа сверх окна управления потоком, секция трейлеров, закрытие потока |
| `nghttp2-client.cpp` | Наш клиентский парсер против серверной сессии nghttp2: запрос с телом, ответ с телом и трейлерами, приём анонсированного push-потока |
| `nghttp2-negative.cpp` | Дифференциальная сверка обработки ошибок: 36 некорректных потоков кадров подаются нашему парсеру и сессии nghttp2, сравнивается класс реакции (ошибка соединения, потоковая ошибка, приём) |
| `nghttp2-extensions.cpp` | Расширенный CONNECT (RFC 8441) в обе стороны, анонсы `ALTSVC` (RFC 7838) и `ORIGIN` (RFC 8336) в обе стороны, `PRIORITY_UPDATE` (RFC 9218) и реакция на `GOAWAY` с необработанными потоками |
| `nghttp2-random.cpp` | Сверка HPACK на случайных наборах: смена размера таблицы на ходу, чувствительные значения, переменные длины строк и чередование Huffman. Выводит кодер на пути, которых фиксированная нагрузка не достаёт |
| `h2spec-server.cpp` | Минимальный сервер поверх парсера для прогона набора конформных проверок h2spec (146 проверок по RFC 9113 и RFC 7541) |

Тела в сессионных проверках намеренно больше начального окна (65535 байт): без
обмена `WINDOW_UPDATE` передача встанет, и расхождение в учёте окон проявится
как недобор байт, а не как молчаливое расхождение.

Приём кадров расширений эталон включает только по прямому указанию —
`nghttp2_option_set_builtin_recv_extension_type()` на `NGHTTP2_ALTSVC`
и `NGHTTP2_ORIGIN`. Без него неизвестные кадры молча отбрасываются, и сверка
подтверждала бы лишь то, что мы не оборвали соединение, а содержимое кадра
не проверялось бы вовсе. Поэтому в `nghttp2-extensions.cpp` сравниваются сами
принятые значения, а не факт живого соединения.

## Сборка и прогон

Нужна собранная библиотека проекта (`libawh.a`) и эталонная реализация nghttp2.
Санитайзеры включаются для самого парсера, поэтому его исходники собираются
вместе с проверкой.

**Эталонная реализация берётся из подмодуля, а не системная.** Системная версия
у каждой ОС своя, а расхождение в поведении сверок между машинами пришлось бы
разбирать как дефект — при том, что дефекта нет. Подмодуль зафиксирован
в репозитории, поэтому везде сравнивается один и тот же код:

```sh
git submodule update --init submodules/nghttp2
cmake -S submodules/nghttp2 -B build-nghttp2 -DCMAKE_BUILD_TYPE=Release \
	-DENABLE_LIB_ONLY=ON -DBUILD_STATIC_LIBS=ON -DBUILD_SHARED_LIBS=OFF -DBUILD_TESTING=OFF
cmake --build build-nghttp2 -j 8
```

Скрипт `./sh/verify_http2.sh` выполняет эту сборку сам, если библиотеки ещё нет,
и **сторожит смену версии эталона**: печатает её в заголовке шага и в итоге,
предупреждает, если она разошлась с той, на которой снята документация, и падает,
если изменилось число известных расхождений в сверке обработки ошибок. Ожидаемые
значения заданы в самом скрипте константами `NGHTTP2_EXPECTED` и
`NEGATIVE_EXPECTED` — их и нужно обновлять вместе с перечнем ниже.
Заголовочные файлы лежат в двух местах: `submodules/nghttp2/lib/includes` и
сгенерированный `build-nghttp2/lib/includes`.

Насколько это важно, показал сам переход: между 1.66.0 из системы и 1.69.90
из подмодуля nghttp2 ускорился на 13–26 % и сменил реакцию на одну из
некорректных ситуаций. Оба различия выглядели бы как регрессия у нас.

```sh
ROOT=$(pwd)
FLAGS="-DAWH_STATICLIB -I$ROOT/contrib/include -I$ROOT/third_party/include \
	-I$ROOT/third_party/include/pcre2 -I$ROOT/include -I/opt/homebrew/include \
	-pthread -std=gnu++17 -O1 -g -fsanitize=address,undefined"

for NAME in http hpack frame h2; do
	c++ $FLAGS -c -o /tmp/h2-$NAME.o $ROOT/src/proto/http/parser/http2/$NAME.cpp
done

for NAME in hpack random server client negative extensions; do
	c++ $FLAGS -c -o /tmp/interop-$NAME.o $ROOT/tools/interop/nghttp2-$NAME.cpp
	c++ -fsanitize=address,undefined -o /tmp/interop-$NAME /tmp/interop-$NAME.o \
		/tmp/h2-http.o /tmp/h2-hpack.o /tmp/h2-frame.o /tmp/h2-h2.o \
		$ROOT/build/libawh.a $ROOT/third_party/lib/libdependence.a \
		$ROOT/third_party/lib/libcommon.a /opt/homebrew/lib/libnghttp2.a -lz
	/tmp/interop-$NAME
done
```

На macOS к сборке добавляются фреймворки `-framework Foundation -framework
CoreFoundation -framework Security`, а путь к заголовкам nghttp2 задаётся
по месту установки.

## Что считать результатом

Каждая проверка печатает итог и возвращает ненулевой код при расхождении:

```
сверено блоков: 8000, расхождений: 0
```

```
статус ответа: 200
тело запроса принято сервером: 150000 из 150000
тело ответа принято клиентом: 200000 из 200000
трейлер: [0xDEADBEEF]
код закрытия потока: 0
расхождений: 0
```

Недобор байт в теле означает расхождение в учёте окон управления потоком, пустой
статус — что сессия не дошла до ответа, а строка `отвергнут кадр` печатает тип
кадра, который эталонная реализация признала некорректным.

Сверка обработки ошибок печатает таблицу и помечает строки, где реакции разошлись;
запуск с ключом `-v` дополняет её списком кадров, отправленных каждой стороной.
Расхождение само по себе не означает дефекта: RFC во многих местах допускает как
потоковую ошибку, так и ошибку соединения, и обе реализации вправе выбрать своё.
Разбирать нужно каждое, сверяясь с текстом RFC. Известные расхождения на nghttp2
1.69.90 — шесть, и в пяти из них наш парсер точнее следует букве:

| Случай | Мы | nghttp2 |
|---|---|---|
| Убывающий идентификатор потока | `GOAWAY(PROTOCOL_ERROR)` | принимает |
| `PRIORITY` с зависимостью от себя | `RST_STREAM(PROTOCOL_ERROR)` | принимает |
| `PRIORITY` некорректной длины | `RST_STREAM(FRAME_SIZE_ERROR)` | `GOAWAY(FRAME_SIZE_ERROR)` |
| `WINDOW_UPDATE` с инкрементом 0 на потоке | `RST_STREAM(PROTOCOL_ERROR)` | `GOAWAY(PROTOCOL_ERROR)` |
| `WINDOW_UPDATE` переполняет окно потока | `RST_STREAM(FLOW_CONTROL_ERROR)` | `GOAWAY(FLOW_CONTROL_ERROR)` |
| Запрещённое поле в секции трейлеров | `RST_STREAM(PROTOCOL_ERROR)` | принимает |

В первых двух nghttp2 мягче: приоритеты RFC 7540 он объявил устаревшими и не
проверяет вовсе. В следующих трёх — жёстче: обрывает соединение там, где RFC 9113
§6.3 и §6.9 требуют именно потоковой ошибки. Наши реакции подтверждены h2spec.

Последнее расхождение — единственное, где строже мы, и буква требования здесь
не на нашей стороне: RFC 9110 §6.5.1 адресует запрет отправителю («a sender
MUST NOT generate a trailer field unless…»), получателя ни к чему не обязывая,
а RFC 9112 §7.1.2 прямо разрешает получателю отбрасывать трейлеры выборочно.
nghttp2 поле пропускает, наш HTTP/1 отбрасывает, а HTTP/2 и HTTP/3 обрывают
поток: принятые задним числом условное поле или управляющие данные ответа
переопределяют уже разобранное сообщение, и молча отбросить их — значит
доставить приложению не то сообщение, которое отправлял пир. Выбор осознанный
и записан здесь именно затем, чтобы его пересматривали как выбор, а не как факт.

**Последнее расхождение появилось со сменой версии эталона.** На 1.66.0 nghttp2
отвечал на переполнение окна потока тем же `RST_STREAM`, что и мы; в 1.69.90 стал
слать `GOAWAY`. RFC 9113 §6.9.1 в этом месте однозначен: «для потоков отправитель
шлёт `RST_STREAM` с кодом `FLOW_CONTROL_ERROR`, для соединения — `GOAWAY`».
Случай показателен: список известных расхождений привязан к версии эталона
и подлежит пересмотру при её обновлении, иначе изменение чужого поведения
однажды примут за собственную регрессию.

**Важно при изменении заголовков модуля.** Объектные файлы собираются вручную,
а остальная инфраструктура берётся из `libawh.a`: если менялась разметка объекта,
доступного из библиотеки, библиотеку нужно пересобрать — иначе санитайзер укажет
на несуществующий дефект.

## Сквозная проверка одной командой

Все проверки модуля HTTP/2 — модульные тесты, пороги бенчмарков, пять сверок
с эталонной реализацией, конформность h2spec и генератор искажённых потоков —
прогоняются одним скриптом, падающим на первом расхождении:

```sh
./sh/verify_http2.sh            # по каталогу сборки build
./sh/verify_http2.sh build-my   # по своему каталогу сборки
```

Скрипт всегда пересобирает объектные файлы модуля: устаревшие указывают на
несуществующие дефекты, если менялась разметка объектов. Отсутствие nghttp2
или h2spec не считается провалом — соответствующие шаги пропускаются
с предупреждением. Журналы шагов остаются во временном каталоге, его путь
печатается в конце.

Ручные команды ниже нужны, когда требуется прогнать одну проверку отдельно
или разобрать провал подробнее.

## Набор конформных проверок h2spec

`h2spec-server.cpp` поднимает сервер HTTP/2 поверх парсера: сокет, поток на
соединение и ответ `200` на каждый запрос. Транспорт нарочно примитивен - весь
смысл в том, чтобы h2spec разговаривал с настоящим парсером.

```sh
c++ $FLAGS -c -o /tmp/h2spec-server.o $ROOT/tools/interop/h2spec-server.cpp
c++ -fsanitize=address,undefined -o /tmp/h2spec-server /tmp/h2spec-server.o \
	/tmp/h2-http.o /tmp/h2-hpack.o /tmp/h2-frame.o /tmp/h2-h2.o \
	$ROOT/build/libawh.a $ROOT/third_party/lib/libdependence.a \
	$ROOT/third_party/lib/libcommon.a -lz

/tmp/h2spec-server 8080 &
h2spec -h 127.0.0.1 -p 8080 -o 3      # штатный набор
h2spec -h 127.0.0.1 -p 8080 -o 3 -S   # со строгими проверками
```

Вторым параметром сервер принимает слово `trace` - тогда он печатает заголовок
каждого принятого и отправленного кадра. Это первое, к чему стоит прибегать при
разборе провала: h2spec показывает только своё ожидание, а трасса - что парсер
ответил на самом деле.

Текущее состояние: **146 проверок, 145 пройдено, 1 пропущена, 0 провалов**
(в строгом режиме 147/146). Пропущенную h2spec отбраковывает сам: она требует,
чтобы окно управления потоком ушло в минус, а для этого сервер должен отдать
больше данных, чем отдаёт наш обработчик.

Обработку соединений обязательно вести параллельно: h2spec открывает соединения
одно за другим и не всегда закрывает предыдущее, поэтому последовательный сервер
задержит следующую проверку до истечения таймаута - и она провалится по времени,
хотя парсер ни при чём. Это стоило половины провалов в первом прогоне.

# Сверка HTTP/3 с внешней реализацией

Три проверки [парсера HTTP/3](../../src/proto/http/parser/http3) против nghttp3.
Транспорт QUIC здесь не поднимается: стороны обмениваются байтами потоков через
очереди, поэтому проверяется именно слой HTTP/3, а не доставка.

| Файл | Проверка |
|---|---|
| `nghttp3-qpack.cpp` | Наш QPACK-кодер против декодера nghttp3 и кодер nghttp3 против нашего декодера — с обратной связью по потоку декодера, то есть с накопленным состоянием динамических таблиц. Отдельным шагом сверяется вся статическая таблица: каждая из 99 записей кодируется индексом и разбирается эталоном |
| `nghttp3-session.cpp` | Наш клиент против серверной сессии nghttp3 и наш сервер против клиентской: параметры соединения, запрос с телом, ответ с телом и трейлерами |
| `nghttp3-negative.cpp` | Дифференциальная сверка обработки ошибок: 53 некорректных набора потоков подаются нашему парсеру и сессии nghttp3, сравнивается код ошибки протокола |

Сверка кодека сразу окупилась дважды. Полный обход статической таблицы нашёл
**реальную ошибку совместимости в уже сданном HTTP/2**: запись 16 таблицы HPACK
содержала `gzip, deflate, br, zstd` вместо `gzip, deflate` из RFC 7541. Прежние
сверки её не видели, потому что индекс 16 отправляется только при точном
совпадении значения, а в их наборах такого значения не встречалось. То же
неверное значение было скопировано в запись 31 таблицы QPACK. Обе исправлены,
а полный обход таблиц добавлен в обе сверки как постоянный сторож.

Сессионная сверка нашла вторую ошибку — уже в новом коде: закрытие потока
снимало ссылки его неподтверждённых секций с записей динамической таблицы,
хотя подтверждение секции законно приходит уже после закрытия потока
(RFC 9204 §4.4.1). Пир отвечал на это `QPACK_DECODER_STREAM_ERROR`.

## Сборка и прогон

Эталонная реализация, как и для HTTP/2, берётся из подмодуля. У nghttp3 есть
собственный вложенный подмодуль `lib/sfparse`, поэтому обновлять нужно
рекурсивно — без него сборка падает на отсутствующем заголовке:

```sh
git submodule update --init --recursive submodules/nghttp3
cmake -S submodules/nghttp3 -B build-nghttp3 -DCMAKE_BUILD_TYPE=Release \
	-DENABLE_LIB_ONLY=ON -DBUILD_STATIC_LIBS=ON -DBUILD_SHARED_LIBS=OFF -DBUILD_TESTING=OFF
cmake --build build-nghttp3 -j 8
```

Скрипт `./sh/verify_http3.sh` выполняет эту сборку сам, если библиотеки ещё нет,
и сторожит смену версии эталона и число известных расхождений — константы
`NGHTTP3_EXPECTED` и `NEGATIVE_EXPECTED` в самом скрипте.

```sh
ROOT=$(pwd)
FLAGS="-DAWH_STATICLIB -I$ROOT/contrib/include -I$ROOT/third_party/include \
	-I$ROOT/third_party/include/pcre2 -I$ROOT/include \
	-I$ROOT/submodules/nghttp3/lib/includes -I$ROOT/build-nghttp3/lib/includes \
	-pthread -std=gnu++17 -O1 -g -fsanitize=address,undefined"

for NAME in http qpack frame h3; do
	c++ $FLAGS -c -o /tmp/h3-$NAME.o $ROOT/src/proto/http/parser/http3/$NAME.cpp
done

for NAME in qpack session negative; do
	c++ $FLAGS -c -o /tmp/interop3-$NAME.o $ROOT/tools/interop/nghttp3-$NAME.cpp
	c++ -fsanitize=address,undefined -o /tmp/interop3-$NAME /tmp/interop3-$NAME.o \
		/tmp/h3-http.o /tmp/h3-qpack.o /tmp/h3-frame.o /tmp/h3-h3.o \
		$ROOT/build/libawh.a $ROOT/third_party/lib/libdependence.a \
		$ROOT/third_party/lib/libcommon.a $ROOT/build-nghttp3/lib/libnghttp3.a -lz
	/tmp/interop3-$NAME
done
```

## Что считать результатом

```
сверено записей таблицы: 99, секций: 640, полей: 4480, расхождений: 0
сверено сессий: 2, расхождений: 0
случаев: 53, расхождений: 2
```

**Сверка ошибок сравнивает код ошибки, а не уровень реакции.** Причина
в устройстве эталонного API: nghttp3 сам выбирает уровень только для
однонаправленных потоков неизвестного типа, а во всех прочих случаях возвращает
код наружу и оставляет выбор приложению — оборвать соединение или сбросить
поток. У нас этот выбор сделан внутри парсера. Сравнивать уровни значило бы
сравнивать нашу реализацию с чужим примером использования, а не с RFC, поэтому
уровень печатается справочно в скобках и на счётчик расхождений не влияет.
Двенадцать случаев семантики сообщения, где мы сбрасываем поток, а nghttp3
отдаёт код наружу, — это именно такая разница, а не расхождение прочтения:
RFC 9114 §4.1.2 требует здесь потоковой ошибки `H3_MESSAGE_ERROR`, и код у обеих
сторон совпадает.

Известные расхождения на nghttp3 1.18.90 — два, и в обоих наш парсер точнее
следует букве:

| Случай | Мы | nghttp3 |
|---|---|---|
| `MAX_PUSH_ID` с убывающим значением | `H3_ID_ERROR` | `H3_FRAME_ERROR` |
| `CANCEL_PUSH` с лишними октетами | `H3_FRAME_ERROR` | `H3_FRAME_UNEXPECTED` |

RFC 9114 §7.2.7 про `MAX_PUSH_ID` однозначен: «получение кадра со значением
меньше ранее принятого ДОЛЖНО трактоваться как ошибка соединения типа
`H3_ID_ERROR`». Во втором случае nghttp3 отвергает `CANCEL_PUSH` целиком
с пометкой в исходниках «мы не поддерживаем push», тогда как RFC §7.2.3
разрешает этот кадр на управляющем потоке, а §7.1 предписывает отвечать
`H3_FRAME_ERROR` на лишние октеты в нагрузке любого кадра. Обе реакции эталона
безобидны на практике — nghttp3 никогда не обещает push, — но буквой они
не подтверждены.

**Третье расхождение было нашим и исправлено.** Обрыв нагрузки `SETTINGS`
посреди пары мы отдавали как `H3_SETTINGS_ERROR`, тогда как RFC 9114 §7.1
относит недостачу октетов к требованиям к нагрузке любого кадра и предписывает
`H3_FRAME_ERROR`; `H3_SETTINGS_ERROR` §7.2.4.1 оставляет за повтором
идентификатора. Собственные тесты этого не ловили: обе ошибки обрывают
соединение, и разница видна только по коду, отданному пиру.
