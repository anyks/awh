# Сличение имён перечислений с системными макросами

Инструмент `clash.py` ищет члены перечислений AWH, чьи имена заняты макросами
системных заголовков, и отвечает отказом, если такое имя не снято парой
`include/sys/macro_push.hpp` и `include/sys/macro_pop.hpp`.

## Зачем

Препроцессор области видимости не разбирает и заменяет имя даже внутри `enum class`:
объявление `CS5 = 0x28` при пришедшем `<termios.h>` обращается в `(0x00000000) = 0x28`,
и сборка отвечает отказом.

Беда капкана в том, что вскрывается он **не у нас**. Дерево собирается, пока
сталкивающийся заголовок в него никто не включает, а у потребителя библиотеки он
приходит первым же подключением. Оттого сличение идёт по широкому набору системных
заголовков, а не по тем, что дерево включает само.

Капкан этот срабатывал уже трижды:

| имя | заголовок | где вскрылось |
|---|---|---|
| `MACHINE` | `<machine/param.h>` | FreeBSD, модуль `regex` |
| `FS`, `ES`, `CS`, `SS`, `DS`, `GS` | `<sys/regset.h>` | OpenIndiana, а на Solaris молчало |
| `CS5`, `CS6`, `CS7` | `<termios.h>` | нигде - сличением, до потребителя |

## Как звать

```sh
python3 tools/verify/enums/clash.py .
```

Первым доводом идёт корень дерева, умолчанием - текущий каталог. Собиратель берётся
из переменной `CC`, умолчанием `cc`.

Код возврата: `0` - непокрытых столкновений нет, `1` - есть, и они названы.

## Что читает вывод

```
система: Darwin | заголовков: 62 | членов перечислений: 1802
столкновений: 5, из них снято парой: 5
```

Столкновение, снятое парой, - это норма, а не находка: пара для того и заведена.
Отказом отвечает лишь имя, какого в паре нет.

## Прогон по стендам

У каждой системы макросы свои, и одного прогона не хватает. Заголовки, каких у
системы нет, сличение пропускает само - наличие спрашивается пробной сборкой.

| система | прогнано | заголовков | столкновений | непокрытых |
|---|---|---|---|---|
| macOS arm64 | 01.09.2026 | 62 | 5 | 0 |
| Astra Linux x86-64 | 01.09.2026 | — | 3 | 0 |
| FreeBSD amd64 | 01.09.2026 | 68 | 3 | 0 |
| DragonFly amd64 | 01.09.2026 | 63 | 3 | 0 |
| NetBSD amd64 | 01.09.2026 | 65 | 3 | 0 |
| OpenBSD amd64 | 01.09.2026 | 60 | 3 | 0 |
| Solaris 11.4 x86-64 | 01.09.2026 | 69 | 6 | 0 |
| OpenIndiana x86-64 | 01.09.2026 | 73 | 7 | 0 |
| Windows MSYS2 MinGW64 | 01.09.2026 | 30 | 11 | 0 |

Solaris и OpenIndiana открыли три столкновения, каких прочие системы не видели:
`PRIVATE` и `SHARED` из `<sys/mman.h>` (собственные признаки отображения Sun поверх
`MAP_*`) и `SUSPENDED` из набора заголовков работы с процессами - все три внесены в
пару. OpenIndiana поймала `SUSPENDED` там, где Solaris нет: набор её заголовков шире.

Windows-прогон вводит в набор `<winsock2.h>`, `<windows.h>` и родню: без них сличение
на MinGW брало лишь POSIX-подмножество из 25 заголовков и семейство `DELETE`/`ERROR`/
`TEXT`, ради какого пара и заведена, не проверяло вовсе. С ними всплывают все
одиннадцать - и все сняты. Порядок в наборе значим: `winsock2.h` идёт прежде
`windows.h`, иначе тот втянул бы winsock первой редакции.

Прогон вёлся не с самих стендов, а локально: оркестрация на рабочей машине, а
компилятор - стендовый через обёртку `cc`, шлющую пробную сборку по ssh с
мультиплексором соединений (иначе десятки заголовков дают десятки рукопожатий и
съём не укладывается в срок). BSD и Windows своего Python не имеют, оттого способ
этот и выбран; метка «Darwin» в их выводе - имя рабочей машины, компилятор при этом
стендовый, что видно по числу заголовков.

## Грабли

**Метка вывода обязана быть ASCII.** Кириллическая метка молчала на GCC: тот экранирует
не-ASCII в `\U00000421`, и поиск её не находил. Сличение отвечало нулём столкновений
там, где их три, - и ответ этот выглядел безупречно.

**В метку идёт номер имени, а не само имя.** Столкнувшееся имя раскрывается в своё
значение и метку с собою съедает: вместо `CS5` выводилось `0x00000000`.
