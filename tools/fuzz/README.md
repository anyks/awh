# Фаззинг парсеров

Генераторы нештатного трафика для протокольных парсеров. Собираются отдельно от
проекта и запускаются вручную: они не входят в набор модульных тестов, потому что
осмысленны только под санитайзерами и на длинных прогонах.

## HTTP/2

`http2.cpp` — структурный генератор для [парсера HTTP/2](../../src/proto/http/parser/http2).
Кадры формируются валидными для текущего состояния соединения (корректный preface,
SETTINGS первым кадром, HEADERS с настоящим HPACK-блоком, DATA на открытых потоках),
и лишь часть из них портится точечной заменой байта. Чисто случайный поток байт
обрывался бы на первом кадре, поэтому глубокие состояния сессии так не достигаются.

Проверяются обе роли эндпоинта, подача рваными кусками, расширенный CONNECT,
кадры `PRIORITY_UPDATE`, server push и pull-модель выдачи исходящих байт.
Отдельно моделируется враждебное поведение приложения: функции обратного вызова
изредка требуют сбросить поток и вызывают `reset()` / `clear()` прямо из обработчика,
а pull-источник тела сбрасывает собственный поток и парсер из своего вызова.
Этот класс реентрантности давал дефекты работы с памятью не раз, поэтому он
проверяется постоянно.

### Сквозная проверка

Генератор входит в общую цепочку проверок модуля, прогоняемую скриптом
`./sh/verify_http2.sh` — он собирает всё нужное сам и падает на первом
расхождении. Ручная сборка ниже нужна для отдельного прогона.

### Сборка и запуск

Генератору нужна собранная библиотека проекта (`libawh.a`). Санитайзеры включаются
для самого парсера, поэтому его исходники собираются вместе с генератором, а из
библиотеки берётся остальная инфраструктура.

```sh
ROOT=$(pwd)
FLAGS="-DAWH_STATICLIB -I$ROOT/contrib/include -I$ROOT/third_party/include \
	-I$ROOT/third_party/include/pcre2 -isystem $ROOT/include -pthread -std=gnu++17 \
	-O1 -g -fsanitize=address,undefined"

for NAME in http hpack frame h2; do
	c++ $FLAGS -c -o /tmp/h2-$NAME.o $ROOT/src/proto/http/parser/http2/$NAME.cpp
done
c++ $FLAGS -c -o /tmp/h2-fuzz.o $ROOT/tools/fuzz/http2.cpp
c++ -fsanitize=address,undefined -o /tmp/h2-fuzz /tmp/h2-fuzz.o \
	/tmp/h2-http.o /tmp/h2-hpack.o /tmp/h2-frame.o /tmp/h2-h2.o \
	$ROOT/build/libawh.a $ROOT/third_party/lib/libdependence.a \
	$ROOT/third_party/lib/libcommon.a -lz

/tmp/h2-fuzz 4000
```

На macOS к сборке добавляются `-x objective-c++ -fobjc-arc` и фреймворки
`-framework Foundation -framework CoreFoundation -framework Security`.

Параметр командной строки задаёт число итераций (по две сессии на итерацию —
клиент и сервер); без параметра выполняется 3000 итераций. Зерно генератора
фиксировано, поэтому прогон воспроизводим: найденный дефект повторяется при
том же числе итераций.

### Что считать результатом

Генератор печатает статистику вида:

```
http2 fuzz: 8000 sessions, 90327 frames (7630 corrupted), 4651 sessions survived the whole stream
```

Значение имеет не сама статистика, а отсутствие диагностики санитайзеров.
Полезно следить за долей выживших сессий: если она падает почти до нуля, значит
трафик отбраковывается слишком рано и глубокие состояния не проверяются —
как правило, из-за новой проверки в начале разбора. Заметное падение бывает
и виной самого генератора, шлющего некорректное не по замыслу: так было
с `PRIORITY_UPDATE` от «серверного» пира, когда испытуемый парсер — клиент
(RFC 9218 §7.1 запрещает серверу слать этот кадр, а клиенту предписывает
оборвать соединение). Ровно тот же дефект был и в генераторе HTTP/3.

**Важно при изменении заголовков модуля.** Объектные файлы генератора и парсера
собираются вручную, а остальная инфраструктура берётся из `libawh.a`. Если менялся
размер объекта, доступного из библиотеки (например, провайдера запроса), библиотеку
нужно пересобрать — иначе части программы разойдутся в разметке одного и того же
класса, и санитайзер укажет на несуществующий дефект в парсере.

## HTTP/3

`http3.cpp` — структурный генератор для [парсера HTTP/3](../../src/proto/http/parser/http3).
Устроен по образцу генератора HTTP/2: потоки формируются валидными для текущего
состояния соединения (управляющий поток начинается с `SETTINGS`, потоки инструкций
QPACK несут настоящие инструкции кодера, секции полей кодируются настоящим кодером
с динамической таблицей), и лишь часть кадров портится точечной заменой байта.

Главное отличие — **чередование потоков**. В HTTP/2 весь обмен идёт одним потоком
байт, а в HTTP/3 каждый поток QUIC доставляется независимо, поэтому порядок прихода
кусков разных потоков произволен. Генератор именно его и перебирает: куски всех
потоков перемешиваются с сохранением порядка внутри каждого. Так достигаются
состояния, недостижимые последовательной подачей: секция полей приходит раньше
вставок в таблицу QPACK, поток блокируется и разблокируется, инструкции декодера
обгоняют собственные секции.

Как и в HTTP/2, отдельно моделируется враждебное поведение приложения: функции
обратного вызова изредка требуют сбросить поток и вызывают `reset()` / `clear()`
прямо из обработчика. **Это окупилось сразу**: первый же прогон под ASan нашёл три
обращения к освобождённой памяти — состояние потока, состояние однонаправленного
потока и список разобранных полей продолжали использоваться после того, как
обработчик снёс их сбросом парсера. Разбор теперь сверяет поколение состояния
соединения после каждого выхода наружу.

### Сквозная проверка

Генератор входит в общую цепочку проверок модуля, прогоняемую скриптом
`./sh/verify_http3.sh`.

### Сборка и запуск

	c++ $FLAGS -c -o /tmp/h3-$NAME.o $ROOT/src/proto/http/parser/http3/$NAME.cpp
done

c++ -fsanitize=address,undefined -o /tmp/h3-fuzz /tmp/h3-fuzz.o \
	/tmp/h3-http.o /tmp/h3-qpack.o /tmp/h3-frame.o /tmp/h3-h3.o \
	$ROOT/build/libawh.a $ROOT/third_party/lib/libdependence.a \

Параметр командной строки задаёт число итераций (по две сессии на итерацию —
клиент и сервер); без параметра выполняется 3000 итераций. Зерно генератора

### Что считать результатом

```
http3 fuzz: 8000 sessions, 88171 frames (7312 corrupted), 361288 stream pieces, 3098 sessions survived the whole stream
```

Как и в HTTP/2, значение имеет не статистика, а отсутствие диагностики санитайзеров.
Доля выживших сессий держится около 60 %: остальные обрываются на испорченных
байтах, и это ожидаемо. Падение доли почти до нуля означает, что генератор шлёт
некорректное сам по себе, а не по замыслу — так уже было: тело до секции полей,
тело после трейлеров, ёмкость таблицы QPACK в обход кодера и
`PRIORITY_UPDATE` от «серверного» пира, когда испытуемый парсер — клиент
(RFC 9218 §7.2 запрещает серверу слать этот кадр).

## HTTP/1.x

`http1.cpp` — структурный генератор для [парсера HTTP/1.x](../../src/proto/http/parser/http1)
с **дифференциальной сверкой путей разбора**. В отличие от генератора HTTP/2 он
проверяет не только отсутствие дефектов работы с памятью, но и конкретный
инвариант модуля: наблюдаемый результат разбора не зависит от того, как вход
разбит на фрагменты.

Инвариант нетривиален, потому что размер фрагмента переключает пути. Метод
запроса, литерал версии, целая строка заголовка, участки токена, значения и
тела обрабатываются крупноблочно, и каждый такой путь срабатывает только тогда,
когда разбираемый участок присутствует во входном буфере целиком. При подаче по
одному октету не срабатывает ни один. Эталоном служит именно посимвольная
подача — самый простой и самый медленный путь; с ней сверяются подачи целиком
и фрагментами по 2, 3, 5, 8, 17, 64 и 250 октетов.

Сверяется всё, что парсер отдаёт наружу: итоговый статус, код ошибки, признаки
полноты и кадрирования, размер тела, разобранная стартовая строка, собранные
заголовки, трейлеры и тело, последовательность фазовых событий и событий границ
чанков. Генерируются оба направления трафика, оба режима строгости, пониженные
лимиты, голые окончания строк, устаревшие переносы, конфликты `Content-Length`
и `Transfer-Encoding`, расширения и трейлеры чанков, непригодные для трейлеров
поля по представителю каждой категории RFC 9110 §6.5.1, длинные прогоны ведущих
OWS значения заголовка при пониженном суммарном бюджете блока (отброшенные при
разборе октеты входят в лимит наравне с сохранёнными, и оба пути обязаны считать
их одинаково), BWS между размером чанка и его расширениями (по RFC 9112 §7.1
допустим только вместе с точкой с запятой), пустые строки перед
стартовой строкой запроса (сервер их игнорирует по RFC 9112 §2.2, строгий режим
отвергает, а поток из них упирается в предел), длинные reason-phrase (они
учитываются в общем бюджете стартовой строки, и без них понижённый лимит этой
длины у ответа не достигается), пустые элементы в списке `Transfer-Encoding`
(RFC 9110 §5.6.1.2 обязывает получателя их игнорировать, поэтому завершающая
запятая не отменяет объявленного chunked), октеты на краю правила допустимости
расширений чанка (DEL и управляющие обязаны отвергаться, пробел и obs-text -
приниматься), коды состояния вне диапазона 100..599 (RFC 9110 §15 объявляет их
недопустимыми, но предписывает обрабатывать ответ как 5xx, а не отвергать),
точечная порча октета и обрыв сообщения.

### Режимы работы парсера

Протокол, установленный методом `proto`, описывает роль узла на соединении, а не
разбираемое сообщение: `PROXY1` означает работу через прокси, `WEBSOCKET1` —
соединение, которому предстоит смена протокола. Оба ужесточают разбор там, где
расхождение соседних звеньев цепочки превращается в подмену сообщения.

Режим выбирается случайно и участвует в дифференциальной сверке наравне с прочими
настройками, но одной её мало: разбиение входа на фрагменты не зависит от режима,
и защита, не срабатывающая вовсе, прошла бы её незамеченной. Поэтому режимы
сверяются ещё и между собой — **таблицей предсказаний**. Каждое сообщение
разбирается прямым соединением и обоими режимами, а таблица предписывает, где им
положено разойтись:

| Вход | `HTTP1` | `PROXY1` | `WEBSOCKET1` |
|---|---|---|---|
| absolute-form, адресат ≠ `Host` | принять | `INVALID_HOST` | принять |
| запрос с `Upgrade` и `Transfer-Encoding` | принять | `INVALID_TRANSFER_ENCODING` | `INVALID_TRANSFER_ENCODING` |
| запрос с `Upgrade` и ненулевым `Content-Length` | принять | `INVALID_CONTENT_LENGTH` | `INVALID_CONTENT_LENGTH` |
| ответ 1xx либо `204` с `Transfer-Encoding` | принять | `INVALID_TRANSFER_ENCODING` | принять |
| ответ 1xx либо `204` с `Content-Length` | принять | `INVALID_CONTENT_LENGTH` | принять |
| ответ `101` с любым из них | принять | (входит в 1xx) | соответствующая ошибка |
| ответ с `Transfer-Encoding` не на `chunked` | тело до закрытия | `INVALID_TRANSFER_ENCODING` | тело до закрытия |

Сверка держит обе стороны. Там, где таблица предсказывает отказ, режим обязан
отвергнуть сообщение **именно предсказанной ошибкой**: отказ по любой другой
причине означал бы, что разбор не дошёл до проверки. Везде остальном режим обязан
разобрать сообщение так же, как прямое соединение, — октет в октет, включая поток
событий. Так ловится и защита, не сработавшая на своём сообщении, и защита,
сработавшая на чужом.

Отказ сверяется только у сообщений, принятых прямым соединением целиком: у
сообщения, отвергнутого и без режима, разбор мог не дойти до проверки вовсе.
Испорченные точечной заменой октета и оборванные сообщения из сверки исключаются
целиком — порча вносится вслепую и способна переписать ровно тот признак, по
которому строится предсказание.

Сверка выполняется с вызовом `eof()`: тело, кадрированное закрытием соединения
(RFC 9112 §6.3 п. 3), иначе не завершается вовсе, и последняя строка таблицы
осталась бы непроверенной — эталон никогда не был бы полным.

Отдельно генерируется путь создания парсера: половина сообщений разбирается
парсером, полученным клонированием настроенной фабрики, а не построенным
конструктором. Соединения обслуживают именно клоны, а настройка выполняется на
фабрике, поэтому настройка, забытая в `clone`, оставляет обслуживающий парсер в
умолчаниях — со всеми выключенными проверками, которые она включает.

### Отправляющая сторона

У отправителя входа нет, поэтому дифференциальная сверка к нему неприменима, и
проверяются два других свойства:

* **обратная разбираемость** — собранное сообщение подаётся свежему парсеру и
  обязано разобраться в то же самое: стартовая строка, все отправленные
  заголовки, тело и трейлеры;
* **отсутствие непотреблённого хвоста** — получатель обязан потребить собранное
  сообщение целиком. Хвост означает, что отправитель выдал байты, кадрированием
  сообщения не описанные: получатель прочитает их как начало следующего
  сообщения. Сверка тела такой хвост не ловит — получатель его просто не отдаёт
  наружу, — поэтому проверка отдельная;
* **независимость провода от способа выдачи** — сообщение, собранное с функцией
  обратного вызова записи, обязано совпасть октет в октет с собранным
  pull-моделью через `pending()`/`consumePending()`.

Побайтового совпадения провода со способом подачи тела не требуется:
pull-источник выдаёт тело своими порциями, разбивка на чанки у него другая, а
границы чанков семантики сообщения не несут — для него проверяется только
обратная разбираемость. Случайно выбираются направление, версия протокола,
метод, код состояния, кадрирование, размер тела и порций, пороги выходного
буфера, набор заголовков и трейлеров, а также объявление транспортного
кодирования, где `chunked` не последний: собирать такое сообщение отправитель
обязан отказаться, и провод после отказа проверяется на пустоту.

Отдельно генерируется pull-источник, объявляющий конец тела, не выдав
анонсированного `Content-Length`. Тело фиксированного размера завершается строго
по исчерпании анонсированного объёма, поэтому такой источник обязан оставить
сообщение незавершённым, а остаток обязан дойти до провода методом `sendData`:
досрочное завершение выдало бы усечённое тело, и обратная разбираемость его
не приняла бы.

Из самого источника выполняются попытки вклиниться в тело — выдать порцию
методом `sendData`, завершить тело блоком трейлеров, подготовить отправитель к
следующему сообщению методом `resetSender` и назначить новый источник поверх
исполняющегося. Две последние попытки закрывают отдельный класс: подготовка сняла
бы признак завершённости, и следующий блок заголовков лёг бы строкой размера
чанка в чужое тело, а назначение уничтожило бы объект функции, из которого пришёл
вызов, — это уже не порча провода, а обращение к освобождённой памяти, и его
ловит санитайзер. Момент выбран наихудший:
выходной буфер находится между резервированием участка под текущую порцию и его
фиксацией, поэтому принятая запись разорвала бы кадрирование прямо внутри
заголовка чанка, а принятый блок трейлеров обрезал бы недочитанный остаток тела.
Обе попытки обязаны быть отвергнуты без следа на проводе, и это проверяет всё та
же обратная разбираемость.

Отдельным классом генерируются сообщения, один из элементов которых непредставим
на проводе: название поля с пробелом или двоеточием, значение поля либо пояснение
к коду состояния с управляющим символом, цель запроса с пробелом или переводом
строки, написание нераспознанного метода с разделителем внутри, код состояния,
не укладывающийся в три цифры, и запрос HTTP/1.1 без заголовка `Host` либо с
пробелом внутри его значения. Возврат каретки или перевод строки в любом из этих
мест расщепляет собираемое сообщение на два, поэтому отправитель обязан отказаться
собирать его целиком, и провод после отказа проверяется на пустоту. Непригодный
блок трейлеров стоит особняком: он отбрасывается один, а тело всё равно обязано
завершиться нулевым чанком — иначе получатель ждал бы его продолжения до закрытия
соединения. Проверяется, что до получателя не дошло ни одного трейлера.

Отдельно генерируются ответы, не способные нести тела, — ответ на запрос `HEAD` и
ответы с кодом 1xx, `204` и `304`. Такой ответ заканчивается первой пустой строкой
после блока заголовков независимо от присутствующих в нём полей (RFC 9112 §6.3
п. 1), поэтому тело обязано не дойти до провода: иначе получатель прочитал бы его
как начало следующего ответа. У ответов 1xx и 204 с провода обязаны исчезнуть и
объявления кадрирования, а у ответа 304 и ответа на `HEAD` — сохраниться. Рядом
генерируется успешный ответ на `CONNECT`: он открывает туннель сразу за пустой
строкой, объявления кадрирования в нём отправлять запрещено, а содержимое туннеля
кадром сообщения не описывается и здесь не выдаётся. Объявление `Transfer-Encoding`,
где `chunked` не последний, в этих ответах отказа не вызывает — заголовок снимается
с провода раньше, чем проверяется исправимость объявления.

Режим работы устанавливается и отправителю, и приёмнику обратной разбираемости:
проверяемый инвариант в том, что собранное сообщение принимает **наш же**
приёмник, а в этих режимах он строже. Отправитель обязан отказаться собрать
запрос со сменой протокола, несущий тело (точка переключения стала бы предметом
догадки), и запрос, адресат цели которого расходится с адресатом заголовка
`Host`, — обе проверки повторяют приёмные, и провод после отказа проверяется на
пустоту. Кадрирования не получает только тело запроса HTTP/1.0 без
`Content-Length`: кадрировать его нечем, и тела в таком запросе нет вовсе,
поэтому смене протокола оно не мешает.

Версия HTTP/1.0 нужна отдельно: кодирования chunked в ней не существует,
поэтому объявление `Transfer-Encoding` отправитель снимает с провода, тело
ответа кадрируется закрытием соединения, а телу запроса требуется
`Content-Length` — без него кадрировать нечем, и тело к отправке не
принимается. У ответа, кадрированного закрытием соединения, конец сообщения
обозначается концом потока, поэтому обратная разбираемость проверяется
с вызовом `eof()`.

### Реентрантность

Моделируется враждебное поведение приложения: обработчики изредка сбрасывают
парсер методом `reset` прямо из своего вызова, а иногда вызывают `clear`, который
удаляет функции обратного вызова, то есть уничтожает ту самую функцию, тело
которой выполняется. Фазовый обработчик изредка прерывает разбор возвратом
`false`. После такого сеанса враждебные обработчики заменяются безобидными, и
парсер обязан разобрать следующее корректное сообщение как ни в чём не бывало.

### Что считать результатом

```
http1 fuzz: 800000 сообщений (200778 разобрано полностью, 552879 отвергнуто), 6400000 сверок путей,
            400000 собранных исходящих сообщений, 199762 сеансов реентрантности - расхождений нет
```

Значение имеют три вещи: отсутствие диагностики санитайзеров, отсутствие
расхождений и доля полностью разобранных сообщений. Последняя держится около
четверти; если она падает почти до нуля, трафик отбраковывается слишком рано,
и тело, чанки и трейлеры перестают проверяться вовсе.

При расхождении печатается номер итерации, направление, размер фрагмента, оба
результата разбора и само сообщение в экранированном виде. Зерно фиксировано,
поэтому расхождение повторяется при том же числе итераций.


**Количество обработанных октетов** на участках имени и значения заголовка:
крупноблочный путь возвращает начало участка, посимвольный — позицию
недопустимого октета. После ошибки разбора это число смысла не имеет —
сообщение отвергнуто целиком.

Стартовая строка сверяется в том числе у отвергнутых сообщений. Первый же прогон
генератора нашёл там два расхождения, и оба исправлены: крупноблочный разбор
адреса запроса теперь дописывает укладывающуюся в лимит часть участка перед
отказом, а крупноблочный разбор литерала версии устанавливает разобранную версию
до проверки лимита — ровно так, как это делает посимвольный путь. Зафиксировано
тестом `StartLineOverflowStateEquivalenceTest`, перебирающим лимит длины
стартовой строки через точку отказа в методе, адресе и версии.

## Настройки INI

`ini.cpp` — структурный генератор для [кодека текста настроек INI](../../src/codec/ini)
с **дифференциальной сверкой подачи**. Как и генератор HTTP/1.x, он проверяет не
только отсутствие дефектов работы с памятью, но и договор модуля: выданные чтением
события не зависят от того, как исходный текст разбит на куски.

Текст настроек строится записями всех признаваемых наречий — объявления разделов
с подразделами через разделитель и в кавычках, свойства с разделителями обоих
видов, значения в кавычках и без, управляющие последовательности, обращения к
другим значениям, продолжения строк обратной косой чертой и отступом, примечания
собственной строкой и в конце строки, свойства без значения, добавление к перечню,
знаки не из набора ASCII, недопустимые последовательности UTF-8, метка порядка
байтов и оба вида окончания строки. Треть текстов затем портится точечной заменой,
вставкой и удалением знака, а также обрезанием: чисто случайный набор байтов
отвергался бы первой же строкой, и глубокие пути разбора так не достигаются.

Проверяется девять договоров:

- **подача целиком равна подаче кусками** — сличается вся выдача разбора: вид
  события, имя раздела и подраздела, имя и значение свойства, содержимое
  примечания, признаки свойства и **место каждого события**. Кусков берётся три
  размера на текст, и первый из них всегда однобайтовый;
- **итог разбора совпадает** — состояние по завершении, код отказа и место его
  обнаружения обязаны совпасть при всякой нарезке;
- **кодировка исходного текста разбора не меняет** — тот же самый текст приводится
  к UTF-16 обоих порядков байтов и подаётся заново, целиком и кусками по одному и по
  три байта. Смещение в байтах не сличается — оно кодировкой разнится по устройству;
- **записанное читается обратно** — дерево настроек собирается разбором,
  переписывается и разбирается повторно;
- **перезапись устойчива** — второй перезаписи положено совпасть с первой
  знак в знак;
- **правка дерева устойчивости не рушит** — в дерево вносятся создания разделов,
  установки и удаления свойств, после чего оба предыдущих договора проверяются
  заново;
- **чтение дерева совпадает с чтением его записи** — после правок все значения
  сличаются со значениями дерева, собранного разбором перезаписи: дерево, чьё чтение
  расходится с чтением собственной записи, выдаёт потребителю то одно, то другое.
  Устойчивость перезаписи такого расхождения не ловит вовсе — в текст уходит
  записанное, а не разрешённое;
- **враждебное значение переживает круговой ход** — в дерево заводится значение из
  набора заведомо неудобных (пробельная обвязка, знаки примечания и разделителя,
  кавычки, обратные косые черты, переводы строк, записи обращений), после чего
  записанное читается обратно и обязано совпасть знак в знак. Значение, наречием
  невыразимое, обязано быть отвергнуто явно: пустая перезапись расхождением не
  считается, а вот выданное изменённым - считается. Обращение читающего с кавычками,
  управляющими последовательностями и примечанием в конце строки при этом
  перебирается: запись берёт эти настройки у чтения и по ним решает, чем значение
  защищать, а сложившиеся наречия дают лишь часть их сочетаний. На сочетании,
  которого среди наречий нет - кавычки частью значения при признаваемых управляющих
  последовательностях, - защиты не было вовсе, и пробельная обвязка терялась молча;
- **перевод в другое наречие читается этим наречием** — дерево переписывается
  настройками одного из четырёх сложившихся наречий и разбирается обратно настройками
  чтения того же наречия: значения обязаны пережить перевод без потерь, а невыразимое
  наречием - быть отвергнуто пустой перезаписью. Правила, значения по смыслу меняющие
  (обращение с повторами, учёт регистра имён, подстановка обращений), переносятся в
  наречие перевода: расхождения по ним законны и к переводу отношения не имеют.

### Сборка и запуск

Кодек ни от чего в проекте не зависит, кроме таблицы разбора чисел, поэтому
собранная библиотека генератору не нужна:

```sh
ROOT=$(pwd)
c++ -std=gnu++17 -O1 -g -fsanitize=address,undefined -I$ROOT/include \
	-o /tmp/ini-fuzz $ROOT/src/codec/ini/*.cpp $ROOT/src/num/lexical/table.cpp \
	$ROOT/tools/fuzz/ini.cpp

/tmp/ini-fuzz 400000
```

Первый параметр командной строки задаёт число проходов (без него выполняется 3000),
второй — зерно источника случайных чисел. Поля настроек разбора — знаки примечания и разделителя,
обращение с повторами и кавычками, признание примечания в конце строки, управляющих
последовательностей, продолжений, свойств без значения, перечней, учёт регистра,
отбрасывание обвязки — перебираются поодиночке у половины текстов: сложившиеся наречия
дают лишь несколько сочетаний из многих, а негодные выходят как раз на тех, которых
среди наречий нет. Пределы разбора — длина строки, длина
имени, глубина подразделов, количество строк продолжения — поджимаются у четверти
текстов: при умолчаниях накопление до них не доходит вовсе, а расхождения пределов
проступают лишь на поджатых значениях.
Зерно генератора закреплено, поэтому прогон воспроизводим — и **не только на своей
машине**: обращения к источнику случайных чисел разнесены по отдельным
предложениям, оттого выдача совпадает знак в знак у разных построителей. Первый
же прогон по стендам показал, зачем это нужно: два обращения в одном выражении
(`text.at(engine() % text.length()) = char(engine() % 256)`) давали clang и gcc
разную последовательность, порядок вычисления доводов языком не определён, и
дефект, найденный на одной машине, на другой не повторялся бы.

### Прогон по отладочным стендам

Кодек ни от чего не зависит, поэтому свёрток `include`, `src/codec/ini`,
`src/num/lexical` и `tools/fuzz/ini.cpp` разворачивается на стенде сам по себе —
возраст тамошнего дерева значения не имеет.

Проверено 11.08.2026 на девяти стендах x86-64 (Ubuntu, Fedora, Alt, OpenSUSE,
NetBSD, OpenBSD, FreeBSD, Solaris, OpenIndiana) вместе с macOS ARM64: выдача
совпала **построчно на всех десяти** — по 20 000 проходов, с суммами событий и
перезаписанным деревом текстом.

Санитайзеры есть не всюду: OpenBSD не поддерживает их вовсе, Solaris и
OpenIndiana — в тамошней сборке GCC, у NetBSD они несовместимы с ASLR и требуют
снятия признака с двоичного файла (`paxctl -0 <файл> && paxctl +a <файл>` —
именно в таком порядке, прямое `+a` отвечает «новые признаки не имеют смысла»).

### Что считать результатом

```
ini fuzz: 400000 texts (133380 corrupted), 612956 events, 35707 parsed to the end,
          400000 trees, 51218 rewrites
```

Значение имеют отсутствие диагностики санитайзеров, отсутствие расхождений и доля
текстов, разобранных до конца: она держится около десятой части, и падение её
почти до нуля означало бы, что тексты отбраковываются первой же строкой, а дерево
и перезапись не проверяются вовсе. При расхождении печатается размер куска, номер
разошедшегося события и сам текст настроек в шестнадцатеричном виде.

Разбор 12.08.2026 нашёл **устаревание подстановки обращений после правки дерева**:
разрешались обращения один-единственный раз, при разборе, и правка значения, на
которое обращение ссылается, чтения не меняла — дерево выдавало подставленное по
прежним значениям, расходясь с тем, что дало бы чтение его же записи. Обращение,
заведённое самой правкой, не разрешалось вовсе. Подстановка пересчитывается теперь
после правок — отложенно, до первого чтения значения, и от значений до подстановки,
- а неразрешимое обращение (источник удалён правкой) чтение выдаёт в записанном виде,
обратную же запись отвергает: текст с обращением в пустоту разбор не примет. Найдено
после того, как в ворошителе включили саму подстановку: умолчанием она отключена, и
проверялась до того **ни разу**.

Тот же разбор нашёл **потерю управляющих знаков значения при записи**: краткое
обозначение имеют лишь несколько из них, а прочие уходили в текст сырыми — и разбор
отвергал собственную же перезапись как недопустимый знак. Записываются они теперь
видом `\xNN` ровно двумя цифрами (разбор читает ровно две, и следующий знак, годный в
шестнадцатеричные, к числу не пристаёт); при запрещённых последовательностях запись
отвечает отказом. Закреплено проверкой `CodecIniWriter.ControlCharacters`.

Разбор 11.08.2026 нашёл **неповторяемость перезаписи у примечания, оканчивающегося
обратной косой чертой**: читающий склеивает такое примечание со следующей строкой, и
объявление раздела, ставшее его хвостом, разделом уже не считается — свойства раздела
уходят в раздел без имени, то есть пропадает целый раздел. Запись отделяет теперь
такое примечание пустой строкой, склеивание прекращающей; закреплено проверкой
`CodecIniWriter.CommentContinuation`. Тем же разбором ноль в пределах длины строки и
имени переведён в «без предела» — прежде он запрещал разбор вовсе и не оставлял
способа предел снять, тогда как у кодека разметки тот же ноль предел снимает. Изъятие
разобранного начала буфера проверено нарочно длинными текстами и закреплено проверкой
`CodecIniReader.Compaction`: короче 64 КиБ этот ход не исполняется вовсе, и до сих пор
его не проходила ни одна проверка.

Первый же прогон нашёл два дефекта, и оба исправлены: приведение исходного текста
к UTF-8 отбрасывало разобранное начало непрерывного отрезка однобайтовых знаков
при отказе посреди него, а отказ приведения выдавался прежде разбора уже
приведённого начала текста — оттого подача целиком теряла события, которые подача
кусками выдавала. Третьим нашлась запись имени, оканчивающегося обратной косой
чертой: читающий склеил бы его со следующей строкой, и записанное деревом уже не
читалось обратно.

### Разбор 15.08.2026: примечания вне значения, места событий и раздел без имени

Разбор кода вскрыл **девять дефектов**, и **четыре из них ворошителю были недоступны**
по устройству — под каждый добавлено утверждение либо построение, и каждое проверено
на прежнем коде.

Первые четыре имеют один корень: **примечание в конце строки признавалось лишь разбором
значения**, а тот исполняется только при найденном разделителе имени и значения.
Свойство без значения забирало примечание себе в имя; знак разделителя внутри примечания
становился разделителем записи (`k ; см. далее: текст` давало имя `k ; см. далее` и
значение `текст`); поиск закрывающей скобки объявления раздела уходил внутрь примечания;
а запись такие имена принимала, хотя собственный разбор читает их иначе — у свойства
пропадало значение, а объявление раздела становилось незакрытым.

Круговым ходом это не ловится: прежнее поведение было **самосогласованным** — имя
`k ; примечание` записывалось обратно тою же строкой и читалось тем же именем. Проверка,
не утверждающая ничего сверх согласия кодека с самим собою, молчит там, где кодек неверен
последовательно. Добавлено прямое утверждение `sound()`: имя, выданное разбором, обязано
быть именем, и знак примечания, отделённый пробельным знаком, в нём недопустим. На прежнем
разборе оно срабатывает за 20 000 проходов и сразу же вывело случай с объявлением раздела.

Ещё два дефекта — в местах событий, и они ворошителю недоступны в принципе: он сличает
места **между нарезками**, а неверное место одинаково неверно при всякой нарезке.
Логическая строка вправе собираться из нескольких физических, а столбец считался от её
начала сквозь переносы: примечание во второй физической строке выдавалось первой со
столбцом больше её длины. Счёт строки и столбца сведён в один метод, а обратное
отображение собранной строки в исходный текст записывается **при самой сборке** — два
списка правил склейки разошлись бы при первой же правке одного из них. Место незакрытой
кавычки указывало на начало значения вместо неё самой.

Седьмой — в подстановке: обращение внутри неё читало значение **разрешённое**, а не
записанное, и подставляло второй раз. Свойство `посредник = $${цель}` разрешается в запись
`${цель}`, обращением уже не являющуюся, и `через = ${посредник}` обязано получить её как
есть — а после первой же правки дерева получало значение самой цели: удвоение знака,
служащее записи его самого, переставало служить. Ворошителю добавлена цепочка из двух
обращений: ни одно из сложившихся наречий такой не строит.

Восьмой найден **новым щупом сличения**, не ворошителем: слепок всей открытой выдачи дерева
(`size`, `empty`, `sections`, `keys`, `has`, `get`, `values`) против такого же слепка дерева,
собранного разбором его собственной записи, после случайных правок вперемешку. Раздел без
имени объявления не имеет, а значит, и последней записи, от которой берётся место вставки, —
место бралось концом перечня, за объявлениями всех прочих разделов. Дерево звало значение
своим, а его же запись отдавала последнему разделу. Ворошитель правил только именованные
разделы (`a`…`d`) и этого пути не проходил вовсе; теперь четверть правок идёт в раздел без
имени.

Девятым проверено, что пустая перезапись выдаётся лишь пустым деревом либо деревом с
обращением в пустоту: отказ записи молчаливым не бывает.

**Прогон 15.08.2026 на четырнадцати машинах** — macOS ARM64, FreeBSD, NetBSD, OpenBSD,
DragonFly, Solaris, OpenIndiana, Alpine (musl), Debian, Alt, Ubuntu, OpenSUSE, Fedora,
Windows x86-64 (MinGW) и Windows ARM64 (clang). Итоги ворошителя совпали **побайтово** по
трём зёрнам: 752 409, 753 391 и 760 146 событий, 22 116, 22 486 и 22 044 перезаписи. Набор
проверок — 115 из 115 всюду, кроме OpenBSD и Alpine, где `CodecIniWriter.LocaleNumbers`
пропускается: локали с иным знаком десятичной точки там нет вовсе.

**Прогон повторён 16.08.2026** после перевода записи чисел на собственный `awh::lexical`
(запись числа брала прежде знак десятичной точки у локали и правила его на месте). Итоги
ворошителя на всех четырнадцати машинах совпали с прежними знак в знак, набор проверок -
тоже: новая запись даёт тот же самый текст.

## Настройки TOML

`toml.cpp` — структурный генератор для [кодека текста настроек TOML](../../src/codec/toml)
с той же **дифференциальной сверкой подачи**, что и генератор INI. Наречий у TOML нет —
описание единственное, — поэтому вместо перебора наречий перебираются пределы разбора,
признание знаков Юникода в имени без кавычек, обращение с повторами и выдача примечаний
с пустыми строками.

Текст настроек строится записями, описанием отводимыми: объявлениями таблиц и наборов
таблиц, парами с составными именами ключей, четырьмя оградами строк, четырьмя системами
счисления чисел, четырьмя видами отметок времени, перечнями (в том числе многострочными,
с примечаниями внутри и с лишней запятой в конце), встроенными таблицами, примечаниями
собственной строкой и в конце строки, знаками не из набора ASCII, недопустимыми
последовательностями UTF-8, меткой порядка байтов и обоими видами окончания строки.
Треть текстов затем портится точечной заменой, вставкой и удалением знака, а также
обрезанием.

Проверяются восемь договоров:

- **подача целиком равна подаче кусками** — сличается вся выдача разбора: вид события,
  составное имя ключа вместе с записью каждой его части, тип значения, ограда строки,
  система счисления числа, все поля отметки времени, содержимое примечания и **место
  каждого события**. Число с плавающей точкой сличается двоичным представлением, а не
  значением: нечисло само себе не равно;
- **итог разбора совпадает** — состояние по завершении, код отказа и место его
  обнаружения обязаны совпасть при всякой нарезке;
- **кодировка исходного текста разбора не меняет** — тот же текст приводится к UTF-16
  обоих порядков байтов и подаётся заново, целиком и кусками по одному и по три байта;
- **записанное читается обратно** — дерево собирается разбором, переписывается и
  разбирается повторно;
- **перезапись устойчива** — второй перезаписи положено совпасть с первой знак в знак;
- **правка дерева устойчивости не рушит** — в дерево вносятся объявления таблиц,
  установки значений всех простых типов и удаления, после чего оба предыдущих договора
  проверяются заново;
- **чтение дерева совпадает с чтением его записи** — обходом всех пар собираются оба
  перечня значений и сличаются: дерево, чьё чтение расходится с чтением собственной
  записи, выдаёт потребителю то одно, то другое;
- **враждебное значение переживает круговой ход** — в дерево заводится значение из
  набора заведомо неудобных (пробельная обвязка, знаки примечания и равенства, кавычки
  всех видов, тройные ограды, обратные косые черты, переводы строк, возврат каретки,
  управляющие знаки, записи, читаемые числом либо отметкой времени), записывается всеми
  четырьмя оградами и читается обратно.

### Сборка и запуск

Кодек ни от чего в проекте не зависит, кроме таблицы разбора чисел:

```sh
ROOT=$(pwd)
c++ -std=gnu++17 -O1 -g -fsanitize=address,undefined -I$ROOT/include \
	-o /tmp/toml-fuzz $ROOT/src/codec/toml/*.cpp $ROOT/src/num/lexical/table.cpp \
	$ROOT/tools/fuzz/toml.cpp

/tmp/toml-fuzz 20000
```

Первый параметр задаёт число проходов (без него выполняется 3000), второй — зерно
источника случайных чисел. Зерно закреплено, обращения к нему разнесены по отдельным
предложениям — прогон воспроизводим и на разных построителях.

Каждые пять процентов проходов генератор выводит отчёт о ходе работы: прогон на многих
миллионах проходов идёт часами, и молчание его от зависания неотличимо.

### Что считать результатом

```

           2777 trees, 2774 rewrites
```

Значение имеют отсутствие диагностики санитайзеров, отсутствие расхождений и доля
текстов, разобранных до конца: она держится около трети, и падение её почти до нуля
означало бы, что тексты отбраковываются первой же строкой, а дерево и перезапись не
проверяются вовсе.

Первый же прогон 12.08.2026 нашёл четыре дефекта, и все исправлены.

**События отвергнутой записи доходили до потребителя.** Запись неделима: события её
выдаются все разом либо не выдаются вовсе, — а очередь собранных событий при отказе не
очищалась. Подача целиком успевала выдать события записи, отвергнутой ниже по тексту, а
подача кусками откатывала их вместе с самой записью: выдача зависела от нарезки.
Закреплено проверкой `CodecTomlReader.RejectedRecord`.

**Отложенный отказ приведения к UTF-8 выдавался лишь одним путём разбора.** Отказ этот
откладывается до исчерпания уже приведённого начала текста, а выдавала его одна лишь
подача куска. Подача же текста целиком доводит разбор до конца переходом к следующему
событию — и отказ пропадал вовсе: недопустимая последовательность UTF-8 принималась
молча. Выдача вынесена в общий для обоих путей метод; закреплено проверкой
`CodecTomlReader.DeferredEncodingFailure`.

**Пустое имя сталкивалось с верхним уровнем.** Описание дозволяет имя ключа пустым, а
полные имена собирались соединением частей разделителем между ними: таблица `[""]`
давала то же полное имя, что и верхний уровень, и ключ её считался повтором
одноимённого ключа верхнего уровня. Тот же изъян был и в указателе дерева, где обход по
дочерним именам возвращался к началу и **не кончался вовсе** — на нём ворошитель и
завис. Разделитель ставится теперь перед всякой частью; закреплено проверками
`CodecTomlReader.EmptyTableName` и `CodecTomlDocument.EmptyKey`.

**Возврат каретки терялся при записи молча.** Разбор приводит пару «возврат каретки —
перевод строки» к одному переводу, а запись многострочной ограды ставила её собою: при
обратном чтении возврат каретки пропадал. Записывается он теперь управляющей
последовательностью, а многострочная дословная ограда, последовательностей не
признающая, его не несёт вовсе и уступает место основной. Закреплено проверкой
`CodecTomlWriter.CarriageReturn`.

Договор о правке дерева нашёл пятым **заведение записи поверх занятого имени**: правка
объявляла таблицу поверх пары, заводила пару поверх таблицы и поверх набора таблиц, а
собранный такой правкой текст разбор отвергал переопределением. Занятость имени
проверяется теперь в месте правки — вместе со всеми объемлющими именами и с порядковым
номером таблицы набора; закреплено проверкой `CodecTomlDocument.Redefine`.

Прогон на полумиллионе проходов 12.08.2026 нашёл ещё четыре дефекта разбора — все они
скрывались за пределами тех восьми тысяч проходов, которыми модуль проверялся прежде.

**Отложенный отказ приведения к UTF-8 разбор заклинивал.** Отказ выдавался лишь по
исчерпании приведённого начала текста, а запись, оборванная посреди, откатывается к
своему началу и ждёт продолжения. Продолжения нет и не будет — приведение отказом
прекращено, накопленный текст больше не пополнится, — и разбор оставался в ожидании
навсегда: с признаком поступления текста целиком он не завершался ни успехом, ни
отказом. Оба зовущих пути зовут выдачу по исчерпании событий, то есть по остановке
разбора, и ждать там нечего: условие снято. Местом отказа берётся теперь конец
накопленного текста — тот знак, на котором приведение оборвалось.

**Разбор отметки времени решал без знака, которого не видел.** Описание дозволяет
отделять время от даты пробелом, и завершает ли пробел запись значения, видно лишь по
знаку за ним. Обрыв накопленного текста ровно на этом пробеле разбор решал одной датой
— и отвергал её построением отметки, тогда как подача целиком читала полную отметку
времени. Закреплено проверкой `CodecTomlReader.StampSpaceBoundary`.

**Таблицу, объявленную исподволь, дозволялось дополнить набором таблиц.** Заголовок
`[a.b]` и составное имя ключа `a.b = 1` заводят таблицу `a`, собственного объявления не
имеющую, — а учёт объявленного держал одни лишь имена объявленные, и `[[a]]` за ними
проходил. Описание это запрещает: значение по имени меняло бы свой тип. Мало того,
дерево настроек адресует таблицы набора порядковым номером частью имени, и `[value.0]`
рядом с `[[value]]` давали одно и то же полное имя — правка такого дерева собирала
текст, который разбор отвергал. Закреплено проверкой
`CodecTomlReader.ImplicitTableAppend`.

**Примечание принимало управляющие знаки.** Описание дозволяет ему из управляющих одну
лишь табуляцию. Возврат каретки к тому же неотличим в примечании от окончания строки:
разбор отбрасывал его окончанием, запись ставила перевод строки, и первая перезапись
текста расходилась со второй — договор об устойчивости перезаписи нарушался. Запись
такие примечания отвергала и прежде; отвергает теперь и разбор. Закреплено проверкой
`CodecTomlReader.CommentControlCharacter`.

Тем же прогоном нашлись два изъяна пределов разбора, ворошителем не ловимые, — они
проступили при разборе его находок. **Предел длины записи мерялся вместе с окончанием
строки**: одна и та же строка предел то превышала, то нет — смотря по тому,
оканчивается ли ею текст, и каким из двух видов окончания она отделена от следующей.
**Место отказа указывало мимо виновной записи**: предел меряется по разборе записи
целиком, а разбор к этому времени стоит уже на следующей строке. Закреплено проверками
`CodecTomlReader.LineLimitTerminator` и `CodecTomlReader.LineLimitLocation`.

Аудит кода с нуля 12.08.2026 нашёл десять дефектов, ворошителем не ловимых: договоры
его сличают разбор с разбором и запись с чтением, а согласие обоих с описанием TOML
проверить нечем - неверно понятое правило описания оба слоя понимают одинаково неверно.
Найденное свелось к учёту объявленных имён и к согласию пределов записи с пределами
разбора.

**Учёт имён перестроен.** Три разрозненных перечня - объявленных имён, наборов таблиц
и таблиц, заведённых исподволь, - сведены в один указатель «имя → род», и всякое
правило описания проверяется теперь одним обращением. Прежним устройством проходили
шесть построений, описанием запрещённых: пары встроенной таблицы без запятой между
ними, повтор ключа внутри встроенной таблицы, дополнение закрытой встроенной таблицы
парой либо заголовком, пара поверх таблицы, заведённой составным именем ключа, пара
под простым значением и заголовок поверх таблицы, заведённой составным именем ключа.
Правила правки дерева настроек приведены к тем же родам имён.

**Пределы записи разошлись с пределами разбора надвое.** Предел глубины вложенности
запись мерила вместе с уровнем самой пары и отвергала перечень там, где разбор его
принимал. Предел длины записи терялся у примечания, дописываемого к готовой строке:
длина считалась заново по последней физической строке, и многострочная запись обходила
предел - собранный текст читающий отвергал длиной.

**Учёт имён одной записи был квадратичным.** Всякое объявляемое имя сличалось перебором
со всеми, объявленными записью прежде: встроенная таблица из восьми тысяч ключей
разбиралась семьдесят миллисекунд. Указатель имён заводится теперь по превышении порога
их числа - обычной записи он не стоит ничего, а враждебной даёт равномерный рост.

Закреплено проверками `CodecTomlReader.InlineSeparators`, `InlineDeclarations`,
`DottedOccupancy`, `ArrayCarriageReturn`, `InlineScaling`, `Conformance`,
`CodecTomlWriter.DepthLimitMatchesReader`, `LineLimitMatchesReader`,
`TrailingLineLimit`, `CodecTomlDocument.EditRules` и `EditReadable`. Отдельной проверкой
`Conformance` сведён набор из восьмидесяти шести случаев, взятых из самого описания:
всякий разбирается вдобавок шестью размерами куска подачи.

Третий проход, сверенный с отчётом стороннего разбора, нашёл ещё три расхождения.

**Примечания внутри перечня терялись перезаписью.** Разбор их пропускал, событий не
выдавая, и дерево о них не знало: `a = [1, # первое` перезаписывался без примечания
вопреки договору дерева, обещающему их сохранность. Примечание внутри перечня строкою
текста настроек не является и держится теперь самим узлом значения - вместе с местом
своим и с тем, стоит ли оно своей строкой или дописано к строке значения. Разбору
добавлена выдача события, записи - методы `remark` и `remarked`, а трижды повторённый
разбор примечания сведён в один метод `commented`.

**Ноль пределом глубины значил у разбора и у записи разное.** Разбор им запрещает
вложенность вовсе, запись же считала его снятием предела: дерево с настройками разбора
`maxDepth = 0` собирало перечень, который читающий отвергает. Смысл выровнен по разбору.

**Имена без кавычек принимали всякий знак вне US-ASCII.** Черновик следующей версии
описания, на который настройка `unicode` и ссылается, дозволяет имени буквы и цифры
письменностей мира, но не знаки препинания и не знаки оформления: имя `a©b` разбор
принимал, а черновик его не дозволяет. Набор задан теперь перечнем границ, взятым из
черновика дословно, и общ у разбора с записью.

Закреплено проверками `CodecTomlDocument.ArrayRemarks`, `CodecTomlWriter.DepthLimitZero`,
`ArrayRemarks` и `CodecTomlReader.UnicodeNames`.

Четвёртый проход нашёл дыру в построении записи дробного числа. **Запись `1.e2`
принималась числом.** Построение проверялось набором знаков записи да первым и
последним знаком её: знаки записи `1.e2` все дозволены, первый и последний - цифры, а
числом по описанию она не является - десятичная точка обязана нести цифру и слева, и
справа. Приведение к числу строило из неё сотню. Тем же путём проходили `1.e+2`,
`1.e-2` и `+1.e2`. Проверка набором знаков заменена разбором по правилу описания:
целая часть, дробная за точкой, порядок за знаком его, - и запись, разобранная не до
конца, отвергается. Закреплено проверкой `CodecTomlReader.FloatGrammar`; двести тысяч
случайных разрядов дробного числа прошли оборот «запись - чтение» без потери значения.

Пятой находкой ворошитель поймал **мою собственную правку скорости**. Повторный разбор
записи при мелкой нарезке был квадратичным, и ограда против него откладывала разбор
записи до знака конца строки среди пришедшего текста - довод точный, ибо записи иначе не
окончиться. Точен он, однако, лишь покуда текст вправе прирасти: отказ приведения к
UTF-8 накопленный текст обрывает, знака конца строки уже не будет, и запись, до него
отложенная, оставалась неразобранной - наружу выходил отказ приведения вместо ошибки
самой записи:

```
chunk=1 outcome differs: state 3/3 error 29/4 at 2:1/2:9 offset 14/22
```

Условие ограды дополнено отказом приведения. Прогон после правки дал те же 26 667 322
события и 158 599 деревьев, что и прогон до ограды: выдача не изменилась ни на одно
событие, изменилась одна лишь цена её. Закреплено проверками
`CodecTomlReader.TruncatedDecodingOutcome` и `ChunkScaling`.

Шестой проход занялся правкой дерева, и нашлась **неограниченно растущая память**.
Правка замещает узел значения новым, а прежний оставляет мусором - изъять его на месте
нельзя, ибо прежнее значение вправе нести вложенные узлы; снятая запись остаётся
надгробием, а строковое содержимое дописывается к хранилищу всякий раз. Четыреста тысяч
правок двух ключей отнимали **сто тринадцать мегабайт** при неизменном составе дерева.
Дерево уплотняется теперь само - записи, узлы, части имён и хранилище знаков собираются
заново, - по накоплении мусора вровень с живым: **113 МБ обратились в 96 КБ**, а
задержка правки осталась прежней, 0.18 мкс. Закреплено проверкой
`CodecTomlDocument.EditFootprint` и сценарием замера «долгая правка дерева».

Порог замера был сперва взят неверно: мерился объём выделенной памяти, а он удержания
не меряет вовсе - дерево без уплотнения давало по нему 466 октетов на правку, дерево с
уплотнением 434. Заведён прямой показатель `Document::footprint()`, а замер переведён на
задержку, которою видно слишком частое уплотнение.

Седьмой проход нашёл три дефекта, два из которых внесены правкой шестого.

**Повтор ключа во встроенной таблице, имени не имеющей, принимался.** Запись
`t = {a = 1, a = 2}` разбор отвергал, а `t = [{a = 1, a = 2}]` принимал: учёт ключей
ведётся по полному имени, а таблице, записанной значением перечня, имени не давалось
вовсе. Довод «у таблицы в перечне имени нет, ключи её не конфликтуют» неверен: ключи
конфликтуют внутри одной таблицы, и соседние таблицы перечня тут ни при чём. Такой
таблице даётся теперь своё имя - «@» со счётом, - живущее лишь до конца записи: полное
имя настоящего ключа начинается разделителем частей, и столкнуться ему не с чем, а в
объявленные имена оно не переносится. Закреплено проверкой
`CodecTomlReader.AnonymousInlineDuplicates`.

**Учёт мусора при снятии пары вёлся мимо скобок.** Правка шестого прохода добавила
счёт снятой записи в ветвь `if` без фигурных скобок, и счёт этот шёл при всяком снятии,
а не при снятии с примечанием: уплотнение приходило чаще нужного. Закреплено проверкой
`CodecTomlDocument.EraseGarbageCount`.

**Заведение пары выдавало указатель на чужой узел.** Уплотнение, шестым проходом
заведённое, вправе прийти посреди заведения новой пары - имя её дописывается к
хранилищу знаков и порог перешагивает, - а перечень узлов оно переносит: указатель,
взятый до уплотнения, указывал на чужой узел либо за край перечня. Запись пары
находится теперь заново по перестроении указателей. Закреплено проверкой
`CodecTomlDocument.EditAfterCompaction`, которая без правки валится выходом за край.

Тем же проходом закрыты два наблюдения об обратной записи. **Знак нулевого смещения
часового пояса терялся**: запись «-00:00» перезаписывалась как «+00:00», а описание
отводит им разный смысл - первою обозначено смещение неизвестное, второю смещение,
заведомо нулевое. Само смещение знака нести не может, и держится он теперь отдельным
признаком рядом с признаком записи знаком «Z»; генератор порождает такие отметки и
сличает признак наравне с прочими. Закреплено проверкой
`CodecTomlReader.NegativeZeroOffset`. **Хвост пробелов в примечании** оказался
расхождением описания с намерением, а не кода с описанием: ведущие пробелы снимаются
затем, чтобы запись не наращивала их своим разделителем при каждом обороте, а хвостовые
писаны человеком, и снимать их значило бы править файл без спросу. Поправлено описание
поля.

Восьмой проход занялся согласием слоёв между собою и полнотою чтения дерева.

**Календарь проверялся одним лишь разбором.** Запись и правка дерева сличали одни
пределы полей: дата «2026-02-31» пределам отвечает, а в календаре её нет - и правка
собирала текст, который свой же разбор отвергает. Проверка вынесена в общий метод
`toml::calendar` и применена во всех трёх слоях, а правка отметки сличает заодно и
время. Закреплено проверкой `CodecTomlDocument.StampCalendar`.

**Составные значения читались лишь одним уровнем.** Запись `a = [[1, 2], [3, 4]]`
выдавала внутренний перечень видом значения, а спуститься внутрь было нечем; та же беда
у встроенной таблицы во встроенной таблице и у встроенной таблицы значением перечня -
`servers = [{host = ...}]` читалось одним лишь обходом событий. Остаток составного
имени ведёт теперь внутрь значения: порядковым номером в перечень, именем ключа во
встроенную таблицу. Порядок поиска - от самого длинного начала имени к самому
короткому, - оттого таблица набора номером адресуется по-прежнему. Закреплено проверкой
`CodecTomlDocument.NestedReading`.

**Потолок хранилища знаков при правке.** Отрезок хранилища задан смещением в четыре
октета, и разбор текст длиннее отвергает, а правка наращивала хранилище молча. Правка
отвергается теперь отказом прежде, чем что-либо в дереве меняется.

Сам генератор нашёлся неисправным дважды. **Приведение к UTF-16 принимало избыточные
последовательности UTF-8**: `\xC1\xBE` оно обращало в знак `~`, то есть строило из
текста, разбором отвергаемого, текст правильный — и итоги двух кодировок расходились по
вине приведения, а не кодека. **Диагностика правки дерева не показывала ни исходного
текста, ни внесённых правок**: расхождение обнаруживается по трём правкам разом, и
повторить его было нечем.

## Разметка XML

`xml.cpp` — структурный генератор для [кодека разметки XML](../../src/codec/xml),
устроенный по образцу генератора INI и с той же **дифференциальной сверкой подачи**.

Текст разметки строится объявлениями всех видов, описанием типа документа с
внутренним подмножеством (сущности простые, содержащие разметку, ссылающиеся на
себя и раскрывающиеся многократно; объявления умолчаний атрибутов; внешний
источник), узлами с пространствами имён и без, атрибутами в кавычках обоих видов и
без них, содержимым со ссылками на отведённые договором сущности и числовыми,
разделами дословного текста, примечаниями, указаниями обработчику, знаками не из
набора ASCII, недопустимыми последовательностями UTF-8 и концами строк всех трёх
видов — приведение их к одному переводу строки договор требует повсюду, вплоть до
значений объявляемых сущностей. Настройки разбора
выбираются случайным сочетанием признаков, а у четверти проходов поджимаются и
пределы — глубины, длины имени, количества атрибутов и сущностей, объёма
подстановки и объёма одного события.

Половина текстов строится **заведомо правильными**: разметка, отвергаемая первой же
меткой, до разрешения пространств имён, подстановки умолчаний и сборки дерева не
доходит вовсе, и пути эти остались бы непройденными. Треть всех текстов затем
портится точечной заменой, вставкой и удалением знака, а также обрезанием.

Проверяется десять договоров:

- **подача целиком равна подаче кусками** — сличается вся выдача разбора: вид
  события, имя узла с префиксом и обозначением пространства имён, содержимое,
  глубина, обращение с пробельным содержимым, признак самозакрывающейся метки,
  перечень атрибутов со значениями и перечень объявлений пространств имён. Кусков
  берётся три размера на текст, и первый из них всегда однобайтовый: расхождения
  предела объёма события проступают лишь при таких размерах, где накопление
  успевает превысить предел прежде, чем построение будет дочитано;
- **итог разбора совпадает** — состояние по завершении, код отказа и место его
  обнаружения обязаны совпасть при всякой нарезке: текст, отвергнутый целиком по
  одному поводу, а кусками по другому, выдаёт зависимость выдачи от устройства сети;
- **дерево обходится целиком** — по всем узлам берутся имена, содержимое, места,
  атрибуты по имени и числом, поиск вложенного узла и поиск по всему поддереву;
- **дерево связно** — узел, полученный движением вперёд, вниз либо вверх, обязан
  вернуть исходный движением обратно, а обходы вперёд и назад — дать одно число
  вложенных узлов;
- **перезапись сохраняет смысл** — слепок дерева, собранного разбором перезаписи,
  сличается со слепком исходного: имена берутся обозначением пространства имён и
  местным именем без префикса (запись назначает префиксы заново), атрибуты
  упорядоченно, подряд идущее содержимое слитно;
- **кодировка исходного текста разбора не меняет** — тот же самый текст приводится
  к UTF-16 обоих порядков байтов и подаётся заново, целиком и кусками по одному и по
  три байта: границы кусков ложатся при этом посреди шестнадцатибитных значений и
  посреди суррогатных пар. Сличается вся выдача, включая место каждого события;
  смещение в байтах не сличается — оно кодировкой разнится по самому устройству;
- **записанное читается обратно** — дерево записывается и разбирается повторно;
- **поддерево записывается наравне с корнем** — записывается случайно выбранный узел
  дерева, а не только корень: пространства имён предков запись обязана объявить
  заново, а обращение с пробельным содержимым, заданное выше по дереву, — унаследовать.
  Слепок записанного поддерева сличается со слепком исходного узла;
- **круговой ход владеющего значения** — с того же случайно выбранного узла снимается
  владеющее значение и гоняется тремя ходами: пересобирается потоковым сборщиком узел за
  узлом, прививается обратно в дерево принимающего документа и записывается в текст с
  последующим разбором. Всякий раз итог сличается со снятым значением сравнением самих
  значений, а не записей их;
- **перезапись устойчива** — второй перезаписи положено совпасть с первой знак в
  знак.

Устойчивость проверяется на обоих видах записи, всеми тремя знаками отступа. При
нарядной записи слепки сличаются без пробельного содержимого: отступы она ставит
сама и вправе их как убрать, так и добавить. Послабление это, однако, даётся не
везде: внутри узлов под отведённым атрибутом `xml:space` и рядом с разделами
дословного текста пробельные знаки значимы, и слепок берёт их знак в знак. Ровно
там прятались два расхождения, найденные последним кругом разбора. Повторный разбор ведётся со снятыми
пределами: запись вправе быть длиннее исходного текста, оставаясь ему равнозначной,
— знаки за пределами US-ASCII записываются числовыми ссылками по десятку байтов на
знак.

### Сборка и запуск

Кодек ни от чего в проекте не зависит, кроме таблицы разбора чисел:

```sh
ROOT=$(pwd)
c++ -std=gnu++17 -O1 -g -fsanitize=address,undefined -I$ROOT/include \
	-o /tmp/xml-fuzz $ROOT/src/codec/xml/*.cpp $ROOT/src/num/lexical/table.cpp \
	$ROOT/tools/fuzz/xml.cpp

/tmp/xml-fuzz 400000
```

Первый параметр командной строки задаёт число проходов (без него выполняется 3000),
второй — зерно источника случайных чисел. Зерно закреплено по умолчанию, обращения к
источнику разнесены по отдельным предложениям — прогон воспроизводится и у других
построителей. Задавать зерно иным стоит затем, что построения одного зерна
складываются в один и тот же набор, сколько проходов ни задай: несколько зёрен
обходят разметку шире, чем один длинный прогон.

### Что считать результатом

```
xml fuzz: seed=369102, 400000 texts (133181 corrupted), 10045101 events, 139267 parsed
          to the end, 400000 trees, 417801 rewrites, 106387 of 133514 intact texts accepted,
          139267 values, 139267 builds, 139267 grafts
```

Значение имеют отсутствие диагностики санитайзеров, отсутствие расхождений и
**доля принятых правильных текстов** — последняя пара чисел. Она держится около
восьми десятых: остаток отвергается поджатыми пределами разбора, и это в порядке
вещей. Падение её заметно ниже означало бы, что правильная разметка отвергается
по недосмотру, и глубокие пути не проверяются. При расхождении печатаются размер
куска, номер разошедшегося события, все настройки разбора и сам текст разметки в
шестнадцатеричном виде.

Первый же прогон нашёл три дефекта, и все три исправлены:

- приведение исходного текста к UTF-8 отбрасывало проверенное начало отрезка при
  отказе посреди него, а отказ выдавался прежде разбора уже приведённого начала —
  подача целиком теряла события, которые подача кусками выдавала. Ровно тот же
  дефект был и у кодека INI: заголовок обещает независимость выдачи от нарезки, и
  проверять её следует у всякого потокового разбора;
- предел объёма одного события держался по-разному в зависимости от нарезки: по
  ходу накопления он сличался с длиной разметки, а по готовому событию — с его
  содержимым. Событиям, чьё содержимое короче своей разметки, — началу узла,
  описанию типа документа, указанию обработчику, содержимому со ссылками на
  сущности — одной проверки содержимого мало, и текст, пришедший целиком, проходил
  мимо предела там, где тот же текст кусками отвергался;
- содержимое, целиком составленное ссылками на сущности с пустыми значениями,
  выдавалось пустым событием. Дерево получало от него пустой узел содержимого,
  из-за которого запись узла переставала складываться самозакрывающейся меткой, и
  переход текст→дерево→текст, повторённый дважды, давал разное написание.

Четвёртый вскрылся уже разбором самих исправлений, и он того же рода: проверка
предела стояла перед выдачей события, а до неё ведут три хода, событий не дающих
вовсе — пробельное содержимое вне корневого узла, содержимое из ссылок на пустые
сущности и обрыв содержимого началом подставляемой сущности. Ходы эти проверку
обходили, а накопление кусков — нет: двести пробелов перед корневым узлом при
пределе в двадцать четыре байта разбирались целиком и отвергались кусками. Проверка
перенесена туда, где конец содержимого уже известен, а пропускающие ходы ещё
впереди. Ворошитель научен сличать по трём размерам куска сразу — прежним одним
размером расхождение не ловилось.

Второй разбор — уже самих исправлений — нашёл ещё два дефекта того же рода, и оба
исправлены:

- **место события зависело от нарезки**. Место считается по ходу разбора и только
  вперёд, а раздел дословного текста начинается на одном куске и дочитывается на
  следующих: к мигу выдачи его начало остаётся позади места разбора. Раздел,
  пришедший целиком, давал местом начало записи раздела, а разорванный границей
  куска — начало своего содержимого. Начало запоминается теперь при входе в раздел;
- **старшинство отказов зависело от нарезки**. Текст, и предел объёма события
  перебравший, и построенный ошибочно, отвергался целиком по ошибке построения, а
  кусками — по пределу: накопление до ошибки не доходило. Проверка предела
  переставлена прежде проверки конца текста, а обход открывающей метки за предел
  больше не заходит.

Оба нашлись оттого, что ворошитель научили сличать **место события и место отказа** —
прежде он сличал одно их содержимое.

Третьим тем же разбором нашлась **неповторяемость нарядной записи**: её отступы
дерево принимало пробельным содержимым, следующая запись отступала уже от них, и
разметка росла пустыми строками с каждым переходом текст→дерево→текст. Узлы со
смешанным содержимым при этом получали перевод строки прямо посреди текста. Запись
пробельного содержимого, порождённого прошлым отступом, снята, а узлы со смешанным
содержимым и узлы под `xml:space="preserve"` записываются в одну строку. Ворошитель
проверяет теперь устойчивость и нарядной записи тоже — прежде для неё стояло
послабление.

Последний круг разбора нашёл ещё три дефекта — все три вокруг обращения с
пробельным содержимым, и все три исправлены:

- **атрибут `xml:space` терялся без пространств имён**. Обращение с пробельным
  содержимым отведено самим договором о разметке, а не договором о пространствах
  имён, но и чтение, и запись искали атрибут разрешённым именем. С выключенным
  разрешением префиксов имя не разделено вовсе, поиск не находил ничего, и нарядная
  запись отступала внутри узла, пробелы которого значимы, — то есть меняла
  содержимое. Атрибут отыскивается теперь обоими написаниями;
- **раздел дословного текста считался незначимым, если собран одними пробелами**.
  Узел `<r><a/><![CDATA[   ]]><b/></r>` смешанным содержимым не признавался, и
  отступ вставал рядом с разделом, дописывая узлу пробельное содержимое. Раздел
  дословного текста значим теперь сам по себе, каким бы ни было его содержимое;
- **чтение и запись расходились в толковании негодного значения**. Договор отводит
  атрибуту ровно два значения; чтение всякое иное толковало отменой, а запись —
  сохранением. Толкование сведено к чтению.

Первые два прятались за послаблением самого ворошителя: нарядной записи прощалось
пробельное содержимое, и прощалось везде. Послабление сужено — там, где пробельные
знаки значимы, слепок берёт их знак в знак.

Последний круг нашёл **потерю значимых пробелов при записи поддерева**: узел, лежащий
под `xml:space="preserve"` предка, своего атрибута не несёт, и запись принимала его за
обычный — расставляла внутри отступы, то есть меняла содержимое. Запись определяет
теперь унаследованное обращение обходом вверх по дереву; закреплено проверкой
`CodecXmlWriter.Refusals` и девятым договором ворошителя, прежде писавшего один лишь
корень. Тем же кругом проверено изъятие разобранного начала буфера под разделом
дословного текста и при открытой подстановке сущности — оба хода держатся, и оба
дописаны в `CodecXmlReader.Compaction`.

Кругом ранее дефектов не нашлось, зато нашёлся **пробел в самом ворошителе**:
подача велась одной лишь кодировкой UTF-8, и обещание кодека разбирать один и тот же
текст одинаково во всякой принимаемой кодировке проверить было нечем. Пробел закрыт
седьмым договором. Кодировки ISO-8859-1 и US-ASCII ворошителем не подаются —
построить их из порождаемой разметки удаётся редко, — и проверены отдельно:
`CodecXmlEncoding.SameTextAcrossEncodings`.

Все десять закреплены проверками: `CodecXmlReader.DecodingPrefix`,
`CodecXmlReader.EventLimitChunking`, `CodecXmlReader.EmptyContent`,
`CodecXmlReader.EventLocation`, `CodecXmlReader.FailurePrecedence`,
`CodecXmlReader.SpaceWithoutNamespaces`, `CodecXmlWriter.PrettyStability` и
`CodecXmlDocument.RewriteStability`.

### Круг разбора 15.08.2026: молчаливый пропуск отказов записи

Круг начался с чтения кода записи и нашёл дефект, ворошителем не пойманный:
**цель указания обработчику с разделителем префикса разбор принимал, а запись
отвергала**. Договор о пространствах имён на цели указаний не распространяется, и
разделитель обычным знаком имени в ней является; проверялась же цель правилом
местного имени, где разделитель запрещён. Разбор с выключенным разрешением
префиксов такую цель принимает целиком, и разобранное дерево обратно не
записывалось. Закреплено `CodecXmlWriter.ProcessingTargetColon`.

Отчего ворошитель молчал — важнее самого дефекта. **Отказ записи он считал поводом
прекратить проверку, а не расхождением**: и перезапись дерева, и запись поддерева
при отказе выходили молча, а молчание неотличимо от согласия. Дерево, которое
разбор собрал, а запись принять отказалась, и есть дефект. Оба места теперь
докладывают отказ с кодом ошибки, и на них же цель с разделителем строится
четвертью указаний.

Усиление вскрыло **изъян самого ворошителя**: приведение к UTF-16 принимало байты
от `0xF8` за начало четырёхбайтового знака. Началом знака они не являются вовсе,
кодек такой текст верно отвергает, а приведение строило из отвергнутого текст
годный — и сличение кодировок ловило собственный изъян приведения вместо
расхождения кодека.

### Пробел: склейка гонялась одна лишь включённой

Самой крупной находкой круга оказался **пробел в охвате: ворошитель гонял склейку
подряд идущего содержимого одной лишь включённой**, а выключена она у разбора **по
умолчанию**. Весь путь частичной выдачи содержимого и дословных разделов — тот самый,
каким пользуются без указания настроек, — не проверялся вовсе. Причина понятна:
без склейки событий выходит тем больше, чем мельче куски, и сличать перечни знак в
знак нельзя. Сличать, однако, следует само содержимое, а не его нарезку на события:
подряд идущее содержимое одного вида сводится теперь в одно событие перед сличением.

Двум свойствам потоковости даны явные послабления, а не молчание:

- **содержимое, выданное до обнаружения отказа, отказом не отменяется.** Подача
  кусками успевает выдать его прежде, чем дойдёт до отказа, а подача целиком видит
  отказ сразу. Снимается одно последнее событие содержимого у обоих перечней, а
  выданное целиком обязано быть началом выданного кусками;
- **предел объёма одного события с выключенной склейкой поджимать нечем.** Число
  событий задаётся нарезкой, и каждая часть предела не достигает, тогда как то же
  содержимое целиком выходит одним событием и предел перебирает. Сочетание это чуждо
  всякой нарезке по устройству, и предел поджимается лишь при включённой склейке.

Открытая склейкой область дала **пять дефектов разбора**, все исправлены:

- **пустое событие дословного раздела.** Раздел, разорванный границами кусков, выдавал
  пустой хвост всякий раз, когда граница легла прямо перед его завершением. Дерево
  получало от него пустой узел содержимого, из-за которого запись переставала
  складываться самозакрывающейся меткой. Раздел, пустой сам по себе, своё единственное
  событие выдаёт по-прежнему;
- **место отказа у незавершённого раздела зависело от нарезки.** Место бралось от
  места разбора, а оно ушло вперёд ровно настолько, насколько успело выдаться
  содержимое. Берётся теперь начало раздела, снятое при входе в него;
- **старшинство отказов в содержимом задавалось порядком проверок.** Запрещённая
  содержимому последовательность конца дословного раздела искалась по всему
  содержимому разом и перекрывала ошибочную ссылку, стоящую в тексте раньше: то же
  содержимое кусками отвергалось по другому поводу. Отказ выдаётся теперь по тому
  поводу, что встретился в тексте раньше;
- **оборванная ссылка отсекалась не всякая.** Удерживалась одна лишь последняя ссылка
  куска, и лишь при полном отсутствии завершителя в буфере: ссылка, завершитель
  которой принадлежал уже другой ссылке за краем, разбиралась оборванной. Отсечение
  повторяется теперь до неподвижности, а завершитель сличается с концом выдаваемой
  части, а не с концом буфера;
- **вид события содержимого определялся по исходной записи, а не по приведённому.**
  Содержимое из ссылок на пустые сущности с пробелами следом выходило текстовым
  целиком, тогда как приведено оно к одним пробелам, — и кусок, ссылок не заставший,
  давал пробельное событие там, где кусок покрупнее давал текстовое.

Шестым исправлено **место содержимого, начатого ссылками на пустые сущности**: шаг,
события не выдавший, место разбора всё же проходил, и начало содержимого терялось.
Начало переносится теперь на следующий шаг.

Закреплены проверками `CodecXmlReader.PartialContent` и
`CodecXmlReader.ContentFailurePrecedence`.

Чтение кода нашло ещё один дефект, ворошителю недоступный: **размещение имени в
хранилище знаков разбора при переполнении выдавало пустой отрезок и запоминало код
ошибки, а разбор о нём не спрашивал**. Заголовок обещает обратить молчаливое
искажение в явную ошибку, но отказ наружу не выходил: узел получал пустое имя, а
связывание — пустые префикс и обозначение, и разбор шёл дальше, выдавая имена не в
тех пространствах имён. Ход достижим лишь на именах свыше четырёх гигабайтов в
одном разборе, то есть у потокового чтения, ради которого он и заведён.

### Прогон по отладочным стендам

Из сличения владеющего значения после записи **изъяты значения с соседствующим текстовым
содержимым**. Два соседних узла текстового либо пробельного содержимого запись сливает
воедино: разделявший их узел, чтением опущенный, — примечание либо указание обработчику, —
в тексте не появляется вовсе, и разбор записи даёт один узел вместо двух. Различие это —
свойство самого написания разметки, а не изъян кодека. Пересборка сборщиком и прививка
записи не касаются вовсе и потому проверяются на всяком значении.

Свёрток `include`, `src/codec/xml`, `src/num/lexical` и `tools/fuzz/xml.cpp`
разворачивается на стенде сам по себе — возраст тамошнего дерева значения не имеет.

Проверено 11.08.2026 на десяти стендах x86-64 (Ubuntu, Fedora, Alt, OpenSUSE,
NetBSD, OpenBSD, FreeBSD, Solaris, OpenIndiana, Windows 10 с MinGW-w64) вместе с
macOS ARM64: выдача совпала **знак в знак на всех одиннадцати** — по 20 000
проходов, с суммами событий, перезаписей и принятых правильных текстов.

Санитайзеры доступны не всюду — см. оговорку в разделе о настройках INI.

## Таблицы CSV

`csv.cpp` — структурный генератор для [кодека таблиц CSV](../../src/codec/csv).
Таблица строится записью, разбору поддающейся: поля, содержащие знаки, разбор
задевающие, берутся в кавычки с их отменой. Порча вносится отдельно и точечно —
заменой, вставкой либо изъятием одного знака: таблица, испорченная целиком,
отвергается первым же знаком, и глубокие состояния разбора так не достигаются.

Проверяется пять договоров сразу:

- **Независимость выдачи от нарезки.** Таблица подаётся целиком и кусками трёх
  размеров, первый из которых всегда однобайтовый. Сличается вся выдача целиком —
  вид события, содержимое, имя столбца, признаки кавычек и изменения содержимого,
  место в тексте, номера записи и поля. Сверх того сличается итог: код ошибки и
  место отказа.
- **Круговой ход таблицы.** Собранная контейнером таблица записывается обратно и
  разбирается вновь: количество записей, количество полей и содержимое каждого поля
  обязаны совпасть.
- **Круговой ход полей.** Поля со враждебным содержимым записываются при всяком
  сочетании правил записи и читаются обратно.
- **Потоковая выдача записей.** Выдача обработчику обязана давать те же записи, что
  и сборка таблицы целиком: путь этот проходит разбор иначе — буфер записи
  переиспользуется, и поля живут лишь на время вызова.

### Сборка и запуск

Кодек ни от чего в проекте не зависит, кроме приведения чисел:

```sh
ROOT=$(pwd)
c++ -std=gnu++17 -O1 -g -fsanitize=address,undefined -I$ROOT/include \
	-o /tmp/csv-fuzz $ROOT/src/codec/csv/*.cpp $ROOT/src/num/lexical/*.cpp \
	$ROOT/tools/fuzz/csv.cpp

/tmp/csv-fuzz 400000
```

Первый параметр командной строки задаёт число проходов (без него выполняется 3000),
второй — зерно источника случайных чисел.

### Что считать результатом

```
csv fuzz: 400000 passes, 400000 texts (133247 corrupted), 120744 survived,
          13364439 events, 12259 documents, 11352 rewrites, 120744 streams
```

Значение имеют отсутствие диагностики санитайзеров и отсутствие расхождений. При
расхождении печатаются размер куска, номер разошедшегося события, оба его вида, все
настройки разбора и сама таблица в шестнадцатеричном виде.

### Что в сверку намеренно не входит

Круговой ход проверяется не всегда: часть настроек содержимое поля изменяет по
указанию потребителя, и расхождение при них означало бы несогласованность настроек,
а не дефект. Из проверки исключены снятие обвязки, объявленный заголовок, дополнение
недостающих полей, поджатые пределы разбора и определение разделителя — последнее
затем, что перезапись меняет расстановку кавычек, и знак, бывший содержимым поля,
после неё вправе оказаться пригодным разделителем. Отдельно исключена запись из
единственного пустого поля: записывается она пустой строкой, а разбор пустые строки
пропускает — свойство самой записи CSV, а не дефект.

Первый же прогон нашёл пять дефектов, и все пять исправлены:

- место события выдавалось местом отказа у всех событий, оставшихся в очереди выдачи
  после него, — при подаче кусками очередь опустошалась до отказа, и расхождение
  зависело от нарезки;
- ошибка приведения к UTF-8 объявлялась прежде ошибки разбора, стоящей раньше по
  тексту: приведение ведётся над всем куском разом, а разбор — знак за знаком;
- определение разделителя брало образец разной длины при разной нарезке, отчего на
  одном и том же тексте выбирало разные разделители;
- правило «в кавычки все, кроме чисел» отвечало прежде проверки необходимости, и
  поле вида `\t\r\n0`, признанное числом, записывалось без кавычек — разрывая запись;
- поле, начинающее запись знаком примечания, записывалось без кавычек и читалось
  обратно строкой примечания, унося за собою всю запись; записи добавлена настройка
  знака примечания.

## Документы JSON

`json.cpp` — структурный генератор для [кодека JSON](../../src/codec/json).
Документ строится разбору поддающимся: вместилища вкладываются друг в друга, строки
собираются из знаков, разбор задевающих (кавычки, знак отмены, записи `\uXXXX` вместе с
суррогатными парами, знаки UTF-8 всех четырёх длин), числа берутся всех восьми видов —
от целого до непредставимого `1e500` и не вмещающегося в точность `9007199254740993`.
Порча вносится отдельно и точечно — заменой, вставкой либо изъятием одного знака: текст,
испорченный целиком, отвергается первым же знаком, и глубокие состояния разбора так не
достигаются.

**Настройки разбора выбираются прежде сборки текста**, и текст собирается с оглядкой на
них: примечания добавляются лишь при разрешённых примечаниях, записи нечисла и
бесконечности — лишь при разрешённых, поток документов — лишь при разрешённом потоке.
Иначе годный текст отвергался бы первым же запрещённым построением, и дерево с перезаписью
не проверялись бы вовсе: связывание сборки с настройками подняло долю разбираемых текстов
с 13% до 93%.

Проверяется пять договоров сразу:

- **Независимость выдачи от нарезки.** Текст подаётся целиком и кусками трёх размеров,
  первый из которых всегда однобайтовый. Сличается вся выдача целиком — вид события,
  содержимое, признак изменения содержимого разбором и место события: смещение, строка,
  положение в строке и глубина вложенности. Сверх того сличается итог: код отказа и место
  его.
- **Круговой ход дерева.** Собранное дерево записывается обратно и разбирается вновь:
  деревья сличаются узел за узлом — вид, имя поля, содержимое строк и значение чисел.
  Числа сличаются значением, а не записью: перезапись даёт кратчайшую запись, и «1.0»
  вернётся как «1».
- **Потоковая выдача документов.** Выдача обработчику обязана давать те же документы, что
  и сборка целиком: путь этот проходит сборку иначе — хранилище знаков очищается на всяком
  документе, а дерево заводится заново.
- **Круговой ход чисел через запись.** Число из случайных битов либо пограничное
  записывается писателем и читается обратно документом: запись обязана вернуть то же самое
  число, а не близкое к нему.
- **Круговой ход владеющего значения.** Значение снимается с собранного дерева и гоняется
  тремя ходами сразу: пересобирается потоковым сборщиком узел за узлом, прививается обратно
  в дерево принимающего документа и записывается в текст с последующим разбором. Всякий раз
  итог сличается со снятым значением сравнением самих значений, а не записей их.

### Сборка и запуск

Кодек ни от чего в проекте не зависит, кроме разбора чисел, а из тела того нужен один файл
— таблица степеней пятёрки:

```sh
ROOT=$(pwd)
c++ -std=gnu++17 -O1 -g -fsanitize=address,undefined -I$ROOT/include \
	-o /tmp/json-fuzz $ROOT/src/codec/json/*.cpp $ROOT/src/num/lexical/table.cpp \
	$ROOT/tools/fuzz/json.cpp

/tmp/json-fuzz 150000
```

Первый параметр командной строки задаёт число проходов (без него выполняется 3000),
второй — зерно источника случайных чисел. Зерно закреплено, поэтому прогон воспроизводим.

### Что считать результатом

```
json fuzz: 150000 passes, 150000 texts (100125 corrupted), 47252 survived,
           5734480 events, 47252 documents, 47252 rewrites, 150000 streams, 149959 numbers,
           47252 values, 47252 builds, 47252 grafts
```

Значение имеют отсутствие диагностики санитайзеров и отсутствие расхождений. При расхождении
печатаются размер куска, номер разошедшегося события, оба его вида вместе с местом, все
настройки разбора и сам текст в шестнадцатеричном виде.

### Что в сверку намеренно не входит

Пересборка объекта идёт **добавлением** имени (`builder_t::append`), а не установкой:
объект вправе нести повторяющиеся имена по настройке `duplicate_t::KEEP`, и установка
свела бы повторы в одно поле. Прежде такие значения из пересборки изымались вовсе —
сборщик воспроизвести повтор не умел.

Прививка проверяется на **существующем** месте принимающего дерева: прививка заменяет
поддерево, а не заводит новое поле, и отказ на несуществующем указателе законен.

Запись значения в текст, вернувшая пустой итог, расхождением не считается: поток записи
отвергает нечисло и бесконечность, разбором дозволенные, и пустой итог означает здесь
отказ, а не усечение.

Потоковая выдача сличается со сборкой целиком лишь на тексте об одном документе: сборка
целиком удерживает **последний** документ потока, и сличать её со всею выдачей нельзя.
Отказ разбора расхождением не считается вовсе — текст испорчен намеренно, и отвергнуть его
дело правильное; значение имеет лишь согласие двух путей.

Числа, вида с плавающей запятой не вмещающиеся (`1e373` и подобные), извлечению видом с
плавающей запятой не поддаются по правилу извлечения — такие сличаются записями, а
совпадение самих отказов извлечения проверяется отдельно.

### Первый прогон нашёл дефект

**Место отказа приведения кодировки не проставлялось вовсе.** Отказ выдавался кодом, а
место его оставалось неизвестным (`NO_OFFSET`, строка 0, столбец 0) — тогда как разбор
дошёл до негодного байта и место его знал. При подаче кусками место оказывалось проставлено
попутно, предыдущими событиями, и одно и то же расхождение зависело от нарезки текста.
Отказ приведения проведён общим путём, проставляющим место.

Отдельно замечено, но дефектом не признано: `location()` по договору отдаёт место **текущего
события**, и всякий `next()`, снятый после отказа, место отказа затирает. Потребителю
надлежит снимать место отказа сразу по возвращении `feed()`, как это и делает сборка дерева.

## Тексты YAML

`yaml.cpp` — структурный генератор для [кодека YAML](../../src/codec/yaml).

Текст строится **деревом, а не строками вперемешку**. Причина в самом устройстве YAML:
отступ там есть суть построения, и текст, собранный строками наугад, отвергался бы первой
же строкой — глубокие пути разбора так не достигаются вовсе. Оттого генератор рекурсивно
собирает отображения и перечни с верным отступом, а внутрь них кладёт всё, что разбор
умеет: обе ограды значений, блочные значения обоих видов со всеми правилами усечения и
указателями отступа, поточные скобки (в том числе растянутые на многие строки), метки,
ссылки на них, метки типов всех четырёх записей, директивы `%YAML` и `%TAG`, примечания
собственной строкой и за содержимым, пустые строки, простые значения с продолжением строкою
ниже, черты начала и конца документа, метку порядка байтов и оба вида окончания строки.

Порча вносится отдельно и точечно — заменой, вставкой, изъятием знака, обрезанием текста
либо вставкой знака горизонтальной подачи. Последняя выделена нарочно: знак этот в отступе
описанием запрещён, и порча им ведёт разбор по ветви отказа, случайным байтом почти
недостижимой.

Сличается три вещи:

- **выдача при подаче целиком против подачи кусками** трёх размеров, первый из которых
  всегда однобайтовый: сличается всё событие целиком — вид, тип значения, ограда, содержимое,
  имя метки, метка типа, строка, знак, глубина и смещение;
- **исход разбора** — состояние и код отказа: разбор, отказавший целиком и прошедший
  кусками, событиями разошёлся бы не всегда, а исход его переменился бы всё равно;
- **выдача в UTF-8 против UTF-16** обоих порядков байтов: текст приводится к UTF-16 самим
  ворошителем, а смещения перед сличением сбрасываются — считаются они байтами и кодировкой
  разнятся по устройству, тогда как строка и знак совпадать обязаны.

### Сборка и запуск

```sh
ROOT=$(pwd)
FLAGS="-DAWH_STATICLIB -isystem $ROOT/include -std=gnu++17 -O1 -g -fsanitize=address,undefined"

for NAME in common encoding reader; do
	c++ $FLAGS -c -o /tmp/y-$NAME.o $ROOT/src/codec/yaml/$NAME.cpp
done
c++ $FLAGS -c -o /tmp/y-fuzz.o $ROOT/tools/fuzz/yaml.cpp
c++ -fsanitize=address,undefined -o /tmp/yaml-fuzz /tmp/y-fuzz.o \
	/tmp/y-common.o /tmp/y-encoding.o /tmp/y-reader.o $ROOT/build/libawh.a

/tmp/yaml-fuzz 20000
```

Первый параметр задаёт число проходов, второй — зерно. Зерно закреплено, и прогон
воспроизводим: найденное расхождение повторяется тем же числом проходов.

## Находки ворошителя YAML (17.08.2026)

**Отказ приведения кодировки съедал уже прочитанные строки.** Подача текста
`a: 1\nb: 2\nc: <битая последовательность>` целиком выдавала одно событие, а подача по
байту — тринадцать. Приведение переносит в накопитель всё, что успело прочесть до битого
байта, но `feed()` объявлял отказ, не разобрав ни строки из перенесённого; при подаче по
байту строки те были разобраны кусками прежними, и отказ приходил уже за ними. Разбор
проведён прежде отказа, причём строка последняя, переводом не закрытая, разбору не подлежит:
прирасти ей уже нечем, но и признать текст оконченным нельзя — окончен он отказом, а не
концом своим. Закреплено проверкой `CodecYamlReader.BrokenEncoding`.

**Знаки, описанием тексту не дозволенные, проходили насквозь.** Функция `printable()` была
написана и не звалась ниоткуда — мёртвый код. Пустой байт и управляющие знаки попадали в
разбор наравне с содержимым. Проверка поставлена в приведение, а не в разбор: приведение
есть единственное место, через которое проходит всякий знак текста любой кодировки, и стеречь
в одном месте вернее, чем в четырёх. Закреплено проверкой `CodecYamlEncoding.Forbidden`.

**Дефект ворошителя, а не кодека.** Сличение кодировок дважды указывало на текст, несущий
пустой байт вторым знаком: `- \0\t ` в UTF-8 опознаётся как UTF-16LE и читается как `-`
и знак U+2009, а приведение тех же четырёх байтов к UTF-16 даёт совсем иное содержимое.
Опознание описанием задано прямо — пара `xx 00` в начале текста без метки порядка байтов
есть UTF-16LE, — и разбор тут верен: это попросту два разных текста, и расхождение их было
бы виною ворошителя. Сличение кодировок пропускается теперь, когда текст без метки опознан
не как UTF-8.

Третий случай той же природы вскрылся на тексте из одного пустого байта: приведение его к
UTF-16 даёт `FF FE 00 00`, а это ровно метка UTF-32LE — приведённый текст опознаётся как
UTF-32 и оказывается пустым. Двусмысленность заложена в самом описании (метка UTF-16LE, за
которой стоит знак U+0000, от метки UTF-32LE неотличима), и разбор тут ни при чём. Сличение
кодировок пропускается теперь и на текстах с пустым байтом — знак этот тексту YAML не
принадлежит вовсе, и приводить его к иной кодировке незачем.

## Находки ворошителя YAML по дереву документа (17.08.2026)

С постройкою дерева ворошитель стал сличать ещё две вещи: перезапись обязана читаться
обратно всегда, и второй проход перезаписи обязан дать то же, что и первый. Первое же
сличение нашло два дефекта чтения:

**Пустое значение пары выдавалось за концом отображения.** Метод `finish()` закрывал
уровни вложенности прежде выдачи значения, какого пара ожидала, и значение оказывалось
вне всякого построения — дерево клало его вторым корнем потока документов. Выдача
проведена прежде закрытия.

**Пара, у которой в строке стоят одни свойства узла, не помечалась ожидающей значения.**
Запись `имя: &метка` со значением строкою ниже читалась смешением построений: признак
ожидания ставился лишь тогда, когда за двоеточием не оставалось ничего, а метка да метка
типа за ним оставались. Признак ставится теперь прежде разбора остатка строки, а снимают
его сами разборы значений — каждый у себя.

## Разбор круговым ходом перезаписи (17.08.2026)

Открытая находка прежнего захода — «перезапись даёт отступ, обратным чтением не
принимаемый» — разобрана. Оказалось за нею не одно построение, а целая гряда дефектов, и
раскрывались они один за другим по мере починки прежнего. Разбор шёл до чистого прогона
в 600 000 проходов под ASan и UBSan; каждая находка закреплена проверкой.

Дефекты чтения:

**Пустая запись перечня не выдавалась вовсе.** Строка `- ` без содержимого за чертою есть
запись перечня с пустым значением, а выдачи её не было: перечень `- \n- beta` возвращал
одну запись вместо двух. Ожидание значения устроено теперь и для записи перечня, а от
ожидания значения пары его отличает одно — черта на отступе ожидания есть для пары
значение её, а для записи перечня запись следующая, и пустоту прежней надлежит выдать
прежде неё.

**Пустое значение выдавалось за закрытием уровней.** Тот же дефект, что был найден в
`finish()` заходом прежде, обнаружился и в разборе строки: пустота выдавалась после
`collapse()`, и запись `''` становилась именем следующей пары уровня объемлющего, а
значение её — значением пустоты. Выдача проведена прежде закрытия.

**Отступ блочного значения отсчитывался от начала строки.** Написание `- имя: |` кладёт
отображение на отступ два, строку же открывает черта на отступе ноль. Отсчёт от строки
брал содержимым и следующую пару того же отображения. Отсчёт ведётся теперь от отступа
объемлющего построения — как для порога окончания значения, так и для указателя отступа
в заголовке.

**Поточное построение метку типа не сличало.** Запись `!!str [ 1 ]` чтением принималась, а
перезапись её отвергалась несоответствием: сличение стояло лишь на пути блочном. Тело
сличения вынесено в общий метод и зовётся со всех трёх мест открытия построения.

**Свойства узла перед вложенным поточным построением не разбирались.** Запись
`[ !!seq [ 1 ] ]` шла разбором значения, скобку прочитавшим началом записи без ограды.
Свойства снимаются теперь прежде проверки на вложенное построение.

Дефекты записи:

**Черта вложенного перечня пропадала.** Сжатое написание перечня внутри перечня есть
`- - значение`, а не `- значение`: первая запись вложенного перечня становилась значением
записи объемлющего. Вместилищу же, свойства несущему, написание это описанием запрещено —
метка стала бы между двумя чертами, — и открывается оно строкою ниже.

**Узлы, корнем документа стоящие, строку за собою не закрывали.** Вместилища над корнем
нет, и признак открытой строки ставить было некому: черта следующего документа
приписывалась к корневому значению вплотную, содержимое блочного значения ложилось в
строку заголовка, а черта первой записи перечня липла к метке. Признак ставят теперь сами
записи — значения, свойств и заголовка.

**Пробелы в конце строки оставались.** Запись `- ` пустого значения оставляла за собою
пробел. Закрытие строки снимает их — кроме строк блочного значения, где они суть
содержимое само.

**Указатель отступа блочного значения не ставился, когда содержимое открывалось пустыми
строками.** Отступ читается по первой непустой строке, а проверка глядела на первую вовсе,
и ведущий пробел содержимого пропадал круг за кругом.

**Знак возврата каретки передавался блочным построением.** Описание велит приводить пару
`CR LF` да одинокий `CR` к переводу строки при чтении, и знак пропадал. Запись отвечает
теперь отказом и отсылает содержимое ограде двойной.

**Непечатные знаки Юникода проходили записью насквозь.** Отмена шла по байту, а не по
знаку: `U+0081` записан байтами `C2 81`, из коих управляющим не является ни один. Отмена
идёт теперь по знаку Юникода, и тем же знаком решается выбор двойной ограды.

**Многострочное значение получало ограду одинарную.** Проверка неотменимых знаков шла
после разрешения вида, а запись, разрешаемая не строкою, до неё не доходила вовсе.
Проверка проведена прежде разрешения.

Дефекты дерева документа:

**Пустота записывалась записью `null`.** Подпорка эта стояла оттого, что чтение записи
`- ` пустоты не выдавало; с починкой чтения она стала вредной — метка типа, значению
предпосланная, отменяет разрешение схемы, и `!своя null` возвращалось строкою. Осталась
она лишь корню документа, и по иной причине: документ, ничего не записавший, пропал бы из
потока вовсе.

Прочее:

**Шестидесятиричная запись за пределом целого вида.** Разряды накапливаются дробным видом,
и число их описанием не ограничено: запись из десятка разрядов выходит за предел
`uint64_t`, а приведение к целому есть неопределённое поведение. Поймано UBSan, выдаётся
теперь дробным видом.

**Вина ворошителя.** Пределы глубины и длины значения при обратном чтении перезаписи не
ставятся: ссылки деревом раскрываются, и перезапись раскрытого дерева законно глубже
исходного текста.

## Находки ворошителя YAML по удержанию исходного текста (17.08.2026)

С удержанием исходного текста ворошитель стал сличать самое сильное: перезапись
нетронутого дерева обязана быть **побайтово равной исходному тексту**. Проверка эта
расходится на всяком примечании, всякой пустой строке и всякой ширине отступа — на всём,
чего дерево не держит. Нашла она пять дефектов:

**Событие блочного значения стояло там, где оно окончилось.** Положение бралось у строки,
содержимое закрывшей, а не у строки заголовка: событие `|` со строки третьей отчитывалось
шестою. Дефект тот прежде виден не был — положение это никому не требовалось, — а
удержание считает по нему начало записи узла, и куски текста поехали. Положение
запоминается теперь при разборе заголовка и ставится событию при выдаче, ровно как оно
уже делалось для простого значения многострочного.

**Документ принимал два корня.** Написание ` - a` со строкою `- b` за ним закрывало
перечень отступа мельче и открывало новый — а корень у документа один. Проверка на
содержимое за завершённой записью стояла прежде закрытия уровней и оттого молчала: уровень
был ещё открыт. Проверка повторена за закрытием.

**Примечание, за значением стоящее, отбирало начало записи у следующего узла.** Строка
`host: localhost # адрес` кончалась примечанием, и оно объявлялось предисловием пары
следующей — запись пары прежней обрывалась на нём, а примечание уходило соседу. Начало
записи берётся теперь лишь у примечания, строку свою открывающего.

**Пустая строка в конце дословного переноса усекалась.** Закрытие строки снимает пробелы
в конце её, а строка, дословно перенесённая, есть исходные байты, и усекать в ней нечего.
Заведён отдельный признак: строка перенесённая усечению не подлежит, и завершение записи
её не закрывает вовсе — перевод строки был бы знаком, исходным текстом не данным.

**Метка порядка байтов в смещениях не считалась.** Чтение снимает её прежде разбора и
считает смещения по тексту без неё, а удержан текст поданным целиком: всякое смещение
указывало на три байта раньше нужного. Поправка на длину метки внесена, а описание поля
положения исправлено — смещение считается по тексту, к UTF-8 приведённому.

**Вина ворошителя.** Побайтовое равенство спрашивается лишь у текста в кодировке UTF-8:
удержание работает только там, а текст иной кодировки перезаписью приводится к UTF-8.

## Находки ворошителя YAML по правке дерева (17.08.2026)

С заведением правки ворошитель стал править узел по случайному пути и сличать, читается
ли перезапись обратно. Проверка эта бьёт по стыку двух кусков — собранного заново и
перенесённого дословно, — и стык этот разъезжается легче всего. Нашла она шесть дефектов:

**Записи поточного построения переносились дословно.** Строкою они не отделены: их стоит
на строке сколько угодно, и перенос вырезал строку целиком — вместе со скобками соседей.
Чтение извещает теперь признаком `flow`, а дерево записи в тексте таким узлам не ставит
вовсе: собираются они заново.

**Снятие метки оставляло ссылки на неё без объявления.** Раскрытие ссылок дерево помнит, а
запись `*метка` возвращалась дословным переносом как есть. Снятие узла с меткою объявляет
теперь дерево правленым целиком: раскрытия соберутся заново значениями своими.

**Черта записи перечня терялась.** Написание `-` со значением строкою ниже кладёт черту в
строку свою, а собственная строка узла стоит ниже: перенос его начинался со строки
значения, и записи перечня сливались с объемлющим построением. Та же ошибка была в отступе
собираемого перечня — отступ брался у строки значения вместо строки черты.

**Граница записи узла заходила за конец документа.** Черта `---` принадлежит документу
следующему, а `...` — прежнему: перенос последнего узла возвращал их вторым разом, а
содержимое, правкой добавленное, ложилось за чертою конца — вне всякого документа.

**Директивы уходили документу соседнему.** Начало документа чтение берёт у черты `---`, а
`%YAML` да `%TAG` стоят прежде неё и принадлежат ему же: перезапись оставляла директиву
без документа своего.

**Документ, собранный заново, черты конца за собою не оставлял.** Документ следующий,
дословно переносимый, вправе открываться директивою — а директива за содержимым без черты
конца читается отказом. Черта ставится теперь сама.

## Находка ворошителя CSV (14.08.2026)

**Поле, содержащее метку порядка байтов, теряло целую запись.** Метку, стоящую в самом
начале текста, разбор снимает как признак кодировки. Поле, её содержавшее и оказавшееся
первым в таблице, после перезаписи опустевало; запись из одного лишь пустого поля
записывается пустой строкой, а пустые строки разбор пропускает — таблица теряла запись
целиком. Круговой ход давал три записи против четырёх, а виновником был не разбор, а
запись: она выдала текст, который собственный разбор читает иначе.

Ограда поставлена по образцу той, что уже стояла для знака примечания: поле, стоящее в
самом начале собираемого текста и начатое меткой, берётся в кавычки. При записи без
кавычек вовсе оградить метку нечем — этот случай ограда пропускает намеренно.

Закреплено проверкой `CodecCsvWriter.SignatureField`: без правки она падает на
потерянной записи, показывая одну вместо двух.

## Разбор 16.08.2026 (кодек TOML): два свода правил, две квадратичности и выделения записи

Круг разбора кода дал **четыре находки, ни одна из которых ворошителю не видна**: три
из них не о том, что кодек выдаёт, а о том, чем это ему обходится, а четвёртая - о том,
что своды правил в коде задвоены и разойдутся при первой же правке одного из них.

**Разбор UTF-8 держался двумя телами.** Одно в `common.cpp` читало текст целиком, другое
в `encoding.cpp` читало по кускам, и правила у них совпадали дословно - избыточная запись,
суррогаты, предел набора, продолжающие байты. Третьей копией был разбор длины по ведущему
байту. Расходились тела лишь тем, **как докладывают исход**: первое отдавало ноль байтов
и на битой последовательности, и на оборванной, второе разделяло их длиной. Это различие
в докладе, а не в правилах, и держать ради него два свода незачем. Своды сведены в
`inspect()`, отделяющий оборванную последовательность от построенной ошибочно, а прежние
два вызова остались прослойками над ним. Четвёртой полукопией оказалось само чтение имени
без кавычек: обрыв оно определяло прикидкой «до конца накопленного текста меньше четырёх
байт», а теперь спрашивает разбор.

Сверено **перебором, а не ворошителем**: все 285 278 720 последовательностей длиной до
четырёх байт, каждая при всяком урезании буфера, поданы обоим прежним телам и новому -
отвечают одинаково, и кодом, и длиной. Перебор здесь сильнее случайной подачи: он
исчерпывает область определения целиком.

**Правка дерева обходилась квадратом, и дважды.** Всякая правка, заводящая запись,
перестраивала указатели по всему дереву: восемь тысяч правок - 3.18 секунды, цена одной
правки удваивалась с каждым удвоением их числа. Запись, встающая в конец, номеров прежних
не сдвигает, и указатели ей теперь наращиваются доборно - **общим с перестроением телом**,
ибо второй список правил разбора записи здесь был бы тем же дефектом, что и два
развёртывателя UTF-8.

Вторая квадратичность вскрылась лишь **счётом операций**: место вставки искалось обходом
всей области таблицы, и это ровно n²/2 - 128 миллионов шагов на 16 000 правок. Время её
прятало: шаг дешёвый и кэшу удобен, отношение выглядело как ×1.4, что легко списать на
память. Место вставки продолжается теперь от подсказки, оставленной прошлым заведением;
подсказка остаётся подсказкой - правило поиска одно, и обход от неё даёт тот же итог, а
всё, что сдвигает номера записей, подсказки отменяет вместе с перестроением. Итог:
**16 000 правок за 0.0121 с вместо 3.18** и 25 254 шага вместо 128 миллионов, рост линеен
по обоим замерам.

**Запись дерева в текст просила памяти на каждую запись.** Составное имя отводилось заново
всякий раз: 8016 выделений на 8000 записей. Буфер заведён единожды на весь обход -
**16 выделений вместо 8016**, и число это от размера дерева не зависит вовсе.

Из семи мест, отложенных прежним разбором, **два оказались пустыми**: подбор точности
записи числа с обратным чтением ушёл вместе с переходом на `awh::lexical`, а обхода
шестнадцати диапазонов Юникода в коде не находится вовсе. Ещё одно - полный обход перечня
имён при заголовке набора таблиц - **измерено и квадратичным не оказалось**: имена там
снимаются на каждом заголовке, и множество остаётся малым. Последнее - двойной поиск при
заведении имени - **устранимым не является**: заведение зовёт `intern()`, кладущий имя в
хранилище, и вызов его наперёд засорял бы хранилище именами, которые не понадобились.
Второй поиск здесь плата за это, и она меньше.

Сличено с кодом до правки тремя способами: перебор развёртывателей выше, ворошитель на
четырёх зёрнах против сборки из прежнего состояния (совпадение на каждой засечке, не
только в итоге) и слепок записи после 20 000 случайных последовательностей правок -
90 592 строки знак в знак. Закреплено проверкой `CodecTomlReader.UnicodeKeyChunking`:
имя со знаками Юникода при всех размерах куска подачи. Оговорка: **прежний код её тоже
проходит** - старая прикидка приводила к тому же итогу, лишь откладывая приговор. Это
закрепляющая проверка на будущее, а не пойманный дефект, и выдавать её за второе неверно.

**Прогон 16.08.2026 на пятнадцати машинах** — macOS ARM64, FreeBSD (clang 18), NetBSD
(g++ 10.5), OpenBSD (clang 19.1), DragonFly (g++ 14 из портов), Solaris 11.4 (g++ 15.2),
OpenIndiana (g++ 14.3), Alpine (musl, g++ 15.2), Debian 12 (g++ 12.2), Alt (g++ 13.2),
Ubuntu (g++ 14.2), OpenSUSE (g++ 15.3), Fedora (g++ 16.1), Windows x86-64 (MinGW 13.2) и
Windows ARM64 (clang 22.1, `libc++`, UCRT). Итоги ворошителя совпали **побайтово** по трём
зёрнам всюду: 6 386 043, 6 395 788 и 6 385 074 события, 38 053, 38 021 и 38 049 дерева,
38 039, 37 998 и 38 032 перезаписи. Набор проверок — 111 из 111 везде, кроме OpenBSD и
Alpine, где `CodecTomlWriter.LocaleNumbers` пропускается: локали с иным знаком десятичной
точки там нет вовсе, как и у INI.

Правка разбора UTF-8 задела как раз то, что от машины зависит: знаковость `char` в ведущем
байте и ширину типов при сборке кодового значения. Совпадение по знаковым `char` (x86-64,
Windows ARM64) и беззнаковым (NetBSD, OpenBSD, FreeBSD ARM64) это и проверяет.

**Ловушка стенда Windows ARM64:** путь `/clangarm64/bin` нужен и при **запуске**, не только
при сборке — собранный файл берёт `libc++.dll` оттуда, и без пути не печатает ничего вовсе,
ни строки вывода, ни жалобы на отсутствующую библиотеку. Молчание это неотличимо от
зависшего прогона, и проверять при пустом выводе следует сперва путь, а не саму программу.

### Круг чтения кода 16.08.2026: три дефекта в открытом API и задвоенный свод правил

Правка скорости, описанная выше, ворошителем проверена целиком - и всё же круг чтения
всех пяти исходников с нуля вскрыл **три дефекта, ни одного из которых ворошитель не
видел**. Два лежат в открытом API правки, куда ворошитель не заглядывал вовсе, а третий
внесён правкой того же дня.

**Первый: запись выдавала оборванный текст как готовый.** Проверка выдачи судила лишь
незакрытые скобки. Отказ, случившийся уже **после** того, как операция дописала своё
начало, оставлял строку рваной: имя таблицы, отвергнутое длиной, оставляло за собою
открывающую скобку, и `text()` отдавал это как собранный документ.

Первая правка была сделана грубо - «выдавать пусто, если был хоть какой-то отказ», - и
уронила проверку `Unfinished`, закрепляющую законный случай: отказ, ничего дописать не
успевший, текста не портит, и запись после него вправе продолжаться. Вторая правка
судила саму рваность - незавершённую последнюю строку, - и **тоже оказалась неполна**:
оборванную строку вправе завершить знаком конца строки следующая удачная операция, после
чего рваность по одному виду текста неразличима.

Нашёл это **отдельный ворошитель открытого API записи** (`tomltorn`): тесные пределы,
чтобы отказы падали часто и падали посреди операций, случайные последовательности вызовов
и утверждение с двух сторон - выданный непустой текст обязан читаться собственным разбором
целиком, а последовательность без отказов обязана выдать непустой текст. Второе стережёт
отказ **сверх меры**, каким была первая правка. Первый прогон упал на третьем проходе.

Признак рваности сделан липким, а ставится он единственным телом `refuse()`, куда сведены
все тридцать восемь мест записи кода ошибки - по образцу `failure()` у разбора. Держать
вместо этого перечень мест, где отказ приходит после дописывания, было бы тем же дефектом,
что и два развёртывателя UTF-8.

Три «отказа» того же ворошителя дефектами **не оказались**: он сам писал повторяющиеся
имена таблиц, а учёта повторов запись не ведёт - реестра имён у неё нет вовсе, это дело
дерева настроек. Граница эта прежде нигде записана не была и внесена теперь в «Намеренные
решения» заголовка вместе с правилом о невыдаче оборванного текста.

**Второй: правка принималась, а собственный разбор её отвергал.** Порядковый номер таблицы
набора снимался **двумя телами**, и проверка пригодности имени признавала номером запись с
ведущим нулём. Указатель дерева ведёт таблицы набора записью кратчайшей, «01» не совпадало
ни с одной, и пара по такому имени вставала верхним уровнем поверх набора: `set()` отвечал
успехом, а собранный текст разбор отвергал дополнением набора таблиц. Оба места снимают
номер теперь одним телом.

**Третий внесён правкой того же дня.** Состояние обхода записей, заведённое доборным
наращиванием указателей, освобождением дерева не сбрасывалось: имена прежнего дерева
отсекали заведение тех же имён заново, и дерево, собранное правками после `clear()`,
теряло дочерние имена. Дефект прошёл ворошитель, весь набор проверок и пятнадцать стендов -
поймало его лишь чтение кода.

Сверх того сведён задвоенный свод правил: пропуск пробельной обвязки и примечаний внутри
перечня стоял **двумя дословно совпадающими телами по 119 строк** - перед очередным
значением и за ним.

Три урока этого круга стоит записать отдельно. Ворошитель ходит теми путями, какие ему
проложены, и открытый API правки лежал вне их вовсе. Правка, прошедшая все проверки и все
стенды, дефекта не лишена - её надлежит читать так же, как читается чужой код. А правило,
выведенное разбором, стоит проверять ворошителем, нарочно под него построенным: обе первые
правки выглядели верными и обе были неполны.

**Повторный прогон 16.08.2026 на пятнадцати машинах** — после правок круга чтения. К
прежнему ворошителю добавлен новый, по открытому API записи: правило рваности выведено
разбором кода и проверяться обязано всюду, а не на одной лишь рабочей машине. Итоги совпали
**побайтово** на всех машинах и по обоим ворошителям: 6 386 043, 6 395 788 и 6 385 074
события у разбора; 45 930, 45 709 и 46 028 выданных текстов при 7 319, 7 363 и 7 427
последовательностях без отказов у записи. Набор проверок вырос до 114 и проходит везде,
кроме OpenBSD и Alpine с законным пропуском `CodecTomlWriter.LocaleNumbers`.

Совпадение счёта выданных текстов знак в знак значит больше, чем совпадение счёта событий:
число это складывается из отказов, а отказы приходят по пределам длины имени и строки, по
знаковости `char` в ведущем байте UTF-8 и по разбору чисел - то есть ровно по тем местам,
где машины расходятся охотнее всего.
