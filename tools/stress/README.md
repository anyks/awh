# Нагрузочные проверки протоколов

`http1.cpp` — нагрузочная проверка [парсера HTTP/1.x](../../src/proto/http/parser/http1)
на больших объёмах данных, обрывах соединения и возобновлении передачи.

Проверяются свойства, которые на коротких сообщениях не проявляются вовсе:

* **доставка тела до октета** — тело порождается позиционной функцией и такой же
  сверяется на приёме. Потеря, перестановка либо дублирование порции дают то же
  количество октетов, поэтому сверяется содержимое, а не объём;
* **ограниченность потребления памяти** — пиковое потребление процесса обязано
  задаваться порогами выходного буфера и размером порции подачи, а не объёмом
  тела. Тело нигде не хранится массивом: ни отправляющая сторона, ни принимающая,
  ни сама проверка;
* **отсутствие роста памяти от сообщения к сообщению** — сценарии с обрывами
  прогоняют сотни циклов и сверяют потребление после первого цикла с итоговым.

## Сценарии

| Сценарий | Что проверяется |
|---|---|
| `приём identity` | Тело фиксированного размера порциями по 64 КиБ |
| `приём chunked 16К` | То же тело в кодировке chunked чанками по 16 КиБ |
| `приём chunked 1М` | То же тело чанками по мебибайту: чанк заведомо больше порции подачи |
| `сборка identity push` | Сборка тела фиксированного размера методом `sendData` |
| `сборка chunked push` | Сборка тела в кодировке chunked методом `sendData` |
| `сборка identity pull` | То же тело, подаваемое pull-источником через `dataSource` |
| `сборка chunked pull` | То же в кодировке chunked |
| `обрыв приёма` | Обрыв соединения посреди тела, полная очистка, работа после неё |
| `докачка 206` | Возобновление прерванной передачи ответом `206 Partial Content` |
| `обрыв сборки` | Обрыв посреди сборки: отказ `resetSender` и восстановление очисткой |

Собранные байты нигде не накапливаются: у сценариев сборки провод разбирается
встречным приёмником на лету, и он же сверяет тело. Это тот же инвариант, что
проверяет генератор нештатного трафика, — **собранное обязано разбираться в
отправленное**, — только на объёмах, до которых генератору не дойти.

### Про обрыв соединения

Обрыв посреди тела обязан дать `PREMATURE_EOF`, а не молча выдать усечённое тело
за целое: приложение приняло бы неполный файл за полученный. Пришедшее до обрыва
обязано совпасть с отправленным до октета — обрыв не вправе испортить уже
доставленное.

Возобновление передачи парсеру не принадлежит: его выполняет приложение запросом
диапазона, а сервер отвечает `206 Partial Content`. Проверяется, что обе части,
принятые разными сообщениями на разных соединениях, складываются в исходное тело
до октета.

Недоотправленное сообщение бросить подготовкой к следующему нельзя: `resetSender`
отказывается и требует закрыть соединение — иначе следующий блок заголовков лёг бы
продолжением чужого тела, и получатель прочитал бы одно сообщение вместо двух.
Проверяется и отказ, и штатный путь восстановления через `clear`.

## Запуск

```sh
ROOT=$(pwd)
FLAGS="-O3 -DNDEBUG -std=c++17"

c++ $FLAGS -I$ROOT/include -I$ROOT/contrib/include -I$ROOT/third_party/include \
	-Wno-reserved-user-defined-literal -Wno-implicitly-unsigned-literal \
	-o /tmp/stress-http1 $ROOT/tools/stress/http1.cpp \
	$ROOT/build/libawh.a $ROOT/third_party/lib/libdependence.a \
	$ROOT/third_party/lib/libcommon.a -lz -liconv \
	-framework Foundation -framework CoreFoundation -framework Security

# объём тела в мебибайтах и количество циклов обрыва
/tmp/stress-http1 4096 32
```

Первый параметр — объём тела каждого сценария в мебибайтах (по умолчанию 1024),
второй — количество циклов обрыва (по умолчанию 32). Ненулевой код выхода
означает несовпадение содержимого, недоставленное тело либо рост памяти.

Для поиска дефектов работы с памятью тот же исходный текст собирается с
`-fsanitize=address,undefined` и запускается на меньшем объёме: под санитайзерами
прогон вчетверо медленнее, а рост потребления памяти от цикла к циклу перестаёт
быть показательным — освобождённая память удерживается карантином.

## Результаты

Apple M4 Max, `Release`, объём тела 4 ГиБ на сценарий (28 ГБ суммарно):

| Сценарий | Пропускная способность | Пик памяти |
|---|---:|---:|
| `приём identity` | 2 016 МБ/с | 7,1 МБ |
| `приём chunked 16К` | 1 996 МБ/с | 7,1 МБ |
| `приём chunked 1М` | 2 042 МБ/с | 8,1 МБ |
| `сборка identity push` | 1 975 МБ/с | 8,2 МБ |
| `сборка chunked push` | 1 942 МБ/с | 8,2 МБ |
| `сборка identity pull` | 1 512 МБ/с | 8,2 МБ |
| `сборка chunked pull` | 1 498 МБ/с | 8,2 МБ |
| `обрыв приёма` × 32 | 2 154 МБ/с | 8,2 МБ |
| `докачка 206` × 32 | 2 017 МБ/с | 8,3 МБ |
| `обрыв сборки` × 32 | — | 8,7 МБ |

Расхождений содержимого нет ни в одном сценарии. **Пиковое потребление памяти —
8,7 МБ на 28 ГБ данных**, и от объёма тела оно не зависит: те же 8,5 МБ выходят и
при 512 циклах обрыва вместо 32. Утечек не обнаружено и штатным инструментом
(`leaks --atExit`): «0 leaks for 0 total leaked bytes».

Показатели пропускной способности здесь **не характеризуют парсер**: в них входит
порождение и посимвольная сверка тела, которые стоят дороже самого разбора. Для
измерения парсера служат [бенчмарки подмодуля](../../benchmark/proto/http1),
где тело не порождается на лету.

Быстрые проверки тех же свойств на объёме 16 МиБ входят в набор модульных тестов
(`tests/proto/http/parser/http1/volume.cpp`) и выполняются за 117 мс — они ловят
регрессию в обычном прогоне, а этот инструмент нужен для объёмов, до которых
модульным тестам доходить незачем.
