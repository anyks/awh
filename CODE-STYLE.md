# Свод правил оформления C++ AWH

Документ — операционный для агентов: правка, не прошедшая сверку по этому
своду, не считается готовой, даже если компилируется и тесты зелёнкие.
Эталонные носители стиля: `include/net/io.hpp` (заголовочные файлы публичного
видa) и `src/net/backend/bsd/kqueue.cpp` (реализация). При сомнении в детали —
смотреть эталон, не догадываться; здесь зафиксированы правила, вынесенные из
этноалона 12.10.2026, но живой эталон всегда впереди.

---

## 1. Физические правила файла

1.1. Отступы — **табуляция**, никогда пробелы. Вложенность — один таб на уровень.
1.2. Пробел между `)` и `{` у управляющих конструкций запрещён: `if(x){`,
    `while((ptr = ::readdir(h)) != nullptr){`, `switch(static_cast <uint8_t> (v)){`.
    Фигурная скобка всегда на той же строке.
1.3. Внутри тела функции **пустых строк нет**; логические части отделяются
    комментариями, не пустыми строками. Пустая строка допустима между отдельными
    определениями верхнего уровня (макро-блоки, функции) — ровно одна.
1.4. Комментарий-блок и следующее определение не разделяются пустой строкой:
    за закрывающим `*/` сразу идёт объявление/определение.
1.5. Одна логическая строка — одна физическая; перенос длинной сигнатуры
    допускается только с продолжением на уровне tabs + выравниванием.
1.6. `#endif` пишется **голым**: ни комментария-хвоста на своей строке
    (`#endif // __linux__`), ни комментария над ним — закрытие условия ничьего
    пояснения не требует, условие уже подписано над `#if`, а ветви — над
    `#elif`/`#else` (§3.4). Заодно и «Конец блока условной компиляции» над
    `#endif` — лишний. После препроцессорных ветвей тела индентятся ещё одним
    табом (см. §3.3). Ловит `§1.6` в чекере: хвост на строке и комментарий над
    директивой — два отдельных ERROR.

## 2. Шапка файла

2.1. Каждый файл начинается с doc-блока: `@file`, `@date` (ГГГГ-ММ-ДД),
    `@license{LicenseRef-AWH-1.0}`, `@author`, `@telegram{...}`, `@phone{...}`,
    `@email ...`, `@site ...`, затем `@brief`, затем `@copyright Copyright © ГГГГ`,
    последняя строка — пустая ` *` перед `*/`.
    1. `@file` — точное имя файла (`@file prefilter.cpp`); написание с
       двоеточием (`@file: obsd.cpp`) и голой строкой с названием вместо тега —
       ошибка. `@date` строго ГГГГ-ММ-ДД; `@copyright` строго `Copyright © ГГГГ`.
    2. Всё содержание шапки живёт в тегах: разъяснение несёт `@brief`, а при
       нужде `@details`/`@note`/`@section` после него. Голых строк между тегами
       нет — ни названием файла перед `@license`, ни абзацем «зачем этот файл»
       вне `@brief`. Продолжение тега — только строкой с выровненным отступом
       (два и более пробела после `*`).
    3. `@brief` в `include/**` стоит в секциях `\~russian` … `\~english` (§2.2);
       в `src/**` — одна русская строка без меток, двуязычная шапка .cpp —
       нарушение §2.3.
    4. Порядок обязательных тегов фиксирован, как выше; лишние разъяснительные
       теги (`@details`, `@section`, `@note`, `@warning`, `@par`) после `@brief`
       порядку не мешают. Ловит `§2.1` в чекере.
2.2. **Заголовочные файлы публичного вида** (`include/**`) — двуязычные:
    блоки размечаются `\~russian` … `\~english` … `\~` (Doxygen многоязычность).
    Порядок всегда: русский, английский, закрывающий `\~`.
2.3. **Файлы реализации** (`src/**`, `src/internal/**`) — **только русский**,
    без меток `\~`; английский в них запрещён, кроме строк журнала (§8.4).
2.4. `@brief` файла формулируется «Реализация …» / «Заголовочный файл …» —
    описывает назначение модуля, а не перечисляет классы. Многострочный brief
    продолжается с выровненным отступом.

## 3. Препроцессор и подключение

3.1. Защита заголовка — `#pragma once`, над ней комментарий-блок:
    ```
    /**
     * Экранируем повторную инициализацию модуля
     */
    #pragma once
    ```
3.2. Каждый `#include` — с собственным комментарием над группой («Подключаем
    заголовочные файлы проекта»); системные — угловыми скобками, проектные —
    углами при подключении из `src` (`#include <net/io.hpp>`). Разные группы
    разделены пустой строкой, внутри группы — подряд, без разрывов.
3.3. Дефолты с guard'ом оформляются так (каждый — блок комментариев + ветви):
    ```
    /**
     * Если размер пакета для таймеров не определён
     */
    #if !defined(AWH_BATCH_SIZE_INTERNAL_TIMER)
            /**
             * @brief Устанавливаем размер пакета для таймеров в 256
             *
             */
            #define AWH_BATCH_SIZE_INTERNAL_TIMER 0x100
    #endif
    ```
    Значения макросов — **шестнадцатеричные** (`0x100`, `0x7A120`), с
    десятичным пояснением в `@brief`. Обоснование величины — в `@note`
    того же блока, включая сравнение с конкурентами, если выбор неочевиден.
3.4. Платформенные ветви `#if defined(__linux__) ...` обязательны там, где
    фича существует не на всех системах; над ветвью — комментарий условия,
    внутри каждой ветви — собственный комментарий-блок. Тот же порядок для
    `#if`/`#ifdef`/`#ifndef`/`#elif`/`#else` любого назначения: над ними стоит
    doc-блоковая секция `/** */`, одиночный `//` над директивой не допускается,
    пустая строка перед директивой требования не снимает. Над `#endif`
    комментарий не ставится. Ловит `§3.4` в чекере.
3.5. `#if defined(DEBUG_MODE) / #else / #endif` — штатный способ различать
    отладочный и продуктовый путь в логах (§8.4).

## 4. Именование

4.1. **Классы**: `Имя_С_Подчёркиваниями` с заглавных (`Origin_Identifier`,
    `Stream_Control_Transmission_Protocol`); короткие общеизвестные аббревиатуры
    — целиком капиталью (`IO`). Публичный класс всегда в паре с typedef-алиасом:
    `typedef class __AWH_SHARED_EXPORT__ Stream_Control_Transmission_Protocol { ... } sctp_t;`
    — наружу тип выходит **алиасом** `*_t` (snake_case + `_t`).
4.2. **Методы** — camelCase: `messageInfo`, `initMessages`, `setTargetPort`,
    `eventsSubscribe`. **snake_case в названиях методов, функций и переменных
    запрещён** — это правило, а не рекомендация. Приставок `get`/`set` для
    «только чтения» **нет**: геттер — существительное (`status(id)`,
    `size(id)`), сеттер — глагол (`eventsSubscribe(id, list)`) либо
    **перегрузка того же имени** с дополнительным аргументом
    (`messageInfo(id)` ↔ `messageInfo(id, info)`).
4.3. **Локальные переменные, параметры, объявляемые переменные функций** —
    camelCase (`initmsg`, `peer`, `bytesRead`). snake_case запрещён (§4.2).
4.4. **Члены класса** — snake_case с **нижним подчёркиванием на конце**
    (`_eth`, `_slot`, `_chunk`, `_owner`, `_state`) и обращение к ним из методов
    **только через `this->`** (§6.1). Публичные поля POD-структур (ключи,
    союзы) — без префиксов/суффиксов, простым именем (`family`, `keyed`, `key`).
4.5. **Файловая статика** — двойные подчёркивания с обеих сторон: данные
    `__awh_nodes__`, `__awh_cmsgbuf__`; константы `__AWH_IO_BACKEND__`.
    Обращение к ним из тела функций — с `::` префиксом (`::__awh_nodes__.find(id)`).
4.6. **Константы и флаги** — ВЕРХНИМ РЕГИСТРОМ: `static constexpr uint8_t READ = 0x01;`
    внутри смысловых namespace'ов (`namespace activity { ... }`,
    `namespace action { ... }`); значения — hex.
4.7. **Значения enum/enum class** — ВЕРХНИМ РЕГИСТРОМ (`NONE`, `PENDING`,
    `HEARTBEAT`).
4.8. **Namespaces** — строчные, по существительному (`engine`, `io`, `timer`,
    `event`, `net`); уровень вложенности отражает путь модуля, не тип сущности.
4.9. **Макросы** — `AWH_` префикс, ВЕРХНИЙ регистр, сущность+свойство
    (`AWH_MAX_POLL_EVENTS_LIMIT`).
4.10. **Исключение для внутренней статики реализаций** (редкое, только когда
    действительно требуется): статические функции и переменные, живущие для
    внутреннего использования `.cpp` внутри анонимного или именованного
    namespace, именуются **всегда** с двойным обрамлением `__awh_{name}__`
    (`__awh_nodes__`, `__awh_cmsgbuf__`, `__awh_zero_mac__`, `__AWH_IO_BACKEND__`
    для констант верхним регистром). Обращение к ним — через `::`.
    Для всего остального (методы, функции, переменные) это исключение —
    не лазейка: snake_case запрещён (§4.2), внутренние имена без крайней
    необходимости заводятся camelCase внутри того же анонимного namespace.
4.11. **Исключение для C-поверхности** (единственная лазейка в §4.2–§4.3):
    объявления, лежащие внутри `extern "C" { ... }`, именуются по соглашению C —
    `префикс_сущность_действие` (`danube_ro_open`, `danube_ro_keys_export`),
    потому что границу модуля разбирает компилятор C, для которого camelCase —
    чужая привычка, а не правило. Макросы той же поверхности — ВЕРХНИМ РЕГИСТРОМ
    с тем же префиксом (§4.6, §4.9). Чекер снимает §4.2 и §4.3 на строках между
    `extern "C" {` и его закрывающей `}`; за пределами области правило действует
    полностью, и уносить C++-код внутрь `extern "C"` ради другого имени нельзя.
    Определения C-функций пишут в `.cpp` в той же области `extern "C" { ... }` —
    иначе линковка и имена разъедутся с заголовком; тела C++-помощников, классы
    и `namespace` держат **вне** области, и имя у них остаётся camelCase. Имена
    констант-флагов той же поверхности не должны сталкиваться с разрядами
    `enum`: столкнувшиеся разводят префиксом (`DANUBE_RO_INFO_VAULT` против
    кода результата `DANUBE_RO_VAULT`), потому что макрос перекрывает
    разряд перечисления молча.

## 5. Устройство классов в заголовке

5.1. Порядок внутри класса:
    1. `private:` — приватные данные (каждому полю комментарий; простой
       — `//` в одну строку, содержательный — `/** */`);
    2. далее **несколько блоков `public:`**, каждый — одна смысловая группа
       (геттер+сеттер пары, затем следующая группа). Группы разделяются
       собственным `public:`, не пустыми строками;
    3. **конструктор и деструктор — в конце блока, после всех методов**:
       деструктора нет — конструктор последний; деструктор есть — предпоследним
       идёт конструктор, деструктор замыкает блок; конструкторов несколько — они
       идут подряд друг за другом, без вставок между ними, и только затем
       деструктор. Пары запрещённых копирования/перемещения (`= delete`) и
       операторы присваивания своего типа держатся той же группы в конце, но
       методами не считаются; обычные операторы (`operator ==`, `operator
       size_t`) — методы, и стоят до группы конструкторов. Ловит `§5.1` в
       чекере: он разбирает тело `class`/`struct`/`union` (с `typedef` и без) на
       объявления и сверяет этот порядок.
5.2. Каждое объявление метода над собой имеет doc-блок (§7); комментариев
    «справа» не бывает — комментарий либо doc-блок, либо одиночный `//` для
    поля-однушки.
5.3. Объявления методов: параметры с qualifiers целиком (`const event::id_t id`,
    `const net::sctp::minfo_t & info`); указатель/ссылка — **пробел с обеих
    сторон**: `uint8_t * ptr`, `const string & path`; `noexcept` обязателен на
    всех методах, не бросающих исключений; геттеры — `const noexcept`.
5.4. Внутренние типы объявляются typedef'ами внутри того же namespace, что и
    владелец; экспорт публичных классов — через `__AWH_SHARED_EXPORT__`.
5.5. **Реализация живёт в .cpp.** В публичном заголовке стоит объявление
    (`void finalize() noexcept;`), тело — в файле реализации. Тело определения в
    заголовке допустимо только там, где оно обязано жить в заголовке: шаблон
    (`template <...>` над определением или над классом-владельцем; заголовок
    шаблона может занимать несколько строк и быть отделён doc-блоком, чекер его
    находит; члены шаблонного класса под правило не попадают — входные типы
    заранее неизвестны, и перенос тела в .cpp делает шаблон недоступным
    собирателю) либо определение, уже помеченное `inline`/`constexpr`/модульным
    `AWH_<МОДУЛЬ>_INLINE`. **Исправление сайта — перенос тела в .cpp, а не
    простановка `inline`**: пометку ставят лишь тогда, когда тело сознательно
    оставляют в заголовке и берут всегда-встраивание (`AWH_*_INLINE` меняет
    решение собирателя, поэтому правка требует сборки и замера). Пометка `inline`
    над членом класса ничего семантически не меняет — член, определённый в теле
    класса, неявно inline и без неё, — значит одна она дефекта не лечит.
    Исключений для «мелких» геттеров, операторов разыменования и конструкторов
    нет. Распознавание не путает с определением и не флажит: скобку лямбды внутри
    `static_assert` или постоянного инициализатора (`[](){ … }()` — это проверка
    времени сборки, переносить её некуда) и члены класса, объявленного внутри
    шаблонной функции (такой класс в .cpp не выразить вовсе). Ловит `§5.5` в
    чекере (только `include/`; внутренние заголовки `src/` не смотрит).
    **Помощник, нужный нескольким единицам трансляции и обязанный встраиваться
    в каждой из них, живёт во внутреннем заголовке модуля** —
    `src/<модуль>/internal/<имя>.inc`, — а не в публичном заголовке: файл
    подключают собою все `.cpp`, зовущие помощника, тело в нём одно (копий
    по числу зовущих файлов нет), в поставку он не входит (ставится только
    `include/**/*.hpp`), и заголовки остаются чистыми. Расширение `.inc`
    отличает фрагмент-для-подключения от интерфейсного заголовка; чекер
    обходит `.inc` наравне с прочими исходными текстами, а §5.5 к нему
    не применяется — тело там и живёт. Первый такой файл —
    `src/regex/internal/helpers.inc` (`hasFlag`, `letter`, `findByte`,
    `identical`, `verbatim`), подключённый реализациями модуля regex.
5.5.1. Модули без файла реализации — исключение по оснастке, а не по стилю, и
    оно **объявлено списком**: `sys/callback.hpp`, `sys/threadpool.hpp`,
    `num/lexical/**`, `net/callback.hpp`, `net/engine.hpp`, `alloc/capture.hpp`,
    `codec/value.hpp` (в чекере — `HEADER_ONLY`). Реализационного .cpp у них нет
    вовсе — весь код живёт в заголовке, и переносить тело некуда. Отсутствие
    парного .cpp само по себе освобождением не служит: у `regex/grok/common.hpp`
    парного файла тоже нет, а перенести тело есть куда — в `src/regex/grok/`,
    и правило на него действует. Чекер молчит только когда заголовок стоит в
    списке И под `src/**` нет .cpp с тем же путём-именем, и ни одна .cpp его
    напрямую не подключает; промолчавшие перечисляет в итоговой строке — их надо
    видеть, а не хоронить. Как только у модуля из списка появляется .cpp (или
    заголовок начинает подключаться из .cpp), правило на него включается само.
    Новый модуль в список вписывается только по слову владельца. Порядок внутри
    таких заголовков — §5.1, оформление комментариев и секций — §3–§7, они не
    ослабляются.

## 6. Обращения и выражения в реализации

6.1. Свой член — **только `this->`**; никогда голое имя, даже когда не
    конфликтует. Мера «член» берётся из индекса объявлений вида `_name`, и из неё
    вычтены имена внутренней статики §4.10 (`__awh_{name}__`): это не члены, к ним
    обращаются через `::` (§6.2), и требовать `this->` у них — ошибка оснастки.
6.2. Файловая/анонимная статика и глобальные функции Си — **только `::`**:
    `::strcmp(...)`, `::stat(...)`, `::__awh_nodes__`. Голые `strcmp` запрещены.
    Правило смотрит на **вызовы**: объявление или определение метода, совпадающего
    именем с функцией Си (`virtual void write(const event::id_t …)`,
    `AWH_GNU_INLINE ssize_t read(…)`, `__AWH_SHARED_EXPORT__ size_t write(…)`),
    вызовом не считается и не флажится — чекер отличает такой заголовок по
    префиксу из модификаторов и типа без операторов и без управляющего слова.
    Голый вызов остаётся ошибкой в любой форме: `free(p);`, `return read(fd, …)`,
    `if(munmap(…) != 0)`.
6.3. Приведения — **не Си-каст, не компактный static_cast**:
    `static_cast <uint8_t> (timer)` — пробелы до `<`, после `>`, перед `(`.
    Проектный динамический каст — `awh_cast <::io::dir_t *> (expr)` в том же
    формате.
6.4. Switch по enum — канонический вид:
    ```
    switch(static_cast <uint8_t> (i->second->state.node)){
            // Если узел является директорией
            case static_cast <uint8_t> (event::node_t::DIR): {
                    ...
            } break;
            // Если узел не является файловым
            default: {
                    ...
            }
    }
    ```
    кейсы со Scope — `{ ... } break;` на той же строке; одиночные действия
    допустимы без скобок, `break` на уровне switch.
6.5. Условие в одну операцию — без скобок, операция на следующей строке с
    собственным комментарием-пояснением:
    ```
    if(dir->path == nullptr)
            // Прерываем выполнение
            break;
    ```
    Больше одной операции — фигурные скобки. `else if(...)` с множественными
    действиями — `else if(...)` + пробел + `{`; одиночное — через комментарий.
6.6. Циклы — всегда с комментарием-блоком `/** Выполняем … */` над заголовком
    и комментарием `//` над телом каждого пропуска/условия (`continue` с
    пояснением обязателен: `// Пропускаем названия "." и "..", так как идет рекурсия`).
6.7. Операторная оболочка вызова — `const auto i = ::map.find(id);` с
    последующей проверкой на `end()` в том же выражении, где используются
    составные условия с кругами попарной группировки:
    `if((i != ::__awh_nodes__.end()) && (i->second->state.status == event::status_t::PENDING)){`.

## 7. Документирующие комментарии методов

7.1. Структура doc-блока объявления (hpp, двуязычный):
    ```
    /**
     * \~russian
     * @brief Метод получения ...
     *
     * @param id   идентификатор события
     * @param info метаданные сообщения
     * @return     значение
     *
     * \~english
     * @brief Method of getting ...
     * @param id   identifier of the event
     * @param info ...
     * @return     ...
     *
     * \~
     */
    ```
    Реализация (cpp) — тот же блок без `\~`-меток, только русский.
    После открывающей метки секции (`\~russian`, `\~english`) пустая ` *` строка
    НЕ ставится — первым сразу идёт тег, как в образце выше. Пустая строка
    обязательна только перед закрывающей меткой `\~` (§7.5) и между группами
    тегов (§7.3.1). После самой закрывающей `\~` пустая строка НЕ ставится: за
    ней сразу идёт `*/` — закрытие секций ведётся встык к концу блока. Ловит
    `§7.1` в чекере в обе стороны (лишняя после открывающей и лишняя после
    закрывающей); `--fix` такую строку удаляет.
7.2. `@brief` всегда «Метод получения/установки/проверки …» — существительное,
    не глагол-призыв. После @brief — пустая ` *` строка, затем @param'ы.
7.3. Имена @param выравниваются по колонке (пробелы до единой позиции), как и
    описания; `@return` — в колонку @param'ов.
    1. Колонка описаний в группе считается так: самое длинное имя (или слово
       `@return`) задаёт границу, описание начинается на шаг за ним — остальные
       имена дополняются пробелами до той же колонки. Русская и английская
       секции выравниваются **независимо**: свалить английские @param в кучу,
       оставив выровненными русские, — нарушение.
    2. Перенос длинного описания параметра продолжается с той же колонки, где
       оно началось.
    3. Область проверки — `include/**`: блоки реализаций (`src/**`) колонку
       не выдерживают (`@param  узел в котором…`), и чекер их по §7.3 не трогает.
       Ловит `§7.3` в чекере: отбивку групп и колонку описаний.
7.3.1. Группы тегов разделяются пустой ` *` строкой: @details/@note/@warning
      после группы @param/@return и между собой — только с отбивкой. Внутри
      блока @param/@return (а также @tparam/@retval) пустая строка **запрещена**:
      @param, следующий @param, @tparam, @retval или @arg, и @return идут
      плотными строками, и перенос перед `@return` — то же нарушение, что перенос
      между @param. Исключение — `@par`
      со своим списком: он заголовок смыслового куска и от своих @param отделяется
      пустой строкой намеренно (24 таких места в эталонном `io.hpp`). Повтор
      одного тега (цепочка @note, абзацы @details) — отбивка по смыслу, чекер её
      не требует и не запрещает. Первая строка секции без тега (зачин после
      `\~russian`/`\~english`) — тоже группа: идущий за ней тег отделяется от неё
      пустой ` *` строкой. Ловит `§7.3` в чекере в обе стороны: недостающую
      отбивку и лишнюю внутри блока параметров, и лишнюю `--fix` удаляет.
      Проверяется отдельно для русской и английской секций. Плотность блока
      `@param`/`@return` едина для всех doc-блоков: в блоке без меток языка
      (реализация, внутренний заголовок) разрыв между `@param` и `@return` тоже
      ошибка. Недостающую отбивку в блоке без меток не требуют: шапка файла
      держит парные теги (`@telegram`/`@phone`, `@email`/`@site`) намеренно (§2.1).
7.4. Обоснования нетривиальных решений — `@note` (и `@details` для классов);
    формат: проблема → следствия → выбранный компромисс, со ссылкой на цифры,
    если они измерены.
7.5. Отбивка перед `*/` стоит только там, где блоку есть от чего отбиваться.
     Блок с тегами `@` (`@brief`, `@param`, `@note`, `@details`, …) — и в заголовке,
     и в реализации — обязан кончаться пустой ` *` линией, затем `*/`. Блок без
     тегов, где ведётся одно пояснение (шапка подключения файла, ветвь `#if`,
     разделение абзацев), кончается встык: `* текст`, затем `*/`, — пустая ` *`
     перед закрытием в нём лишняя и только имитирует структуру doc-блока. Блок,
     закрытый строкой `* \~` (конец языковых секций), отдельной ` *` не требует:
     `* \~` стоит на месте отбивки, и за ним сразу идёт `*/`. Ловит `§7.5` в
     чекере в обе стороны, `--fix` вставляет недостающую линию и снимает лишнюю.

7.6. **Парность секций**: английская секция обязана точно соответствовать
     русской оформлением — тот же набор тегов в том же порядке (переводится
     всё, включая @details/@note/@warning; отсутствие английского @note при
     наличии русского — ошибка перевода), та же расстановка пустых ` *`
     разделителей между группами, те же переносы: где русская группа разбита
     строками-продолжениями, английская обязана быть разбита так же — запрет
     «смять абзац в одну длинную строку». Механическая проверка — `§7.6`
     в `tools/code-style-check.py`; пустые строки ставит `--fix`, перевод
     отсутствующих тегов и переносы — только руками/агентом.
7.6.1. Парность по смыслу: английская группа обязана переводом русской, а не
      собственным текстом — та же полнота, те же абзацы, те же таблицы и цифры.
      Английский @details в три короче русского, русская @note с историей
      вопроса, а английская с одной отпиской — это дефект перевода, а не стиль
      изложения. Механически ровно это и ловится: `§7.6` сверяет объём каждой
      группы (число знаков без пробелов) и число строк таблицы между секциями,
      при двукратном расхождении даёт WARN — направление расхождения не важно,
      неполным бывает любой из двух переводов. Текст поправляется чтением обеих
      секций и переводом, не механической правкой.
7.6.2. Наличие секций (§2.2): блок в `include/**` обязан нести и `\~russian`,
      и `\~english`. Одной русской прозы или блока без меток вовсе — перевод
      отсутствует, а не «забыли разметку». Ловит `§7.6` в чекере: блок без меток,
      блок с одной секцией, блок с английской без русской и секция, в которой нет
      ни одного тега, пока в другой они есть — перевод остался голой строкой, а
      `@details`/`@note` в него не перешли; направление дефекта значения не
      имеет, пустой бывает любая из двух. Итог — четыре отдельных ERROR. Файлы
      `src/**` правило не касается (§2.3).
7.6.3. Завершение секций: блок, где есть `\~russian` или `\~english`, обязан
      закрыться строкой `* \~` до `*/` — в Doxygen `\~` без аргумента и есть
      `\endif`, а без него условная секция перевода не закрыта. Порядок строк
      конца: последняя строка перевода, пустая ` *`, `* \~`, `*/`. Ловит
      `§7.6.3` в чекере, `--fix` вставляет `* \~` (и пустую ` *` перед ней, если
      её нет). Отсутствие завершения — дефект разметки, а не перевода: строки
      перевода на месте, закрытия нет.

## 8. Каркас тела функции (cpp)

8.1. Определение: `size_t awh::engine::IO::size(const event::id_t id) const noexcept {`.
8.2. Первая строка тела — объявление результата и комментарий к нему:
    ```
            // Результат работы функции
            size_t result = 0;
    ```
    (если результата нет — этот блок отсутствует).
8.3. Тело обёрнуто в перехват ошибок с каноническими комментариями:
    ```
            /**
             * Выполняем перехват ошибок
             */
            try {
                    ...
            /**
             * Если возникает ошибка
             */
            } catch(const exception & error) {
                    ...
            }
            // Выводим результат
            return result;
    ```
    «Выполняем перехват ошибок» и «Если возникает ошибка» — дословно,
    комментарием-блоком, не `//`.
8.4. Журнал: в ветке DEBUG_MODE — `log::debug("...", __PRETTY_FUNCTION__, {id}, flag, ...)`;
    в продуктовой — `log::print("...", flag, ...)`. Строки журнала — **английский**.
    Флаги `log::flag_t::WARNING/CRITICAL`. Каждая ветвь guard'ом §3.5.
8.5. Каждый значимый оператор снабжается однострочным комментарием `//`
    над ним, глаголом настоящего времени: «Выполняем поиск …», «Если …
    найдены», «Снимаем состояние …», «Получаем …», «Ставим …». Комментарии
    описывают действие и намерение, а не синтаксис.
    1. Первый оператор внутри блока `{` наследования комментария от заголовка
       не получает: у `for (...) {`, `if (...) {` и заголовка цикла комментарий
       стоит над самим заголовком, а тело начинается с собственного комментария
       над первым оператором. Наследует заголовок только бесфигурное тело
       (`if (x)` и одна строка без `{`).
    2. Одиночный `//` над заголовком цикла или `switch` не заменяет doc-блок
       (§6.6); над `#define` и над условной директивой — тоже (§3.3, §3.4).
    3. Продолжение того же оператора комментарием не снабжается: перенос
       аргументов и открывающаяся скобка; строка, начинающаяся с оператора
       (`<<`, `>>`, `&&`, `||`, `->`, `.`) — хвост предыдущего высказывания, вроде
       `ASSERT_TRUE(...)` и идущей под ним строки `<< "Шаблон: "`; строки списка
       инициализаторов между `= {` и `};` — данные, а не операторы. Ловит `§8.5`
       в чекере; `--no-steps` выключает проверку на разборе чужого кода.
8.6. Финал тела — комментарий вывода результата перед `return`.

## 9. Статические функции и внутренняя обвязка

9.1. Всё внутреннее (.cpp-ное, не вывозимое наружу) живёт в **безымянном namespace**:
    ```
    namespace {
            /**
             * Используем пространство имён AWH
             */
            using namespace awh;
            ...классы, typedef'ы, хелперы...
    }
    ```
    `using namespace std;` — на уровне основного namespace заголовка/реализации,
    не внутри функций.
9.2. Хелпер-функции модуля — `static` + snake_case имя + doc-блок; вызовы —
    через `::` либо прямо (статика того же TU).
9.3. Вспомогательные классы (узлы, таблицы, слоты) — typedef-пара как §4.1,
    внутри анонимного namespace, с полями-комментариями; союзы и структуры
    адресов — с doc-блоком на каждый вариант.
9.4. Скрипты шаблонов-утилит (`trust_cast`, касты) — шаблонные функции внутри
    того же анонимного namespace.
9.5. Объявление namespace (`namespace {`, `namespace имя {`) над собой имеет
    doc-блок `/** */` с `@brief`, что это за пространство и зачем; одиночный
    `//` не допускается. Ловит `§9.5` в чекере. В `src/net/backend/bsd/kqueue.cpp`
    один `namespace fs` стоит без блока — наследие, свежим правкам не образец.
    Директива `using namespace X;` вне тела функции — той же мерки: над ней
    doc-блок с пояснением («Используем пространство имён AWH»), а не `//`;
    чекер ловит тем же `§9.5`. Внутри тела директива — обычный оператор,
    над ней строчный `//` по §8.5, и чекер её не трогает.

## 10. Запреты (ловятся на ревью diff)

* пробел в `if (x) {` / `for (i...)` / `while (x) {` — **запрещён**;
* пустые строки внутри тел функций;
* `m_`/`k_`/`s_` префиксы, PascalCase методы, snake_case методы и переменные —
  чужие стили (§4.2; внутренняя статика реализаций — только `__awh_{name}__`, §4.10);
* голое обращение к члену без `this->`, голое `strcmp/::`-отсутствие у системных;
* Си-касты `(uint8_t)x` и `static_cast<uint8_t>(x)` без пробелов;
* английский в комментариях `src/**` и `src/internal/**`;
* конструктор в начале класса до методов;
* десятки `public:` без смысловых групп (или одна `public:` на всё);
* макросы с десятичными «сырыми» значениями без обоснования;
* `@brief` глагольного вида («Возвращает …» вместо «Метод возврата …»);
* «висячие» `else` без комментария ветви в многословных конструкциях;
* автоформатирование чужих черновиков без отдельного задания.
