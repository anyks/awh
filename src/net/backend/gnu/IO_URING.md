# Движок io_uring

Устройство и порядок работ по `src/net/backend/gnu/io_uring.cpp`.
Выбор при сборке: `-DAWH_ENGINE=io_uring` (по умолчанию `epoll`).

Начато **07.08.2026**. Эталон для сличения поведения — `gnu/epoll.cpp`.

---

## Чем это не является

Это **не** режим совместимости поверх epoll и не обёртка, подающая
`IORING_OP_POLL_ADD` вместо `epoll_ctl`. Такой движок дал бы те же обращения
к ядру плюс накладные расходы колец и был бы медленнее epoll.

Смысл в другом: io_uring умеет **сам выполнять работу**, а не только сообщать
о готовности. У него свои `accept`, `connect`, `recv`, `send`, `close`,
`shutdown` и настоящий `splice`. Движок обязан пользоваться ими, а
`POLL_ADD` держать лишь для того, чему родной операции нет.

Отсюда главное отличие от epoll и kqueue: **модель завершения вместо модели
готовности**. Там ядро говорило «читать можно» и работу выполняло приложение.
Здесь приложение говорит «прочти» и получает готовый результат. Разница
проходит насквозь через весь путь данных, поэтому движок пишется отдельным
файлом, а не ветвлением внутри `epoll.cpp`.

## Что установлено замером, а не по таблицам версий

Проверено на стендах Fedora 44 (ядро 6.19) и Ubuntu 24.10 (ядро 6.11)
пробой `io_uring_register(IORING_REGISTER_PROBE)`.

**`liburing` не установлен ни на одном из четырёх стендов**, а
`linux/io_uring.h` есть везде. Внешнюю зависимость не заводим: кольца
отображаются и обходятся своими силами, обращения к ядру — три
(`io_uring_setup`, `io_uring_enter`, `io_uring_register`) через `syscall()`.
Это и отвечает укладу проекта, и снимает вопрос установки на стенды.

**Заголовок дистрибутива отстаёт от ядра.** На Ubuntu `linux/io_uring.h` не
знает `IORING_OP_SEND_ZC`, `FIXED_FD_INSTALL`, `BIND`, `LISTEN`, а ядро их
поддерживает — проба отвечает «есть». Отсюда правило: **коды операций и флаги
объявляются в движке своими числами**, заголовок дистрибутива берётся только
за устройством структур. Иначе сборка на одном дистрибутиве молча теряет
возможности, которые ядро даёт.

**Наличие операции проверяется пробой при запуске, а не версией ядра.**
`RECV_ZC` есть на 6.19 и отсутствует на 6.11 — а обе версии выше той, где он
появился по документации. Проба обязательна, отход по каждой операции свой.

Наличие на обоих стендах:

| Операция | Fedora 6.19 | Ubuntu 6.11 |
|---|---|---|
| `ACCEPT`, `CONNECT` | есть | есть |
| `RECV`, `SEND`, `RECVMSG`, `SENDMSG` | есть | есть |
| `SPLICE`, `TEE` | есть | есть |
| `CLOSE`, `SHUTDOWN` | есть | есть |
| `TIMEOUT`, `LINK_TIMEOUT`, `POLL_ADD` | есть | есть |
| `MSG_RING` | есть | есть |
| `SEND_ZC`, `SENDMSG_ZC` | есть | есть |
| кольцевые буферы приёма (`PBUF_RING`) | есть | есть |
| `RECV_ZC` | есть | **нет** |

Возможности устройства колец на обоих: `SINGLE_MMAP`, `NODROP`,
`SUBMIT_STABLE`, `FAST_POLL`, `EXT_ARG`, `CQE_SKIP`, `REG_REG_RING`,
`RECVSEND_BUNDLE`; флаги `SINGLE_ISSUER`, `DEFER_TASKRUN`, `COOP_TASKRUN`
принимаются.

## Устройство

### Кольца

Одно кольцо на цикл событий. Отображение одним `mmap` (`SINGLE_MMAP` есть на
обоих стендах, отход на два отображения оставлен).

**Признаки устройства не задаются вовсе.** `SINGLE_ISSUER` привязывает кольца к
заведшему их потоку и обращения из прочих потоков отвергает, а уклад AWH прямо
допускает ведение движка из разных потоков — на этом устроен фасад QUIC,
поднимающий сервер своим потоком. `DEFER_TASKRUN` без `SINGLE_ISSUER` не берётся,
оттого отпадают оба. Замер: с этими признаками весь набор проверок фасада QUIC
отказывал по превышению времени — **15 000 мс вместо 15 мс**, — и отказывал
молча, не оставляя в журнале ни одной ошибки ядра.

`SQPOLL` **не берём** по другому доводу: он выигрывает лишь при постоянной
нагрузке и жжёт ядро процессора вхолостую, а движок общего назначения обязан
вести себя прилично и в простое.

### Чем сменяется что

| Было у epoll | Стало у io_uring |
|---|---|
| `epoll_ctl` на подписку | нет вовсе: подаётся операция, а не подписка |
| `epoll_wait` со сроком | `io_uring_enter(GETEVENTS)` с `EXT_ARG`-сроком |
| `accept4` вручную | `IORING_OP_ACCEPT`, многократный (multishot) |
| `connect` + подписка на запись | `IORING_OP_CONNECT` — исход приходит завершением |
| `recv` по готовности | `IORING_OP_RECV`, многократный, с кольцом буферов |
| `send` по готовности | `IORING_OP_SEND`, при больших объёмах `SEND_ZC` |
| `close` | `IORING_OP_CLOSE` |
| `eventfd` для пробуждения | `IORING_OP_MSG_RING` из чужого потока |
| срок из кучи дедлайнов | `IORING_OP_TIMEOUT`, срок ведёт ядро |
| `inotify` через дескриптор | `POLL_ADD` на дескриптор `inotify` |

Отдельно: **`::kernel::flush` и весь отложенный учёт подписок не нужен**.
Он затевался ради того, чтобы свести правки подписки в одно обращение к ядру.
Здесь подписок нет, а подача и так пакетная по устройству: сколько операций
положено в кольцо подачи, столько уйдёт одним `io_uring_enter`.

### Что остаётся от epoll

`POLL_ADD` держится для того, чему родной операции нет:

- дескриптор `inotify` (наблюдение за файлами и каталогами);
- туннельное устройство TUN/TAP;
- отделённые (peeloff) сокеты SCTP и приём уведомлений SCTP;
- узлы, у которых приложение попросило только уведомления о готовности.

Это не отступление, а верное употребление: `POLL_ADD` и есть родная операция
io_uring для «сообщи о готовности».

## Splice: главное приобретение

У epoll и kqueue `splice` движка — синтаксический сахар: данные читаются в
пользовательскую память и оттуда пишутся в приёмник (`IO::relay`). Иначе
нельзя — ограничитель скорости, шифрующая инъекция и учёт трафика требуют
доступа к байтам.

io_uring даёт **настоящий** `IORING_OP_SPLICE`, при котором байты не выходят
из ядра вовсе. Для прокси-сервера это разница между двумя копированиями на
пакет и нулём.

Отсюда **два пути, выбираемых по обстановке**:

| Обстановка | Путь |
|---|---|
| ограничитель скорости **не** задан, инъекции нет, оба конца допустимого вида | **ядерный**: `SPLICE` источник → канал → приёмник, байты в пользовательскую память не поднимаются |
| ограничитель скорости задан **либо** есть функция инъекции (QUIC и прочие шифрующие транспорты) **либо** приложение подписано на данные | **пользовательский**: как у epoll, через `IO::relay` |

Выбор делается при **каждой** готовности заново, а не запоминается: ограничитель
вправе появиться на живом соединении, и переход на пользовательский путь обязан
произойти без разрыва. Проверка стоит нескольких сравнений и к ядру не обращается.

### Что установлено замером о границах сообщений

Канал — поток октетов, границ сообщений сам по себе он не хранит. Но запрет на
дейтаграммы оказался чрезмерным: замер на стенде Fedora показал точнее.

- Из сокета с сообщениями ядро переносит в канал **ровно одно** сообщение за
  вызов — `splice` с пределом 65536 забрал 4 октета при трёх ждущих
  дейтаграммах в 4, 12 и 20 октет.
- Граница сохраняется, если выдать это сообщение из канала отдельным вызовом:
  приёмник получил ровно одно сообщение в 4 октета.
- **Но два сообщения, скопленные в канале, склеиваются**: дейтаграммы 4 и 12
  октет вышли одним сообщением в 16.
- `SEQPACKET` ведёт себя так же, как дейтаграммы (проверено на `AF_UNIX`).
- Перенос сообщения в потоковый приёмник безопасен всегда: границ там нет.

Отсюда устройство: сохранность границ обеспечивается **не запретом, а порядком
«одно вошло — одно вышло»**. Состояние объединения ведёт остаток, лежащий в
канале, и пока он не отдан приёмнику, новое сообщение из источника не забирается.
Порядок этот соблюдается для всех видов разом: потоку он не нужен, но и не
вредит, а одна ветвь надёжнее двух.

Если выдача остатка не удалась (буфер отправки приёмника переполнен), бросить его
нельзя: данные уже извлечены из источника, и пользовательский путь до них не
дотянется — они пропали бы вовсе. Взводится ожидание готовности приёмника к
записи, по которому выдача повторяется.

### Допустимые сочетания

| Источник | Приёмник | Допустимо |
|---|---|---|
| STREAM | STREAM | да |
| DATAGRAM | STREAM | да |
| SEQPACKET | STREAM | да |
| DATAGRAM | DATAGRAM | да |
| SEQPACKET | DATAGRAM | да |
| DATAGRAM | SEQPACKET | да |
| SEQPACKET | SEQPACKET | да |
| FILE | STREAM | да |
| STREAM | FILE | да |
| STREAM | DATAGRAM либо SEQPACKET | **нет** |
| FILE | DATAGRAM либо SEQPACKET | **нет** |
| FILE | FILE | **нет** |

Правило простое: **границы можно терять, но нельзя выдумывать**. Сообщение в
поток переносится свободно — границы там лишь теряются. Поток же в сокет с
сообщениями делить пришлось бы наугад, и приёмник получил бы куски произвольной
длины вместо осмысленных записей.

Размеры сообщений сходятся оттого, что объединяются сокеты **своих** узлов, а
предел размера пакета у них общий: сообщение, прошедшее источник, пройдёт и
приёмник.

### Чего сочетания с дейтаграммами пока не достигают

Правила выше описаны и запрограммированы, но **сочетания с дейтаграммным
источником в движке сейчас недостижимы**, и виной тому не они сами.

Врезка ядерного объединения стоит в разборе готовности к чтению. У потоковых
узлов читает сам принятый узел, и врезка его застаёт. У дейтаграммных читает
**серверный** узел, а он источником объединения быть не вправе по устройству
движка (`SpliceServerSourceRejectedTest` это закрепляет) — принятый же узел
готовности к чтению не получает вовсе.

Проверено следом: на дейтаграммной паре развилка срабатывает дважды и оба раза
видит узел вида «сервер», отчего отвечает отказом и данные идут прежним путём.

Чтобы сочетания эти заработали, врезку нужно ставить не только в разбор
готовности, но и туда, где серверный узел раздаёт принятое своим узлам. Работа
эта отдельная и здесь не сделана.

Чего ядерный путь **не даёт** и о чём приложение обязано знать:

- байтов не видно, поэтому учёт трафика ведётся по числам из завершений, а
  подписка на чтение данных на таком объединении не работает;
- ограничитель скорости неприменим — это и есть условие выбора пути;
- шифрующий транспорт неприменим по той же причине.

Всё это описывается в заголовке, а не оставляется на догадку.

## Три дефекта перехода, найденные прогоном

Все три вскрыты не чтением кода, а прогоном набора `net` на стенде Fedora, и
все три — про то, чем модель завершения отличается от модели готовности.

### Отложенная обработка задач требует признака выборки всегда

При `DEFER_TASKRUN` ядро складывает завершения у себя и переносит их в кольцо
**только** когда обращение помечено `IORING_ENTER_GETEVENTS`. Обращение без
него задач не разбирает вовсе: кольцо остаётся пустым, сколько бы работы ни
было выполнено.

Признак ставился лишь при непустом ожидании — и опрос с нулевым ожиданием не
получал завершений никогда. Цикл событий вставал намертво. Теперь признак
ставится всегда, нулевым остаётся лишь **число ожидаемых** завершений:
обращение забирает готовое и возвращает управление сразу.

### Закрытие дескриптора не прекращает поданную операцию

Главное расхождение с epoll. Там `close()` снимал подписку сам, и настолько
надёжно, что весь учёт строился вокруг закрытия как достоверного признака.

У io_uring это неверно. Поданная операция держит **свою** ссылку на файл, и
закрытие дескриптора её не снимает. Ядро держит файл живым: соединение не
разрывается, дальняя сторона закрытия не видит, занятый порт не освобождается,
а учёт поданного растёт без предела. Замер показал **десять незавершённых
операций на двух дескрипторах** и цикл, вставший в ожидании завершения,
которого никто уже не подаст.

Отмену надо подавать по-настоящему, а не помечать, и доводить до ядра
**прежде** самого закрытия. Обращение это тратится лишь тогда, когда отменять
действительно есть что.

### Многократное ожидание не повторяет уровень

`IORING_POLL_ADD_MULTI` сообщает о готовности **один раз на переход** и ждёт
следующего. Уровень он не повторяет.

Движок же вычерпывает сокет не до конца намеренно: и по бюджету времени, и по
ограничителю полосы — иначе один нагруженный узел заморил бы все прочие. При
многократном ожидании остаток данных не разбудил бы цикл никогда.

Оттого **все ожидания готовности подаются однократными** и взводятся заново
разбором каждого события. Однократное ожидание, поданное на готовом сокете,
срабатывает тут же, чем и восстанавливается уровневое поведение, на которое
опирается весь разбор. Обращений к ядру это не добавляет: повторная подача
копится наравне со всем прочим и уходит тем же обращением, которым опрос
засыпает.

Замер: с многократным ожиданием проверка ограничителя полосы не завершалась за
две минуты, с однократным укладывается в **1072 мс** против **1058 мс** у epoll.

## Опасности, замеченные заранее

**Время жизни поданного.** Ядро читает `struct msghdr`, `struct sockaddr` и
буферы **после** возврата из `io_uring_enter`, и приложение обязано хранить их
до завершения. У epoll такого не было вовсе. Это самый вероятный источник
ошибок, и учёт поданных операций обязан владеть их памятью.

**Отмена не мгновенна.** `IORING_OP_ASYNC_CANCEL` не гарантирует, что
завершение не придёт: возможно, операция уже выполнена. Значит, узел нельзя
уничтожать по факту отмены — только по приходу завершения. Учёт «сколько
операций в полёте на узле» обязателен, иначе движок будет обращаться к
освобождённой памяти. У epoll эту роль играла отложенная уборка
(`::kernel::retired`/`sweep`) — здесь она устроена иначе и строже.

**`IORING_OP_CLOSE` и учёт.** Урок переноса на epoll — учёт обязан забываться
ровно в момент закрытия — остаётся в силе, но закрытие теперь **отложенное**:
дескриптор освободится тогда, когда ядро дойдёт до операции. До этого момента
номер занят, а после может быть выдан заново. Соответствие «номер дескриптора
→ узел» ненадёжно; связь ведётся через `user_data` завершения.

**Переполнение кольца завершений.** При `NODROP` ядро сохраняет завершения во
внутреннем списке, но подача при этом дорожает. Кольцо завершений берётся
вчетверо больше кольца подачи, а переполнение (`cq_overflow`) заносится в
журнал — молчать о нём нельзя.

## Порядок работ

1. Основание: устройство колец, проба возможностей, подача и разбор
   завершений, `NOP` и `MSG_RING`-пробуждение. Прогон `net` на пустом каркасе.
2. Таймеры на `TIMEOUT`/`LINK_TIMEOUT`.
3. Приём и подключение: `ACCEPT` многократный, `CONNECT`.
4. Обмен: `RECV`/`SEND` с кольцом буферов, `RECVMSG`/`SENDMSG` для дейтаграмм
   и SCTP.
5. Закрытие: `CLOSE`, `SHUTDOWN`, учёт операций в полёте.
6. `POLL_ADD` для inotify, TUN и SCTP.
7. Ядерный `SPLICE`.
8. Сличение с epoll: `net`, `proto`, `units` обязаны сойтись число в число.
9. Замер против epoll и соперников, счёт обращений к ядру.

Готовность считается по девятому пункту, а не по первому проходящему прогону.

## Замер: девятый пункт выполнен и опроверг ожидание

Стенд Fedora 44, ядро 6.19.10, сборка `Release`, оснастка
[`benchmark/net/io`](../../../../benchmark/net/io/README.md) — та же, которой
снимался эталон `epoll`.

| Показатель | epoll | io_uring |
|---|---:|---:|
| `echo/single`, обменов/с | 46 710 | 42 615 |
| Обращений к ядру на обмен | 6.00 | 6.00 |
| Разрез обращений | `poll 2, recv 2, send 2` | `io_uring 2, recv 2, send 2` |
| `accept/connections`, подключений/с | 9 769 | 9 370 |
| Обращений к ядру на подключение | 17 | 16 |
| `stream/throughput`, МБ/с | 2 289 | 2 351 |

**Одна лишь замена ожидания кольцом не даёт ничего.** `io_uring_enter`
заместил `epoll_wait` ровно один к одному, а обмен как шёл пользовательскими
`recv` и `send`, так и идёт. Обращений к ядру поровну, расход самих колец
добавился сверх того — и движок оказывается медленнее на девять процентов.

Вывод для порядка работ: пункты 3 и 4 — не украшение, а единственное, ради
чего движок этот вообще имеет смысл. Пока приём и передача не ушли в кольцо,
io_uring остаётся строго худшим `epoll`.

### Что счётчик обращений не видел

Оснастка подменяет **именованные функции** libc, а io_uring ходит в ядро через
`syscall` по номеру. Обращения его были невидимы вовсе, и первое сличение вышло
бы ложным: у io_uring получалось бы четыре обращения на обмен против шести у
epoll — мнимая победа на ровном месте.

В [`syscount`](../../../../tools/benchmark/syscount/README.md) заведён вид
`io_uring` и подмена вариативного `syscall`, считающая обращения с номерами
425–427. Номера заданы числами: заголовки сборочной машины вправе отставать.

### Найдено замером: два выделения памяти на каждый обмен

Учёт числа операций в полёте на узле был устроен отображением по указателю
узла: запись заводилась на каждой подаче и стиралась при освобождении — по
выделению и освобождению памяти на операцию, то есть **два на обмен**, тогда
как у `epoll` их ноль.

При этом ни `count`, ни `cancel` по узлу не звались **ниоткуда**: учёт был
мёртв целиком. От обращения к уничтоженному узлу бережёт не он, а отметка
`cancelled`, которую ставят пути закрытия.

| Показатель | До | После |
|---|---:|---:|
| Выделений на обмен | 2.0 | **0.0** |
| Выделений на подключение | 16 | **12** (как у epoll) |
| `echo/single`, обменов/с | 39 239 | **42 615** (+8.6 %) |

### Кольцо буферов: почему приём устроен именно так

Родной приём требует буфера, отданного ядру **заранее**, до прихода данных.
Отдавать его на каждое подключение нельзя: сценарий `idle` держит четыре тысячи
подключений, и по 64 КБ на каждое это четверть гигабайта, лежащей без дела.

Кольцо буферов (`IORING_REGISTER_PBUF_RING`) снимает это: приложение кладёт
общий на всех запас, ядро берёт буфер **в миг прихода данных** и сообщает его
номер в завершении. Память тогда стоит по числу подключений, у которых данные
есть прямо сейчас, а не по числу подключений вообще. Кольцо заводится лениво,
при первой надобности, и приложению без потокового обмена не стоит ничего.

**Опасность, которую надо держать в уме при врезке.** Пока по сокету заведён
приём в кольце, звать по нему обычный `recv` нельзя вовсе: ядро исполнит обе
операции, и данные придут потребителю вперемешку. Отход на `recv` допустим
только у сокетов, где приём в кольце не заведён, — и признак этот обязан быть
по сокету, а не общий на движок.

### Родная отправка: перенос памяти взамен системного вызова

Приём избавил движок от двух обращений из четырёх, а другие два оставались за
отправкой: `send` ходил в ядро сам. Устранить его оказалось не переделкой
отправки, а переделкой **владения буфером**.

Ядро читает буфер после возврата из обращения, и буфер обязан жить до прихода
завершения. Буфер вызывающего для этого не годится — он умирает возвратом из
отправки. Годится только очередь передачи узла: она порцию держит, пока
потребитель не заберёт исход. Оттого родная отправка не заменяет обращение, а
меняет **перенос памяти на системный вызов**.

Обмен этот выгоден не всегда, и граница нашлась замером. Отсюда порог
`::drain::INLINE_LIMIT`: порция мельче него идёт родным путём, крупнее — прежним,
прямо в сокет и без переноса. Без порога потоковая передача теряла треть
(1 795 → 1 298 МБ/с) — перенос 64 КБ дороже обращения, которое он берёг.

| Показатель | epoll-путь | родная отправка |
| --- | ---: | ---: |
| `idle/exchanges`, обменов/с | 45 878 | **79 327** (+73 %) |
| `echo/multi`, обменов/с | 43 029 | **62 630** (+46 %) |
| `echo/single`, обменов/с | 38 669 | 39 381 |
| `stream`, МБ/с | 1 795 | 1 820 |
| Обращений на обмен, `echo/multi` | 2.04 | **0.04** |
| Обращений на обмен, `idle` | 2.05 | **0.05** |
| Обращений на обмен, `echo/single` | 4.00 | **2.00** |

Обмен мелкими сообщениями обращается к ядру раз в двадцать пять обменов вместо
двух раз на каждый — это и есть то, ради чего io_uring подключался.

### Четыре изъяна, за которые заплачено прогонами

Все четыре — об одном: **родная отправка отвечает не тем заходом, который её
затеял**, и всякое место, где движок опирался на немедленный ответ, приходится
либо переучивать, либо обходить.

**1. Свой учёт вместо общего.** Первая врезка завела в открытой отправке
отдельную ветку, воспроизводящую учёт очереди. Воспроизвела неточно — набор терял
четыре проверки. Лечится не отладкой этой ветки, а её отсутствием: узел, годный
к родной отправке, просто **не заходит** в ветку прямой записи в сокет и попадает
в очередь общим путём, со всеми его таймаутами и обратными вызовами.

**2. Ветка очереди не взводит событие на запись.** Писалась она под случай
«очередь и без того не пуста» — стало быть событие уже взведено. С родной
отправкой туда приходит узел с пустой очередью, и взвести событие некому: данные
ложатся в очередь навсегда, цикл о них не узнаёт. Набор вставал на `IoTCPTest`.

**3. Взвод, поставленный для всех.** Ветка эта общая, и туда же попадает узел под
ограничителем полосы, которому движок паузы держит нарочно. Безусловный взвод
ломал его порядок пауз — терялся `IoBandwidthDuplexTest`. Взвод сужен ровно до случая
родной отправки.

**4. Ограничитель полосы и отложенный исход.** Ограничитель списывает токены там,
где отправка и происходит, а родная отвечает оборотом позже — учёт отстаёт, и
полоса недобирается до заданной. Узлы с заданными параметрами полосы идут прежним
путём.

### Лишний оборот цикла: где он брался и как исчез

Первое рабочее устройство было **медленнее прежнего пути** на обмене по одному
соединению: 24 814 против 38 669 обменов/с при `io_uring 4.00` на обмен вместо
двух. Причина — два оборота цикла на одну отправку: первый подавал её по
готовности к записи, второй забирал исход по завершению.

При множестве соединений это терялось в общем счёте: один заход в кольцо
обслуживает разом сотни обменов. На одном соединении обмен строго
последовательный, амортизировать нечем, и лишний оборот платится целиком.

Ждать готовности перед подачей незачем вовсе: сокет к записи готов — ничего в
очередь не клали бы иначе, — а отказ ядро сообщит завершением наравне с удачей.
Отправка подаётся **тем же заходом**, что кладёт порцию в очередь, и оборот
остаётся один. Учёт при этом не переписан ни на строку.

### Опрос ошибки сокета: признак обязан жить в событии, а не в движке

Путь записи зовёт `getsockopt(SO_ERROR)` **на каждое событие готовности**,
безусловно. Прежде это было незаметно — отправка шла прямо в сокет и событий
готовности почти не порождала. С родной отправкой всякий обмен стал проходить
через готовность, и опрос этот встал ровно на место убранного `send`.

Спрашивать ядро о том, что оно только что сообщило завершением, незачем. Но
**способ** пропуска решает всё:

- **по состоянию движка** — отложенному исходу, привязанному к дескриптору:
  набор терял четыре проверки, и терял только в полном прогоне. Состояние
  переживает и узел, и номер дескриптора; привязка исхода к узлу взамен номера
  беды не сняла;
- **по признаку в самом событии** (`::change::COMPLETED`): признак живёт ровно
  столько, сколько событие, и достаться чужому не может никак. Набор зелёный.

Разница здесь не в осторожности, а в устройстве: сведение о событии обязано
ехать вместе с событием.

**Не забыто.** Путь через очередь выделяет память под её буфер на каждый обмен
(`echo/multi`: 1.0 выделения на операцию против 0.0 у прежнего пути) — очередь
берёт блок из пула при первой записи и возвращает при опустошении, а опустошается
она каждым обменом. Разбирается это удержанием блока, а не отказом от родной
отправки.

### Кольца одного подателя: почему признаки лежали отложенными и что мешало на деле

`IORING_SETUP_SINGLE_ISSUER` вместе с `IORING_SETUP_DEFER_TASKRUN` — самое весомое,
что io_uring даёт сверх обычной подачи. Признаки эти лежали выключенными долго, и
довод был такой: они привязывают кольца к заведшему их потоку, а движок настраивают
из одного потока, цикл же ведут из другого.

**Довод оказался неполон, и разбор это исправил.**

Движок в AWH заводится **единожды на процесс** (`__awh_event_base__`) и живёт, пока
живёт процесс. Цикл же над ним поднимают и останавливают **многократно**, и всякий
раз вправе поднять в новом потоке. Кольца тогда остаются за потоком давно ушедшим,
и подача нового цикла отвергается ядром **молча** — цикл встаёт навсегда.

Проявлялось это так: набор `proto` терял пять проверок фасада QUIC по сроку
ожидания, и терял только в полном прогоне — поодиночке всякая проверка была для
колец первой.

**Попутно вскрылся изъян, живший и без признаков.** `poll()` перезаписывал
поток-владельца на **каждом** вызове:

```cpp
::__awh_poll_thread_known__ = true;
::__awh_poll_thread__ = ::pthread_self();   // безусловно, каждый оборот
```

Новый поток объявлял своим себя, кольца оставались за прежним, и подача шла прямо в
кольцо, минуя очередь отложенных. Без `SINGLE_ISSUER` ядро такую подачу прощало, и
изъян не проявлялся вовсе.

**Лечение — `::kernel::rebind()`**: заметив смену потока, движок перезаводит кольца
под новый. Учёт подписок при этом **не сбрасывается** — сокеты живы, и подписки на
них нужны; снимаются лишь метки завершения, а сами подписки помечаются требующими
согласования, и ближайший оборот подаёт их новым кольцам тем же путём, каким движок
поступает после всякого прекращения ожидания ядром. Случается перезаведение ровно
при подъёме цикла, а не в работе.

**Одновременности циклов нет** — установлено замером, счётчиком потоков внутри
опроса. Условие это обязательное: будь циклы одновременными, перезаведение не
помогло бы вовсе и кольца пришлось бы разводить по потокам.

### Итог: где io_uring стоит против epoll

Замер на одной машине, тот же стенд, те же сценарии:

| Сценарий | epoll | io_uring без признаков | **с признаками** |
| --- | ---: | ---: | ---: |
| `stream`, МБ/с | 2 125 | 1 749 | **2 201** |
| `echo/multi`, обменов/с | 46 350 | 63 173 | **71 098** |
| `idle/exchanges`, обменов/с | 44 090 | 77 744 | **72 060** |
| `accept`, подключений/с | 9 409 | 8 695 | 9 227 |
| `echo/single`, обменов/с | 40 183 | 38 839 | 38 353 |

Потоковая передача была единственным местом, где io_uring уступал, — **−18 %**
против epoll. С признаками она **+3.6 %**, то есть отставание закрыто и обращено.

Остаётся `echo/single` — обмен по одному соединению, где io_uring на 5 % позади.
Странность его в том, что обращений к ядру там **2.00 против 6.00** у epoll: расход
лежит не в обращениях.

**Отвергнуто замером: лишний оборот родной отправки.** Догадка была та, что исход
отправки приходит завершением, а не возвратом, и на строго последовательном обмене
оборот этот платится целиком. Опыт с погашенной родной отправкой (`INLINE_LIMIT`
в ноль) её не подтвердил: `echo/single` дал 37 965 против 38 353 — не лучше, а чуть
хуже. Заново не проверять.

Опыт тот же заодно измерил, чего родная отправка стоит там, где соединений много:
`echo/multi` без неё **44 092** против 71 098, то есть она даёт +61 % и почти весь
отрыв от epoll.

Признаки на `echo/single` тоже влияют слабо и в минус (38 839 без них против 38 353
с ними) — `DEFER_TASKRUN` откладывает работу задачи до прихода потока за
завершениями, и на одиночном последовательном обмене это добавляет задержки, а не
снимает её.

**Объяснено профилем: расход в нашей надстройке, а не в ядре.** Отдельным прогоном
на стенде Fedora (`perf record --call-graph=dwarf`, пять пар подряд) выяснилось
сперва, что отставание меньше заявленного и лежит на грани разброса: io_uring
42 987 в среднем против 43 870 у epoll, то есть **≈2 %** при собственном разбросе
прогонов около 2 % — лучший прогон io_uring выше худшего прогона epoll. Цифра −5 %
бралась из полного набора, где сценарий идёт после других.

Собственные затраты по коду AWH:

| | io_uring | epoll |
| --- | ---: | ---: |
| `IO::poll` | **5.15 %** | 2.98 % |
| обвязка подачи (`post::sqe`, `drain::usable`, `drain::transmit`, `polling`) | ≈2.1 % | — |

В ядре при этом всё наоборот: `__internal_syscall_cancel` с `do_syscall_64` дают
у epoll 18.3 %, у io_uring те же строки — 6.9 %. Ядерная часть втрое дешевле,
и выигрыш этот съедает **≈+4 п. п.** собственных затрат: разбор колец, реестр
дескрипторов, согласование подписок. На одном соединении экономить нечего —
обращений всего шесть и они дешёвые, — потому баланс выходит чуть в минус. Стоит
соединениям пойти счётом, и та же обвязка размазывается на десятки событий за
оборот, давая +53…63 %.

Это плата по устройству, а не упущение: разгонять `poll` ради 2 % на наименее
показательном сценарии смысла нет, тем более что тот же код и даёт весь выигрыш
на остальных. Вопрос закрыт, заново не открывать.

Попутно: сборка с `-g -fno-omit-frame-pointer` показателя не роняет, а строки
исходника `perf` не разворачивает и с `-g` (`io_uring.cpp:0`) — разбор шёл
по символам.

**Попутно решился и вопрос с выделениями.** У `echo/multi` их было 1.0 на операцию —
очередь брала блок из пула и отдавала его каждым обменом, а пул держит 64 блока при
пятистах соединениях. С признаками цикл стал быстрее, соединения реже стоят в
очереди разом, и выделения упали до **0.0**. Трогать порог пула не понадобилось.
