# Бенчмарки контейнера JSON

Отчёт по набору сценариев `benchmark/codec/json`. Измеряется модуль
`src/codec/json` — потоковое чтение текста, сборка дерева, обход дерева,
перезапись дерева в текст и запись текста значение за значением.

Набор этот меряет **нас самих во времени** и стережёт регрессии. Сличение с чужими
разборщиками ведётся отдельными стендами — `tools/benchmark/json`, — а отчёт по ним
лежит рядом, в [COMPARISON.md](COMPARISON.md). Соответствие стандарту проверяется
набором `tools/verify/codec/json`.

## Как запускать

```sh
# все сценарии подмодуля с проверкой порогов
./benchmarks/codec --filter=json

# измерение без проверки порогов (калибровка на новой машине)
./benchmarks/codec --filter=json --relaxed

# один сценарий, отбор ведётся по вхождению в название
./benchmarks/codec --filter="выделения"
```

Отклонение любого показателя от порога завершает прогон с ненулевым кодом,
поэтому набор пригоден как шаг сборки: регрессия останавливает конвейер.

## Что измеряется и почему именно это

| Сценарий | Что нагружает |
|---|---|
| `чтение ответа службы` | Постоянные накладные расходы на документ: сброс состояния, заведение вместилищ, определение кодировки. Документ малый, около 250 октетов, — тот самый случай, ради которого контейнер и написан |
| `чтение описания настроек` | Настройки службы в несколько килобайт: вложенные объекты и массивы, разбираемые однажды при запуске |
| `чтение крупного документа` | Установившаяся пропускная способность за пределами кэша процессора: 16 МБ объектов, массивов, строк и чисел в соотношении настоящих выгрузок |
| `чтение чисел` | Определение самого узкого вмещающего вида числа вместе с преобразованием записи. Виды чередуются: целое без знака, целое со знаком, дробное, дробное с порядком |
| `чтение строк` | Содержимое строк: английский текст, неанглийский текст и отменяющие последовательности разбираются тремя разными путями |
| `чтение вложенности` | Стек открытых вместилищ и размах поддерева: половина знаков такого документа приходится на строение, а не на содержимое |
| `просадка от подачи кусками` | Главное обещание чтения: выдача от нарезки текста не зависит, а стоимость её зависеть почти не должна. Подача кусками по семь байтов рвёт всякое значение |
| `выделения на чтение` | Сохранность памяти между документами: хранилище знаков и очередь событий разбор переживают, и расход на документ обязан оставаться постоянным |
| `задержка чтения ответа службы` | Тот же ответ службы, но мерою времени на документ: на мелком документе постоянные издержки в мегабайтах в секунду растворяются |
| `запись ответа службы` | Сборка исходящего документа значение за значением без удержания дерева |
| `запись чисел` | Устройство записи числа: кратчайшая запись вычисляется разбором чисел сразу, без подбора точности пробами с обратным чтением |
| `запись отменяемых знаков` | Отмена кавычек, знака отмены, перевода строки и управляющих знаков |
| `запись человекочитаемым видом` | Отступы и переводы строк: вид переключается настройкой, и собирающий документ код от него не зависит |
| `выделения на запись` | Расход на собранный и отданный наружу документ. Замер ведётся вместе с изъятием текста: без изъятия расход нулевой, ибо сброс записи память удерживает |
| `сборка дерева ответа службы` | Заведение вместилищ дерева на мелком документе |
| `сборка дерева крупного документа` | Установившаяся скорость сборки дерева сплошным перечнем узлов |
| `сборка дерева чисел` | Сборка дерева там, где всякий узел требует определения вида числа |
| `обход собранного дерева` | Обход ссылками: переход к соседу и пропуск вложенного вместилища стоят одного сложения. Дерево собирается до замера, чтобы сборка и обход не скрывали друг друга |
| `перезапись дерева в текст` | Обратная запись собранного дерева |
| `задержка обращения по имени поля` | Устройство обращения по имени: мелкие объекты разыскиваются перебором детей, крупные — отображением, заводимым по требованию |
| `выделения на сборку дерева` | Дерево хранится сплошным перечнем узлов, знаки — одним хранилищем: расход обязан оставаться считанными единицами |
| `сохранность памяти при переиспользовании документа` | Сохранность памяти между разборами: потребителю, разбирающему много документов подряд, надлежит держать один объект документа |
| `снятие значения с дерева` | Мост от разбора к владению на крупном документе: снятие поддерева собственной памятью |
| `снятие значения ответа службы` | Тот же мост на мелком документе, где решают постоянные издержки |
| `потоковая сборка значения` | Сборка документа полем за полем без дерева вовсе — путь потребителя, строящего исходящий документ |
| `запись значения в текст` | Обратная запись владеющего значения |
| `обход владеющего значения` | Обход россыпью вместилищ, сличаемый с обходом дерева ссылками |
| `выделения на снятие значения` | **Цена владения.** Дерево обходится одним выделением на документ, а значение держит память у всякого узла: показатель стережёт устройство, а не малость расхода |
| `сборка значения вызовами` | Заведение полей объекта поодиночке на 20000 полях: стережёт то, что плата на одну установку от размера объекта не зависит |
| `поиск поля значения по имени` | Парный предыдущему: обращение к полю по имени на том же объекте. Без него сторожилась бы половина свойства — правка, ускорившая сборку и замедлившая поиск, прошла бы незамеченной |

## Пороги

Пороги назначены по наименьшему из показателей отладочных стендов с двукратным
запасом: время на занятой машине расходится между прогонами на десятки
процентов, и порог, заданный впритык, поднимал бы ложную тревогу чаще, чем
ловил бы настоящую регрессию.

**Калибровать пороги по рабочей машине нельзя**: между нею и самым медленным из
стендов разница пятикратная.

**Пороги двух сценариев значения сняты обходом 22.08.2026** по двенадцати машинам:
`сборка значения вызовами` и `поиск поля значения по имени`. Дно по обоим держит
OpenBSD amd64.

**Дно берётся по середине ряда из пяти кругов, а не по худшему.** Замеры эти
чувствительны к посторонней нагрузке вспышками, а занятость машины по её
собственной выдаче не видна: стенды лаборатории живут на одном сервере, и
`load average` гостя молчит, когда грузится хозяин.

## Показатель «не более» при молчащем счётчике

Сценарии расхода памяти проверяют работоспособность учёта прежде самого
показателя: нулевой расход меньше всякого порога, и молчащий счётчик
отчитывался бы «уложился» всегда. Поломка эта уже случалась у соседнего
контейнера — у MinGW стандартная библиотека подключалась отдельной библиотекой,
и выделения внутри неё замене оператора в приложении видны не были.

## Отрицательные результаты

Записываются здесь, чтобы их не переоткрывали.

**Удешевление проверки действительности ссылки даёт 9 %, но платится
сохранностью — отвергнуто.** Обход дерева JSON шёл медленнее обхода владеющего
значения (3729 против 4088 МБ/с), тогда как у разметки XML — наоборот и вдвое с
половиной быстрее. Разница объясняется посредником обхода: у XML дерево
обходится записями арены по указателю, а у JSON — объектами ссылок
`Document::Value`, и всякое обращение через ссылку заново проверяет
действительность её сличением `_index` с размером перечня узлов. Проверка эта —
загрузка через указатель на документ, зависимая и повторяемая по нескольку раз
на узел.

Проверка была заменена на сличение `_index` с полем `_bound`, у ссылки уже
имеющимся: все места построения ссылок задают границу не свыше размера перечня,
и при живом дереве сличение это равносильно прежнему. Замер вперемежку, пять
прогонов эталона и пять правленого двоичного файла, дал медианы **3782 против
3462 МБ/с — выигрыш 9 %** при разбросе прогонов до 11 %, то есть на грани
различимости.

Отвергнуто по существу, а не по величине выигрыша: **сличение с размером
перечня — это то, что удерживает устаревшую ссылку от обращения за пределы
памяти.** Ссылка, взятая до повторного разбора, после него указывает в перечень
уже другой; ныне она отдаёт неверные данные, а с правкой отдавала бы обращение
за границу. Менять сохранность памяти на девять процентов у **самой быстрой
работы набора** — обход идёт вдесятеро быстрее разбора, и узким местом не
является нигде — цена неверная.

Оставлено как есть намеренно. Если к обходу дерева когда-нибудь вернутся,
начинать надлежит не отсюда, а с сокращения **числа** обращений через ссылку на
один узел: ныне обход зовёт `kind`, извлечение содержимого и переход к соседу
порознь, и всякое из них проверяется заново.

## Показатели по системам

Оба столбца пересняты **18.08.2026** после правки записи строк (см. ниже): macOS — на
свободной рабочей машине (Apple Silicon, macOS 26, сборка Release), Windows — на стенде
**Windows 11 ARM64** (Apple Silicon, clang 22.1 из окружения `clangarm64`, стандартная
библиотека `libc++`, библиотека языка Си UCRT) отдельным двоичным файлом замеров.
Показатели служат основанием для порогов и точкой отсчёта при правках.

**Столбец порогов пересмотрен 20.08.2026** по семи отладочным стендам и с показателями
двух столбцов рядом не снимался: пороги берутся по ДНУ, а дно держат стенды, а не эти
две машины. Прежде столбец этот стоял от 18.08.2026 и разошёлся с кодом по всем без
исключения сценариям, местами вшестеро.

**Замеры в отладочной сборке негодны**: она равномерно медленнее в девять раз и
изображает точечную регрессию там, где её нет.

**Снимать только на свободной машине.** Показатели, снятые 16.08.2026 под сборкой,
занижали полосу втрое-впятеро (чтение строк 135 вместо 384 МБ/с, обход дерева 582
вместо 3366 МБ/с) при тех же самых расходах памяти. Расход выделений при этом стоял
как вкопанный — он от загрузки машины не зависит вовсе, потому и годится основанием
там, где полоса лжёт.

### Правка записи строк 18.08.2026

Запись строки переносила знаки в текст **знак за знаком**, вызовом на всякий байт.
Обнаружилось это при замере платы за проверку кодировки UTF-8: проверка сама по
себе просаживала запись неанглийского текста на четверть, и, взявшись вытаскивать
эту четверть, нашли под нею вчетверо больше.

Знаки, отмены не требующие, переносятся теперь в текст **отрезком целиком**, и в
отрезок входят правильные последовательности UTF-8 тоже, коль скоро запись кодовыми
значениями не затребована.

| Сценарий | было 17.08 | стало 18.08 | во сколько раз |
|---|---:|---:|---:|
| запись ответа службы | 346.1 МБ/с | 568.8 | 1.64 |
| запись отменяемых знаков | 304.2 МБ/с | 926.4 | 3.05 |
| запись человекочитаемым видом | 426.0 МБ/с | 619.0 | 1.45 |
| перезапись дерева в текст | 275.0 МБ/с | 425.8 | 1.55 |
| чтение строк | 384.0 МБ/с | 412.9 | 1.08 |

Чтение правки этой не касалось вовсе, и разница в чтении строк лежит в пределах
разброса прогонов. Проверка кодировки при том **не бесплатна**: она есть, она
разбирает всякую последовательность свыше US-ASCII, — но поиск конца отрезка окупил
её впятеро.

**Столбец Windows переснят 18.08.2026** на том же стенде Windows 11 ARM64 — медиана трёх
прогонов отдельным двоичным файлом замеров (каркас плюс кодек, без библиотеки целиком).
Правку записи строк он теперь видел, и разница в записи выросла у него так же, как у
рабочей машины:

| Сценарий | было 17.08 | стало 18.08 | во сколько раз |
|---|---:|---:|---:|
| запись ответа службы | 383.1 МБ/с | 591.3 | 1.54 |
| запись отменяемых знаков | 306.4 МБ/с | 795.7 | 2.60 |
| запись человекочитаемым видом | 448.7 МБ/с | 689.3 | 1.54 |
| перезапись дерева в текст | 226.5 МБ/с | 310.8 | 1.37 |

Правка перенеслась на другой набор команд и другую стандартную библиотеку **без потерь**:
множители те же, что и у рабочей машины (1.64, 3.05, 1.45, 1.55), с точностью до разброса
прогонов. Приём — перенос знаков отрезком вместо переноса знак за знаком — от машины,
стало быть, не зависит.

Прочие столбцы Windows тоже переснялись тем же заходом: прежние снимались другой сборкой
(полной, через CMake), и разброс между ними и нынешними доходит до 24 % на чтении строк.
Сличать надлежит числа одного сеанса, а не разных.

### Владеющее значение

Снято 18.08.2026 там же; столбец Windows снят тем же заходом на стенде Windows 11 ARM64.

| Сценарий | macOS ARM64 | Windows ARM64 | Порог |
|---|---:|---:|---:|
| снятие значения с дерева | 476.6 МБ/с | 182.7 | 12 |
| снятие значения ответа службы | 676.5 МБ/с | 740.6 | 26 |
| потоковая сборка значения | 629.3 МБ/с | 486.0 | 26 |
| запись значения в текст | 485.0 МБ/с | 355.4 | 34 |
| обход владеющего значения | 4072.7 МБ/с | 3234.5 | 210 |
| выделения на снятие значения | 5 выд./док. | 5 | не более 12 |

**Снятие крупного документа на Windows идёт втрое медленнее** (182.7 против 476.6), тогда
как снятие ответа службы там даже быстрее (740.6 против 676.5). Расход памяти при том
совпадает знак в знак — 530 989 выделений и 130 МБ на обеих системах, — и значит, дело не
в объёме работы, а в **цене одного выделения**: на мелком документе их пять, на крупном
полмиллиона, и разница распределителей проступает именно там. Это довод в пользу того же
правила: снимать надлежит поддерево, а не выгрузку целиком.

#### Цена владения

Главное число здесь — **не полоса, а расход памяти**, и оно велико:

| Что снимается | выделений на документ | взято памяти |
|---|---:|---:|
| ответ службы, 208 октетов | 5 | 1384 октета |
| крупный документ, 16 МБ | 530 989 | 130 МБ |

Дерево на тот же крупный документ обходится **одним** выделением. Разница эта не
изъян, а устройство: дерево хранит узлы сплошным перечнем, а знаки — одним
хранилищем, тогда как владеющее значение держит у всякого узла свою строку, свой
перечень имён и свой перечень детей. Плата эта берётся за то, ради чего тип и
заведён, — за право пережить документ и уйти наружу итогом метода.

**Отсюда правило употребления, и его стоит держать в описаниях на виду:** снимать
владеющим значением надлежит **поддерево**, а не документ целиком. Снятие
шестнадцатимегабайтной выгрузки берёт вчетверо больше памяти, чем сам её текст;
снятие ответа службы — полтора килобайта на две сотни октетов, и это уже цена
разумная.

#### Неожиданное: обход и запись у значения быстрее, чем у дерева

| Сценарий | дерево | значение |
|---|---:|---:|
| обход | 3775.5 МБ/с | 4072.7 |
| запись в текст | 425.8 МБ/с | 485.0 |

Сплошной перечень узлов, казалось бы, обязан обходиться быстрее россыпи. Объяснение
в том, чем обходят: у дерева обход идёт **ссылками**, и всякий шаг заводит объект
ссылки из трёх полей и зовёт переход к соседу, а у значения дети лежат готовым
вместилищем и обходятся перебором его. То есть меряется здесь не расположение
памяти, а стоимость посредника обхода.

Вывод для дерева отсюда напрашивается, но его надо ещё проверить замером: обход
ссылками стоит дороже, чем мог бы, и это место — кандидат на правку. Записано как
наблюдение, а не как приговор: сличение неполное, ибо документ у обоих один и тот
же, но и работа у них разная — значение уже снято, а дерево обходится по месту.

### Сличение систем

Расходы памяти совпали **знак в знак** на обеих системах — 1 выделение на чтение,
1 на сборку дерева, 3 на запись, 5 на снятие значения ответа службы и 530 989 на снятие
крупного документа. Полоса же разошлась по-разному: на чтении и сборке дерева Windows
отстаёт в пределах 1.2 раза, на обходе дерева — в 1.4, на снятии крупного значения — в
2.6, а на **записи он местами впереди** (запись человекочитаемым видом 689 против 619).
Это разница стандартных библиотек и распределителей (`libc++` UCRT против `libc++`
macOS), а не кодека: работа у обоих одна и та же, что и подтверждается совпадением
расхода памяти.

Учёт памяти на стенде Windows работает **только при связывании с
`-static-libstdc++`**: иначе оператор выделения приходит из отдельной библиотеки,
замены не видит и отчитывается нулём. Каркас замеров такой ноль ловит сторожем и
объявляет сценарий негодным, а не проходящим.
