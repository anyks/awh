# Бенчмарки контейнера INI

Отчёт по набору сценариев `benchmark/codec/ini`. Измеряется модуль
`src/codec/ini` — потоковое чтение текста настроек, сборка дерева, поиск по
дереву и запись текста настроек.

## Как запускать

```sh
# все сценарии подмодуля с проверкой порогов
./benchmarks/codec --filter=ini

# измерение без проверки порогов (калибровка на новой машине)
./benchmarks/codec --filter=ini --relaxed

# один сценарий, отбор ведётся по вхождению в название
./benchmarks/codec --filter="выделения"
```

Отклонение любого показателя от порога завершает прогон с ненулевым кодом,
поэтому набор пригоден как шаг сборки: регрессия останавливает конвейер.

## Что измеряется и почему именно это

| Сценарий | Что нагружает |
|---|---|
| `чтение настроек службы` | Постоянные накладные расходы на файл: заведение хранилищ разбора, приведение кодировки, сброс состояния. Файл малый, около 500 октетов, — тот самый случай, ради которого контейнер и написан: файл настроек читается однажды при запуске приложения |
| `чтение настроек Git` | Наречие, нагружающее разбор сильнее прочих: подраздел в кавычках, примечание в конце строки, управляющие последовательности и свойство без значения — всё сразу |
| `чтение крупного файла` | Текст на 16 МиБ: разбор в установившемся режиме, где накладные расходы на файл пренебрежимы, а видна собственная скорость разбора |
| `чтение примечаний` | Текст, наполовину состоящий из примечаний. Файл настроек, писанный человеком, устроен именно так, и путь разбора примечаний нагружается наравне с разбором свойств |
| `выделения на чтение` | Количество выделений памяти на разбор одного файла. Показатель воспроизводим до единиц и от размера файла не зависит: чтение ведётся на переиспользуемых хранилищах |
| `просадка от подачи кусками` | Отношение времени подачи текста кусками по 1460 октетов ко времени подачи того же текста целиком |
| `задержка чтения настроек службы` | Время обработки одного малого файла в микросекундах. На таком файле решает не пропускная способность, а стоимость запуска разбора |
| `запись настроек службы` | Сборка исходящего текста: объявления разделов, свойства, примечания, запись чисел |
| `запись ограждаемых значений` | Значения, требующие кавычек либо управляющих последовательностей: пробельная обвязка, знак примечания, кавычка, знак конца строки |
| `сборка дерева настроек службы` | Сборка дерева поверх чтения: к разбору добавляются хранилище знаков и указатели поиска |
| `сборка крупного дерева` | То же на тексте в 16 МиБ: видна стоимость роста хранилищ |
| `сборка дерева со множеством разделов` | Около сотни тысяч разделов: стережёт устройство поиска разделов. Раскладка по свёртке имени держит стоимость заведения раздела постоянной, попарное сличение имён обратило бы сборку в квадратичную |
| `обратная запись дерева` | Запись собранного дерева обратно в текст с сохранением примечаний и порядка записей |
| `поиск значений по имени` | Обращения к значениям по имени раздела и имени свойства. Стережёт раскладку по свёртке имён: перебор записей дерева при каждом обращении уронил бы показатель на порядки |

### Про потребление результата

Чтение содержимое **само не копирует**: события выдают представления во
внутреннее хранилище разбора. В сценариях чтения потребитель обязан
просуммировать итог, иначе компилятор вправе устранить измеряемый разбор
целиком и замерялась бы стоимость пустого цикла. Итоги всех прогонов
накапливаются в контрольную сумму `checksum()`.

### Про эталонные тексты

Все эталонные тексты собираются однократно до замера и возвращаются ссылкой на
объект строки: сборка их внутри измеряемого цикла выделяла бы память и вносила
бы в замер стоимость работы со строкой вместо стоимости разбора.

### Про пороги

Пороги получены из показателей выше делением на восемнадцать: девятикратный
запас на отставание самого медленного из отладочных стендов и двукратный на
разброс между прогонами. Показатели, не зависящие от быстродействия машины, —
количество выделений и просадка от подачи кусками — заданы впритык.

**Пороги назначены расчётом, а не замером на стендах.** Отношение между рабочей
машиной и стендами взято из уже известного по бенчмаркам контейнера XML, но там
оно по сценариям расходилось: OpenBSD отставал вдесятеро на задержке и вчетверо
на пропускной способности. После первого прогона на стендах пороги следует
уточнить по наименьшему из снятых там показателей.

## Чего в наборе нет

**Сличения со сторонними разборами.** Ни `inih`, ни `SimpleIni` в дерево
подмодулей не заведены, и сличение с ними потребовало бы их туда добавить.
Работа эта осмысленна — она показала бы, чего стоит поддержка пяти наречий
против разбора, знающего одно, — но заводить подмодуль ради замера следует
осознанно, а не мимоходом.

**Замера расхода памяти деревом.** Дерево держит весь текст настроек вместе с
примечаниями, и расход его памяти кратен размеру файла — величина эта видна из
столбца `окт./файл` сведений о прогоне и отдельного сценария не требует.
