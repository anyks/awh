# Бенчмарки контейнера CSV

Отчёт по набору сценариев `benchmark/codec/csv`. Измеряется модуль
`src/codec/csv` — потоковое чтение текста таблицы, сборка таблицы целиком,
обход собранного, запись текста и потоковая выдача записей.

## Как запускать

```sh
# все сценарии подмодуля с проверкой порогов
./benchmarks/codec --filter=csv

# измерение без проверки порогов (калибровка на новой машине)
./benchmarks/codec --filter=csv --relaxed

# один сценарий, отбор ведётся по вхождению в название
./benchmarks/codec --filter="выделения"
```

Отклонение любого показателя от порога завершает прогон с ненулевым кодом,
поэтому набор пригоден как шаг сборки: регрессия останавливает конвейер.

## Что измеряется и почему именно это

| Сценарий | Что нагружает |
|---|---|
| `чтение ответа службы` | Постоянные накладные расходы на таблицу: заведение хранилищ разбора, приведение кодировки, сброс состояния. Таблица малая, около двух сотен октетов, — выдача по договору HTTP идёт именно такими |
| `чтение крупной таблицы` | Текст на 16 МиБ: разбор в установившемся режиме, где накладные расходы на таблицу пренебрежимы, а видна собственная скорость разбора |
| `чтение широкой таблицы` | Тридцать два столбца: работа приходится на разделители и завершение полей, а не на содержимое |
| `чтение полей в кавычках` | Всякое поле в кавычках, внутри разделители и удвоенные кавычки. Путь этот у разбора отдельный, и снятие отмены кавычек нагружает его сильнее прочих |
| `чтение многострочных полей` | Поля с переводами строк внутри кавычек. Путь, отличающий договор RFC 4180 от разбора по строкам: половина сравниваемых реализаций его не умеет вовсе |
| `выделения на чтение` | Количество выделений памяти на разбор одной таблицы. Показатель воспроизводим до единиц и от размера таблицы зависеть почти не должен: чтение ведётся на переиспользуемых хранилищах |
| `просадка от подачи кусками` | Отношение времени подачи текста кусками по 1460 октетов ко времени подачи того же текста целиком |
| `просадка от определения разделителя` | Отношение времени разбора с определением разделителя ко времени разбора с заданным. Определение откладывает выдачу до тех пор, пока разделитель не определится, и надбавка эта приходится на начало текста |
| `задержка чтения ответа службы` | Время обработки одной малой таблицы в микросекундах. На такой таблице решает не пропускная способность, а стоимость заведения разбора |
| `запись полей без кавычек` | Сборка исходящего текста: разделители, знаки конца строки, проверка необходимости кавычек |
| `запись полей в кавычках` | Поля, требующие кавычек: разделитель внутри поля, кавычка, перевод строки, пробельная обвязка |
| `запись числовых полей` | Запись чисел подбором кратчайшей записи, читающейся обратно тем же числом. Наращивание точности от единицы до наибольшей стоит дороже записи последовательности знаков |
| `выделения на запись` | Количество выделений памяти на запись одной таблицы. Запись ведётся дописыванием в одно хранилище, и число выделений растёт логарифмом от размера |
| `надбавка потокового изъятия` | Отношение времени записи с изъятием собранного по мере накопления ко времени записи той же таблицы целиком |
| `сборка крупной таблицы` | Сборка таблицы поверх чтения: к разбору добавляются хранилище знаков и указания на поля |
| `обход собранной таблицы` | Обход всех полей собранной таблицы по номерам. Стережёт устройство хранения: поля суть указания в единое хранилище знаков, и обращение стоит сложения указателя |
| `доступ по имени столбца` | Обращения к полям по имени столбца. Стережёт соответствие имён их номерам: поиск попарным сличением имён обратил бы обход таблицы в квадратичный |
| `перезапись собранной таблицы` | Запись собранной таблицы обратно в текст |
| `просадка потоковой выдачи` | Отношение времени потоковой выдачи записей обработчику ко времени сборки той же таблицы целиком. Выдача проходит те же события, но таблицу не заполняет вовсе, и медленнее сборки быть не должна |
| `память потоковой выдачи` | Объём выделяемой памяти на одну запись при потоковой выдаче. Путь этот заведён ради таблиц, в память не помещающихся, и объём на запись от размера таблицы зависеть не должен вовсе |
| `выделения на сборку таблицы` | Количество выделений памяти на сборку одной таблицы |
| `задержка сборки ответа службы` | Время сборки одной малой таблицы в микросекундах |

### Про потребление результата

Чтение содержимое **само не копирует**: события выдают представления во
внутреннее хранилище разбора. В сценариях чтения потребитель обязан
просуммировать итог, иначе компилятор вправе устранить измеряемый разбор
целиком и замерялась бы стоимость пустого цикла. Итоги всех прогонов
накапливаются в контрольную сумму `checksum()`.

### Про эталонные таблицы

Все эталонные таблицы собираются однократно до замера и возвращаются ссылкой на
объект строки: сборка их внутри измеряемого цикла выделяла бы память и вносила
бы в замер стоимость работы со строкой вместо стоимости разбора.

#### Учёт памяти там молчал

Прогон вскрыл поломку **учёта выделений памяти**, а не модуля. Учёт ведётся
заменой оператора выделения памяти в самом бинарном приложении, а у MS Windows
всякая динамическая библиотека несёт свой собственный оператор: выделения,
сделанные внутри `libstdc++-6.dll`, замене не видны вовсе.

Учёт при этом **не отказывал, а молча недосчитывал**: 22 выделения против 64 на
чтении, 57 против 110 на сборке, а на записи — ровно нуль. Показатель «не более»
при молчащем счётчике отчитывается «уложился» при любом пороге, и все четыре
сценария расхода памяти проходили, ничего не проверяя.

Лечится связыванием со статической стандартной библиотекой
(`-static-libstdc++ -static-libgcc`) — после него Windows даёт те же 17, 64, 110
и 56.56, что и прочие стенды. Правка внесена во все наборы замеров, а не только
в этот. Сверх того, сценарии расхода памяти теперь **отчитываются отказом при
молчащем счётчике** — нулевой расход больше не проходит за исправность.

### Что видно из прогона

**Самый медленный стенд — OpenBSD**, и отстаёт он не равномерно: на чтении он
даёт вдесятеро меньше рабочей машины, тогда как прочие — втрое-впятеро. Пороги
чтения оттого держатся именно им.

**Запись числовых полей зависит не от машины, а от библиотеки языка Си.** Стенды
`glibc` дают 3.44–3.66 МБ/с против 4.88–7.18 у `musl` и систем BSD — вдвое
меньше при вдвое более быстрой машине. Подбор кратчайшей записи упирается в
обратное чтение числа средствами библиотеки, и её устройство решает здесь
больше, чем частота.

**Расход памяти расходится по стандартной библиотеке, а не по системе.** Замер
подтвердил это дважды: выделений на чтение 63 у `libc++` против 64 у
`libstdc++`, памяти на запись потоковой выдачи 46.45 октета против 56.56.
Границей проходит короткий запас строки — 22 знака против 15.

**Просадка от подачи кусками ниже единицы у всех двенадцати** (0.26–0.71):
подача кусками идёт быстрее подачи целиком. Куски укладываются в кэш, тогда как
проход по тексту на 16 МиБ вымывает его целиком.

### Про пороги

**Пороги сняты прогоном по стендам** и назначены по самому медленному,
делённому надвое — тем же правилом, что и у контейнера INI.

Правило это возникло не из осторожности: пороги, назначенные прежде по рабочей
машине с десятикратным запасом, на стендах **не удержались дважды**, и оба раза
код был полностью исправен.

| Сценарий | Прежний порог | Стенд | Снято | Новый порог |
|---|---:|---|---:|---:|
| чтение широкой таблицы | 20.00 | OpenBSD | 19.01 | 9.00 |
| запись числовых полей | 4.00 | Debian | 3.42 | 1.00 |

Отсюда правило: **запас к рабочей машине доводом не служит**, порог берётся
замером на стендах.

Показатели, не зависящие от быстродействия машины, — просадки и количество
выделений — оставлены впритык намеренно: именно тугими они и нашли два дефекта
расхода памяти. Ослаблять их при отказе нельзя, отказ там означает, что
хранилище перестало переиспользоваться.

## Что нашёл набор при первом прогоне

Оба дефекта — расход памяти, и оба нашлись сразу, потому что показатели по
выделениям заданы впритык.

**Очередь событий разбора выделяла двадцать шесть тысяч раз на таблицу.**
Заведена она была двусторонней очередью, а та отводит по блоку памяти на каждые
несколько десятков событий и освобождает его по опустошении. Разбор таблицы на
16 МиБ выдаёт около двух миллионов событий — двадцать шесть тысяч блоков,
заводимых и освобождаемых по одному. Очередь заменена перечнем с указанием на
голову: выделенное удерживается и переиспользуется, и после первой таблицы
выделений не бывает вовсе. Итог: 26 034 → 63.

**Потоковая выдача записей удерживала в памяти всю таблицу.** Разбор собирает
события в очередь выдачи, а выдаются они лишь по возврате из подачи: подача
текста целиком наполняла очередь событиями всей таблицы разом. Путь этот заведён
ради таблиц, в память не помещающихся, и удержание разобранного отнимало у него
то единственное, ради чего он есть. Подача разбита на куски по 64 КиБ - и для
потоковой выдачи, и для сборки таблицы целиком. Итог: 1114 → 46 октетов на
запись, а скорость разбора не изменилась вовсе.

## Сличение со сторонними реализациями

Стенды сравнения с `libcsv`, `csv-parser`, `csv2`, `fast-cpp-csv-parser` и
`rapidcsv` лежат в [tools/benchmark/csv](../../../tools/benchmark/csv), отчёт по
ним — в его описании. Собираются они отдельно от библиотеки и в состав её не
входят.

Сличение это уже окупилось: первый его прогон показал двукратное отставание от
прочих потоковых реализаций и позволил разложить стоимость разбора по частям.
По итогам разбор ускорен вполовину-вдвое.
