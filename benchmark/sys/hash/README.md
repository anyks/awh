# Бенчмарки модуля хэширования

Отчёт по набору сценариев `benchmark/sys/hash`. Измеряется модуль
`src/sys/hash` — быстрое некриптографическое хэширование данных произвольного
размера с выводом результата произвольной разрядности, в одноразовом и
потоковом режимах.

Сравнение с CityHash, ради замены которого модуль и написан, вынесено в
отдельные стенды: [`tools/benchmark/hash/`](../../../tools/benchmark/hash/README.md).
Здесь измеряется только сам модуль.

## Как запускать

```sh
# все сценарии подмодуля с проверкой порогов
./benchmarks/sys --filter=hash

# измерение без проверки порогов (калибровка на новой машине)
./benchmarks/sys --filter=hash --relaxed

# одна группа сценариев
./benchmarks/sys --filter=hash/stream
./benchmarks/sys --filter=hash/oneshot/key-8
```

Отклонение любого показателя от порога завершает прогон с ненулевым кодом,
поэтому набор пригоден как шаг сборки: регрессия останавливает конвейер.
Полный прогон занимает около четырёх секунд в неоптимизированной сборке.

## Что измеряется и почему именно это

Размеры данных выбраны не круглыми числами ради красоты таблицы, а по границам
ветвей обработки: движок обрабатывает данные до 16 октетов одним чтением
внахлёст, до 64 — свёрткой двумя встречными накопителями минуя состояние, свыше
64 — блоками через состояние из четырёх независимых разрядов. Сценарий на каждую
ветвь ловит регрессию именно в ней.

| Сценарий | Что нагружает |
|---|---|
| `oneshot/key-8` | Ключ хэш-таблицы размером в машинное слово. Здесь измеряется не пропускная способность, а стоимость вызова: работы с данными меньше, чем работы по её запуску |
| `oneshot/key-16` | Граница первой ветви: данные читаются двумя числами внахлёст и сворачиваются двумя умножениями |
| `oneshot/key-32` | Вторая ветвь: два встречных накопителя, идущих с начала и с конца буфера навстречу друг другу |
| `oneshot/key-64` | Верхняя граница короткого пути: четыре независимых умножения плюс окончательная свёртка |
| `oneshot/bandwidth-256` | Переход на блочную обработку через состояние движка: один полный блок плюс неполный |
| `oneshot/bandwidth-4k` | Установившийся режим блочной обработки на данных, целиком помещающихся в кэш первого уровня |
| `oneshot/bandwidth-1m` | Пропускная способность на данных, не помещающихся в кэш: показатель ловит потерю независимости разрядов состояния |
| `oneshot/allocations-per-op` | Количество выделений памяти на одну операцию хэширования |
| `stream/chunk-17` | Худший случай потокового режима: порция меньше блока, каждая подача копируется в буфер неполного блока целиком |
| `stream/chunk-1500` | Типичный случай: порции размером с сетевой пакет, копируется только неполный остаток |
| `stream/chunk-64k` | Крупные порции: блоки обрабатываются прямо из буфера вызывающего, минуя копирование |
| `stream/update-64` | Стоимость передачи одной порции размером ровно с блок |
| `stream/digest` | Стоимость формирования результата: выполняется по копии состояния, поэтому не должна зависеть от объёма уже обработанных данных |
| `stream/allocations-per-run` | Количество выделений памяти на полный прогон потокового хэширования мегабайта |
| `widths/uint32`, `widths/uint64` | Результат разрядностью до машинного слова: возвращается числом, минуя буфер и формирование потока октетов |
| `widths/uint128`, `widths/uint256`, `widths/uint1024` | Результат свыше машинного слова: формируется потоком октетов, каждые следующие восемь октетов стоят одного перемешивания |
| `widths/bignum-key` | Хэширование самого длинного числа — 32 октета его буфера |
| `widths/std-hash` | Специализация `std::hash` для длинных чисел: создаёт объект хэширования на каждый вызов |
| `widths/allocations-per-op` | Количество выделений памяти на вывод результата наибольшей разрядности |

### Про данные

Эталонный буфер заполнен значащими октетами во всех позициях и общий для всех
сценариев: отрезок нужного размера берётся от его начала, поэтому сценарии
сравнимы между собой. Результат каждой операции накапливается в контрольную
сумму — без потребителя результата компилятор вправе устранить измеряемое
хэширование целиком, и замерялась бы стоимость пустого цикла.

### Про учёт выделений памяти

Показатели `allocations/*` в отличие от пропускной способности **не зависят от
машины и режима сборки**, поэтому их пороги заданы вплотную к измеренному
значению.

Ноль выделений — следствие устройства: состояние движка (четыре 64-битных
разряда) и буфер неполного блока (64 октета) размещаются в самом объекте
хэширования, а результат — в буфере вызывающего либо в собственном массиве
октетов длинного числа. Динамическая память в модуле не используется вовсе,
включая потоковый режим на данных любого объёма.

## Что из этого следует

**Хэширование не выделяет память вообще — ни в одном режиме.** Это самый ценный
показатель набора: он не зависит от окружения и ловит появление любого выделения
в горячем пути. Потоковое хэширование мегабайта порциями по 1500 октетов — 700
вызовов передачи данных — обходится нулём выделений, потому что буфер неполного
блока живёт в самом объекте.

**Стоимость короткого ключа определяется не размером данных, а вызовом.** Ключ
в 8 октетов обрабатывается за 1.25 нс, ключ в 16 — за 1.25 нс, то есть **ровно
столько же**: обе длины проходят одной ветвью в два умножения, и разница в
восемь октетов чтения на фоне вызова неразличима. Рост начинается с 32 октетов
(1.49 нс) и с 64 (1.87 нс), где добавляются вторая пара накопителей и
окончательная свёртка.

**Пропускная способность выходит на полку к четырём килооктетам** — 37.4 ГБ/с
против 37.2 ГБ/с на мегабайте, то есть 4 КБ уже достаточно, чтобы стоимость
входа в функцию и обработки неполного блока размазалась. На 256 октетах
пропускная способность на четверть ниже полки (26.7 ГБ/с): там на четыре полных
блока приходится одна фиксированная свёртка состояния.

**Потоковый режим на крупных порциях бесплатен относительно одноразового**
(37.1 ГБ/с против 37.2 ГБ/с, разница меньше процента): блоки обрабатываются прямо
из буфера вызывающего, и данные через буфер неполного блока не проходят вовсе.
На порциях размером с сетевой пакет потери тоже почти нет (31.3 ГБ/с) —
копируется только неполный остаток, в среднем полблока на порцию.

**Мелкие порции стоят десятикратно** (3.85 ГБ/с против 37.1): порция в 17
октетов копируется в буфер неполного блока целиком, и на каждый обработанный
блок приходится около четырёх копирований плюс четыре проверки заполнения.
Это цена не хэширования, а сборки блоков — по этой причине потоковый режим
имеет смысл кормить теми порциями, которыми данные приходят от сети или с
диска, а не дробить их искусственно.

**Формирование результата в потоковом режиме не зависит от объёма обработанных
данных** — 217 млн операций в секунду после четырёх килооктетов обработки.
Результат считается по копии состояния, поэтому промежуточный результат можно
снимать сколь угодно часто, продолжая подачу данных.

**Результат до машинного слова обходится вчетверо дешевле 128-битного**
(664 млн против 173 млн операций/с, 1.51 нс против 5.78 нс). Разница делится на
две части, и это важно для выбора типа результата:

- собственно хэширование шире машинного слова стоит одного перемешивания на
  каждые следующие восемь октетов — по замеру стенда сравнения, где результат
  снимается в массив октетов, 128 бит обходятся в 3.6 нс против 1.4 нс у 64;
- остальное — цена **длинного числа как объекта**: его конструктор и методы
  доступа живут в `src/sys/bignum.cpp` и вызываются через границу единицы
  трансляции, поэтому не встраиваются. На одной и той же разрядности и тех же
  входных данных вывод в `uint128_t` стоит 5.8 нс против 3.6 нс у массива
  октетов — разница целиком приходится на объект.

Отсюда практическое следствие: для ключа хэш-таблицы брать `uint64_t`, для
широкого результата в горячем цикле — `std::array`, а длинное число — там, где
с результатом дальше идёт арифметика.

**Специализация `std::hash` для длинных чисел не дороже прямого вызова** —
2.25 нс против 2.23 нс. Прежде она создавала объект хэширования на каждый вызов
и стоила 2.53 нс в оптимизированной сборке и втрое дороже в неоптимизированной;
теперь она обращается к функции формирования хэша напрямую, минуя объект.

**Оптимизация даёт от четырёх до пятнадцати раз** — заметно больше, чем в
арифметических модулях. Причина в природе кода: хэширование состоит из
умножений и сдвигов над регистрами, и без оптимизации каждый промежуточный
результат уходит в стек и читается обратно. Больше всего выигрывает
хэширование коротких ключей (в 13–15 раз), где после встраивания от операции
остаётся несколько регистровых умножений.
Меньше всего — потоковый режим на мелких порциях (в 4 раза): там доминирует
копирование в буфер неполного блока, скорость которого от режима сборки почти
не зависит.

## История разработки

Первая версия модуля повторяла устройство CityHash буквально: короткие данные
обрабатывались отдельными ветвями по длинам, длинные — четырьмя разрядами
состояния, результат свыше 64 бит собирался из пары чисел. Замеры показали
две проблемы, обе устранены и обе закреплены порогами.

**Короткие данные проходили через буфер результата.** Хэш ключа в 8 октетов
формировался как поток октетов: свёртка, запись восьми октетов в буфер, чтение
их обратно в число. Стоило это 5.2 нс против 1.4 нс у CityHash — вчетверо
дороже при том же количестве умножений. Быстрый путь для результата разрядностью
до машинного слова (`hashing::generate` с выводом числом) снял накладные расходы
целиком: 1.96 нс. Порог `oneshot/key-8` ловит возврат к прежнему пути.

**Свёртка коротких данных не встраивалась в место вызова.** Компилятор не
встраивал её из-за размера: она вызывалась из двух мест и содержала обе ветви —
и короткую, и блочную. Разделение на встраиваемую короткую часть и вынесенную
блочную дало ещё примерно в полтора раза на коротких ключах — 1.60 против
2.35 ГБ/с на четырёх октетах. Порог здесь тот же.

**Цепочка зависимых умножений в свёртке коротких данных.** Первая версия
свёртки для 17–64 октетов шла последовательным накопителем: каждое следующее
умножение ждало результата предыдущего. Замена на два встречных накопителя,
перекрывающихся посередине, дала +50 % на 32 октетах, потому что процессор
выполняет их умножения одновременно. Порог `oneshot/key-32` ловит возврат к
последовательному накопителю.
