# Бенчмарки модуля криптографии

Отчёт по набору сценариев `benchmark/cryptography/crypto`. Измеряется модуль `src/cryptography/crypto` —
симметричное шифрование блоками AES в обоих режимах, потоковая работа, вывод ключа из
пароля, хэширование, выработка имитовставки, кодирование BASE64, работа с ключами RSA и
схемы электронной подписи, включая ГОСТ Р 34.10-2012 обеих разрядностей.

Сличение своей реализации ГОСТ по скорости с `gost-engine` вынесено отдельно —
[`COMPARISON.md`](COMPARISON.md). Здесь измеряется только сам модуль.

## Как запускать

```sh
# все сценарии подмодуля с проверкой порогов
./benchmarks/cryptography --filter=crypto

# измерение без проверки порогов (калибровка на новой машине)
./benchmarks/cryptography --filter=crypto --relaxed

# одна группа сценариев
./benchmarks/cryptography --filter=crypto/stream
./benchmarks/cryptography --filter=crypto/keys
```

Отклонение любого показателя от порога завершает прогон с ненулевым кодом, поэтому набор
пригоден как шаг сборки: регрессия останавливает конвейер.

**Мерить только выпускной сборкой.** Отладочный каталог `build` для замеров непригоден:
на потоковой расшифровке он врёт на порядок (см. ниже), и порог, снятый по нему, стоял бы
не там, где надо.

### Прогон по стендам

**Только настоящей сборкой проекта.** Прежде здесь стояла строка сборки отдельным
двоичным файлом «без `libawh` и без подмодулей — нужен лишь системный OpenSSL». Она
экономила часы и **мерила не тот продукт**: AWH несёт свой BoringSSL, вкомпилированный
статически, а такой файл связывался с системным OpenSSL. Расхождение не в процентах —
`signature/fingerprint` отличался в сорок пять раз, а расход памяти на `digest/sha256`
менялся с одного выделения на два. Пороги, снятые так, стояли не там, где надо.

```sh
mkdir build-release && cd build-release
cmake .. -DCMAKE_BUILD_TYPE=Release -DCMAKE_BUILD_BENCHMARKS=ON
make awh_BENCHMARK_cryptography -j8
./benchmarks/cryptography --filter=crypto
```

**Предмет измерения доказывать двумя щупами на выходе**, а не предполагать:

```sh
strings ./benchmarks/cryptography | grep -c BoringSSL   # должно быть больше нуля
ldd ./benchmarks/cryptography | grep -c libcrypto       # должно быть ноль
```

Условия отдельных систем: у DragonFly собиратель задаётся явно
(`-DCMAKE_CXX_COMPILER=g++14`, системный g++ 8.3 наш код не собирает) и при запуске
нужен `LD_LIBRARY_PATH=/usr/local/lib/gcc14`; у macOS `src/sys/fs.cpp` требует
Objective-C++ и связки `-framework Foundation`, о чём CMake знает сам.

### Порог сторожит окружение, регрессию сторожит сличение с собой

Порог здесь — **дно окружения**: одно число на все машины, снятое по самой медленной из
них с двукратным запасом. Оно ловит грубую поломку сценария и сборку без оптимизации.
Просадку вдвое на быстрой машине оно **не поймает** — там запас до дна многократный, и
это не изъян калибровки, а свойство одного числа на разные машины.

Регрессию ловит сличение машины **с самой собой**: у каждой свой ряд, и допущений о
машине оно не делает вовсе.

```sh
./benchmarks/cryptography --filter=crypto --record=~/crypto.base   # снять ряд
./benchmarks/cryptography --filter=crypto --baseline=~/crypto.base # сличить с ним
```

Просадка сверх четверти (`--slack=ДОЛЯ`) печатается строкой «ПРОСАДКА» и даёт код выхода
1. Четверть взята между разбросом соседних прогонов на одной машине (до десятой доли) и
двукратным запасом порога. Отсутствие файла ряда — не отказ, а первый прогон, и набор
говорит об этом прямо: молчание иначе неотличимо от сличения, не нашедшего просадки.

Без этих ключей набор ведёт себя в точности как прежде.

## Что измеряется и почему именно это

| Сценарий | Что нагружает |
|---|---|
| `oneshot/gcm-64` | Разовое шифрование сообщения размером с сетевой кадр. На таком размере измеряется не пропускная способность шифра, а стоимость самого вызова: отведение буфера, выработка вектора инициализации, снятие имитовставки |
| `oneshot/cfb-64` | То же гаммированием. Сличение с предыдущим даёт цену проверки подлинности |
| `oneshot/gcm-1k` | Разовое шифрование порции, на которой стоимость вызова уже не главенствует |
| `oneshot/gcm-1k-decode` | Разовая расшифровка той же порции: сверка имитовставки против её выработки |
| `oneshot/base64-1k` | Кодирование BASE64 цепочкой объектов библиотеки криптографии. Замер даёт цену этого выбора против табличного кодировщика |
| `stream/encode-1k` | Поток шифрования, подаваемый порциями по килооктету — обычная единица подачи в сетевых работах |
| `stream/encode-64k` | Тот же поток крупными порциями: сличение показывает цену самой подачи |
| `stream/decode-1k` | Поток расшифровки порциями. В режиме с проверкой подлинности удерживает последние октеты потока, и сличение с шифрованием даёт цену этого удержания |
| `stream/decode-64k` | То же крупными порциями |
| `stream/cycle` | Полный оборот потока — заведение, одна порция, завершение. Показывает, выводится ли ключ заново при всяком заведении |
| `stream/derive` | Вывод ключа из пароля и соли. Соль меняется на всяком обороте, иначе замерялось бы удержание ключа |
| `digest/sha256-64` | Хэширование короткого сообщения: стоимость вызова вместе с отведением памяти под запись |
| `digest/sha256-1k` | Хэширование порции потока: работа самой суммы |
| `digest/hmac-1k` | Выработка имитовставки на тех же данных: цена ключа |
| `keys/encrypt` | Шифрование ключом RSA открытым ключом |
| `keys/decrypt` | Расшифровка закрытым ключом — на два порядка дороже |
| `keys/sign` | Выработка подписи закрытым ключом |
| `keys/verify` | Проверка подписи открытым ключом |
| `signature/ed25519-sign`, `signature/ed25519-verify` | Схема, подписывающая сообщение сама, без отдельной хэш-суммы |
| `signature/ecdsa-sign`, `signature/ecdsa-verify` | Схема на кривой P-256 средствами библиотеки криптографии |
| `signature/rsa-sign`, `signature/rsa-verify` | Схема RSA: выработка на два порядка дороже проверки |
| `signature/gost-hash` | Хэш-функция ГОСТ Р 34.11-2012, считаемая своими силами. Мера её — пропускная способность, а не число оборотов |
| `signature/gost-sign`, `signature/gost-verify` | Схема ГОСТ Р 34.10-2012 на 256 разрядов, считаемая своими силами на своей длинной арифметике |
| `signature/gost512-sign`, `signature/gost512-verify` | То же на 512 разрядов. Сличение с предыдущей парой даёт цену удвоенной ширины счёта |
| `signature/fingerprint` | Снятие отпечатка открытого ключа |

## Что показали измерения

Числа рабочей машины (macOS ARM64, выпускная сборка) — среднее трёх прогонов.

### Удержание хвоста потока стоит около пяти сотых, а не кратной цены

Открытым вопросом решения 6.5 было: во сколько обходится лишний проход копирования при
потоковой расшифровке в режиме с проверкой подлинности, и окупится ли замена удержания
кольцевым буфером. Измерено в выпускной сборке:

| Сценарий | Пропускная способность |
|---|---|
| `stream/encode-1k` | 4.7 ГБ/с |
| `stream/decode-1k` | 4.3 ГБ/с |
| `stream/encode-64k` | 7.1 ГБ/с |
| `stream/decode-64k` | 6.0 ГБ/с |

Расхождение — 8% на килооктетных порциях. Крупные порции для этого сличения негодны:
`stream/decode-64k` гуляет от прогона к прогону втрое (2.3–6.6 ГБ/с), и разница режимов
в этом разбросе тонет. Кольцевой буфер снимет часть этих сотых ценой
второго вызова шифра на всякой порции, на самом ответственном пути модуля. Не окупается.

### Отладочная сборка на этом пути врёт в тринадцать раз

В отладочной сборке те же сценарии дают 3245 МиБ/с у шифрования и 183 МиБ/с у
расшифровки — разрыв в восемнадцать раз. Разрыв этот целиком её собственный: работа с
накопителем хвоста при отключённой оптимизации разворачивается в поэлементный перебор.
Проверено сличением режимов: гаммирование, хвоста не удерживающее, даёт в отладочной
сборке 1102 МиБ/с у шифрования и 1195 у расшифровки — то есть провал приходится ровно на
удержание и ровно на отладочную сборку.

**О стоимости этого пути судить по отладочной сборке нельзя.** Прочие показатели набора
между сборками расходятся в разы, этот — на порядок с лишним.

### Число отведений памяти одинаково на всех системах — и это следствие своей сборки

На девяти системах показатель совпадает **точно**: разовое шифрование — одно отведение на
операцию, кодирование BASE64 — одно, свёртка SHA-256 — два. Ни система, ни стандартная
библиотека, ни собиратель на него не влияют.

Прежняя редакция утверждала обратное — «три отведения у libc++ рабочей машины и одно на
стендах, BASE64 шесть и одно», — и это было свойством **не модуля, а замера**: числа
снимались стендом, связанным с системным OpenSSL, а разные его сборки отводят память
по-разному. AWH несёт свой BoringSSL, один и тот же на всех системах, и расхождению
взяться неоткуда.

Показатель этот, стало быть, ловит появление лишнего отведения в горячем пути и требует
точного порога, а не запаса.

### Вывод ключа стоит шесть с половиной миллисекунд

`stream/derive` даёт около 160 выводов в секунду, то есть 6.3 мс на вывод. Цена эта взята
намеренно — сто тысяч итераций защищают от перебора пароля (решение 7.8), — и потому ключ
удерживается между потоками (решение 3.7). Сличение с `stream/cycle`, дающим около трёх
миллионов оборотов в секунду, показывает разницу прямо: оборот потока на удержанном ключе
дешевле вывода в восемнадцать тысяч раз.

Это самый медленный сценарий набора на стендах: 18,2 вывода в секунду на худшей из девяти
машин против 164,7 у рабочей — разрыв в девять раз, самый крупный по набору.

### СНЯТО: «отпечаток держится разновидностью OpenSSL, а не машиной»

Прежняя редакция сообщала о расхождении `signature/fingerprint` между машинами **в
восемьсот раз** и объясняла его разновидностью системного OpenSSL: у 3.0 всякий вызов
`i2d_PUBKEY` разыскивает кодировщик через поставщика, у 3.6 этот путь исправлен.

Находка снята: **расхождения нет**. На девяти системах настоящей сборкой разброс
составляет 4,2 раза — 1 451 045 отпечатков в секунду на худшей машине против 6 155 437
на лучшей, — и это ровно разброс самих машин: подпись Ed25519 расходится там же в 4,8
раза.

Восьмисоткратный разрыв принадлежал стенду, связанному с СИСТЕМНЫМ OpenSSL, разновидности
которого на стендах разные. Продукт несёт свой BoringSSL, одинаковый всюду. Случай этот
стоит держать в памяти как образец: находка была подробной, объяснённой по механизму и
правдоподобной — и целиком принадлежала оснастке замера, а не измеряемому.

### Схема ГОСТ разогнана на порядок

Своя реализация ГОСТ Р 34.10-2012 разогнана Монтгомери, окном перебора и таблицей кратных
точки основания: подпись схемы на 256 разрядов идёт 8 500 в секунду против 751 до разгона,
хэш-функция — 205 МБ/с против 95. Подробности, цена каждой ступени порознь и сличение с
`gost-engine` — в [`COMPARISON.md`](COMPARISON.md).

Первая подпись схемой ГОСТ снимает таблицу кратных — 98 килооктетов на набор свойств
кривой, — оттого первый оборот сценария дороже последующих; на числах набора это не
сказывается, прогон идёт тысячами оборотов.

## Пороги

Пороги сняты **выпускной сборкой по самому медленному из восьми стендов** и держат к нему
двукратный запас: они ловят регрессию в разы, а не колебания планировщика и не разницу
самих машин.

Стенды прогона — восемь машин x86-64: Debian 12, Ubuntu 24.10, Fedora 44, Alpine 3.24,
NetBSD, DragonFly 6.4, OpenIndiana, Solaris 11.4. Рабочая машина — macOS ARM64.

Самым медленным оказывается **разный стенд у разных сценариев**, и это обычное дело:
поток и вывод ключа держит NetBSD, разовое шифрование коротких сообщений — DragonFly,
хэш-функцию ГОСТ и отпечаток — Solaris, схему на 512 разрядов — Ubuntu. Запас, посчитанный
от рабочей машины, валил бы прогон на стендах при полностью исправном модуле: она быстрее
самого медленного стенда впятеро и более, а на отпечатке — в восемьсот раз.

Измерения имеют заметный разброс от прогона к прогону, причём первый прогон всегда
медленнее последующих. Судить о правке по одному прогону нельзя.
