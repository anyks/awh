# IOCP: восстановление базиса и профиль CPU

Дата: 08.10.2026. Исходный снимок: `685f89257`, ветка `v5`.

## Итог этапа

- Базис AWH/libuv восстановлен; системные символы показали значимые затраты
  на страницы 64-КиБ буфера приёма, в том числе в стеке отправителя на loopback.
- Обход IOCP при синхронном успехе libuv даёт измеримый эффект, но не объясняет
  весь разрыв: его отключение снизило медиану скорости на 5,64 %.
- Приём AWH по 4 КиБ ускорил echo на 18,58 %, но снизил stream throughput
  на 49,08 %. Фиксированный лимит для основного кода отвергнут.
- Согласованный адаптивный приём перенесён в основной checkout: echo
  +16,54 %, CPU −14,43 %; stream −0,67 % при одинаковой медиане CPU.
  Семь регрессионных тестов и автономная проверка прошли; четыре мутации
  обнаружены. Реализация и инкапсуляция локальных объявлений теперь входят
  в HEAD `c9f62a454`; автономный probe также закоммичен в `4da45d467`.
- Профиль этого HEAD обновлён: AWH 24603,34 против libuv 44037,56 обменов/с.
  Эксперимент без зануления выходного массива IOCP не ускорил echo
  (−0,25%, CPU без изменения) и оставлен только на стенде.
- Выравнивание буфера по странице не ускорило обмен. Отдельное переключение
  обычного TCP на readiness + `recv` дало +25,23% echo и −20,37% CPU,
  выиграв все семь пар. TCP readiness принят в `fac0f8a1a`.
- Копия события внутри worker принята в `5784f194f`. Текущий backend
  повторно собран и проверен после оформления владельцем конструктора Worker:
  29/29 регрессий, пять smoke-проверок и оба отрицательных контроля прошли.
  Новый профиль подтверждает исчезновение основной heap-ветки dispatch;
  свежий повтор с libuv дал 27684,90 против 44166,49 обменов/с.
  Первый сравнительный профиль загрязнён фоновой нагрузкой и сохранён

## Метод проверки

1. Проверить код завершения сборки и предупреждения, дату и SHA-256 `net.exe`.
2. Запустить `datagram/single`, `datagram/multi` и `stream/throughput` с полными
   журналами и кодами завершения.
3. Снять `echo/single` отдельными процессами: один прогрев и семь измерений.
   Встроенный `--repeat` не использовать: часть сценариев кеширует результат
   в `static const` и не повторяет нагрузку.
4. Снять профиль CPU отдельным запуском. WPR и xperf установлены;
   начальная проверка `wpr -status` показала отсутствие записи.
   Наличие инструментов ещё не подтверждает успешный сбор профиля.
5. Только после профиля выбирать изменение и сравнивать с тем же базисом.
   Профилируемые запуски не включать в ряд измерений скорости.

Для xperf применимы события `PROC_THREAD+LOADER+PROFILE` и `-stackwalk Profile`.
Адреса MinGW следует сопоставлять с таблицей символов точного бинарного файла;
успешность раскрутки стеков и потери событий требуется проверить отдельно.
Справка Microsoft: [stackwalk](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/stackwalk),
[profile](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/xperf/profile).

Из разницы 6871 выборки на ядро пришлось 4476 (65,14 %), на пользовательский

Ближайший кадр AWH каждому sample назначается единожды; строки ниже

|---|---:|---:|

| `kernel::reconcile` | 2193 | 2004 |

Таким образом, первый предмет эксперимента — стоимость отправки, затем

определялись до module+RVA без PDB; уточнение по PDB приведено ниже.

## Уточнение по системным символам

Сохранённые ETL повторно выгружены с Microsoft PDB и локальным SymCache.
Первые выгрузки без символов сохранены. Данные относятся к тем же PID и
13980/7109 samples, новая нагрузка для этого анализа не запускалась.
Инструкция Microsoft: [поддержка символов](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/symbols).
Не разрешены до имени функции 297 samples AWH (2,124 %) и 55 libuv (0,774 %).

| Exclusive функция Windows | AWH | libuv |
|---|---:|---:|
| `MmUnlockPages` | 626 | 0 |
| `MiProbeLockFrame` | 463 | 0 |
| `MiFillSystemPtes` | 196 | 0 |
| `MiSetProbePagesAhead` | 142 | 0 |
| `MiProbeAndLockPrepare` | 67 | 0 |
| `MiProbeAndLockPages` | 59 | 0 |

Все 626 exclusive samples `MmUnlockPages` находятся в стеке завершения
ожидающего приёма: `IopfCompleteRequest` → `AfdTLCompleteBufferUserReceive`
→ `TcpSatisfyReceiveRequests` → loopback delivery → `AfdTLStartBufferedVcSend`.
Поэтому прежнюю формулировку «дорогая отправка» следует уточнить: отправитель
на loopback оплачивает в том числе завершение приёма другой стороны.
Это не доказательство самостоятельного дефекта `WSASend`.

Inclusive samples AWH: `AfdAllocateMdlChain` — 1060,
`MmProbeAndLockPages` — 1016, `MmUnlockPages` — 739. Эти числа перекрываются
по стеку и не складываются. Ветка `kernel::reconcile` содержит 1014 samples
под `MmProbeAndLockPages`. В libuv нулевой overlapped receive использует
другой путь завершения, без наблюдаемого page-lock/unlock.

В AWH полезная нагрузка echo — 64 байта, но `post::fetch` подаёт буфер
`pool::SIZE = AWH_EVENT_MAX_BUFFER_SIZE = 65536`. Уменьшение всего пула
недопустимо: UDP требует минимум 65527 байт. Следующий эксперимент ограничивает
только длину потокового `WSARecv`, сохраняя пул и остальные ветки.

Архив выгрузок на стенде: `system-symbol-analysis.tar.gz`.
Анализ: локальный `analyze_symbols.py`, `results/*-symbols-{analysis,nearest,detail}.json`.
Копии скриптов сохранены на стенде в `awh-iocp-analysis-tools.tar.gz`;
встроенный путь к каталогу результатов при переносе требуется изменить.

## Эксперимент с сигналом объекта сокета

Проверен только `FILE_SKIP_SET_EVENT_ON_HANDLE` (`0x2`) на подтверждённых
через `SO_TYPE` сокетах. Завершения IOCP не отключаются; режим
`FILE_SKIP_COMPLETION_PORT_ON_SUCCESS` (`0x1`) не используется. Microsoft
указывает, что явно заданное `OVERLAPPED.hEvent` сохраняет сигнал:
[SetFileCompletionNotificationModes](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setfilecompletionnotificationmodes).

Гипотеза: автоматическая сигнализация самого объекта сокета добавляет стоимость
kernel path. В libuv устанавливаются оба названных режима; это основание
проверить 0x2, а не доказательство его выигрыша.

Исходный бинарник сохранён в `baseline/net.exe`, вариант собран только
в staging из `iocp-event-candidate.cpp`. Успешная установка режима подтверждается
сообщением `IOCP_EVENT_SKIP_ENABLED` при привязке, вне горячего пути обмена.
Постоянной функциональной правки в репозитории пока нет. Для включения в
основной код недостаточно замера: режим необратим, поэтому отдельно требуются
проверки snapshot/restore, передачи сокета другому процессу и явного hEvent.

После одного прогрева каждой сборки выполнены семь чередующихся пар
`echo/single`, по 100000 обменов в каждом процессе. Это отдельный ряд:
его исходная AWH сравнивается с вариантом, а не с прежними замерами libuv.

| Метрика | Исходная AWH | Вариант 0x2 |
|---|---:|---:|
| Медиана, обменов/с | 21717,22 | 22092,69 |
| Минимум — максимум, обменов/с | 21513,78 — 22710,69 | 21099,57 — 22734,97 |
| Медиана CPU процесса, с | 4,640625 | 4,562500 |

Устойчивый выигрыш не установлен, поэтому режим в основной код не переносится.

## Адаптивный потоковый приём

Адаптивная реализация согласована отдельно после результатов фиксированных 4 КиБ.
Политика хранится в существующей `kernel::registry_t`:

- Начальный размер 4096; полный положительный приём увеличивает следующий
  запрос вчетверо, до `min(65536, pool::SIZE)`.
- Приём не более четверти поданного размера увеличивает счётчик; после
  16 таких завершений подряд длина уменьшается вчетверо, минимум 4096.
  Промежуточный по размеру приём сбрасывает эту последовательность.
- Только STREAM/TCP на IPv4/IPv6 участвует в адаптации. UDP/raw/metadata,
  именованные каналы, другие протоколы и сам пул не меняются.
- В inflight-записи сохраняются фактическая длина и владелец операции;
  копии снимаются до освобождения slot. Обучение проходит после отсева
  отмены, до сброса токена подписки, с проверкой token/sock/owner/длины.
- Ошибка и EOF не обучают. `forget` и смена владельца ADD/ENABLE сбрасывают
  состояние. Обычное перевзведение его сохраняет. Формат snapshot не меняется.

## Следующий шаг

TCP readiness принят владельцем в `fac0f8a1a`, worker и постоянный
lifetime-пробник — в `5784f194f`. Свежие парные серии AWH/libuv выполнены;
после обнаружения чужой нагрузки сделан независимый повтор. Он сохранил
разрыв, а профиль показал распределённые расходы: 1788 из 3282 лишних
samples приходятся на пользовательский режим (54,48%). Большая общая
ветка отправки сама по себе не означает устранимый расход отправителя.

Следующий узкий этап — диагностическая карта оборота `IO::poll`:
частота `poll`/`submit`, распределение `received`, число READ/WRITE/timer
и fallback dispatch, реальные обращения к часам, registry и двум точкам
lock. Адреса runtime уже привязаны к точному EXE; для частот предложена
отдельная staging-сборка со счётчиками и одним итоговым выводом, без часов
вокруг каждого callback. Этот инструментированный код пока не создавался.

## Локализация четырёх выделений на echo-обмен

`IO::poll` захватывает `this` и копию `change::record_t` в `std::function`.
На измеренном Win64 record занимает 32 байта, захват — 40, что не помещается
во встроенный буфер libstdc++. В точном базисе `8dbeaed53` disassembly
подтверждает `mov $0x28,%ecx` по `0x1400d0c51`, вызов `operator new` по
`0x1400d0c94`, сохранение полей record/this и затем `fibers::run`.
Перемещение функции в `worker->job` второго выделения не создаёт;
освобождение происходит после возврата callback в `fibers::body`.

Два RECV и два SEND полного echo превращаются в четыре READ/WRITE события,
каждое проходит этот dispatch. Это согласуется с измеренными 400000
выделений на 100000 обменов; отдельный динамический счётчик только этого
callsite не ставился. Профиль прежнего HEAD также показывает allocation
и освобождение этой лямбды, но не определяет возможный выигрыш её устранения.

Возможный следующий опыт — хранить record по значению в worker, передавая
ему малую лямбду с `this`. Ссылку на запись текущей пачки брать нельзя:
волокно вправе заснуть, а следующий `poll` перезапишет массив. До такого
опыта нужны целевые проверки сохранности record через yield, исчерпания
64 worker с fallback и возврата после `deinitialize` из callback.
Существующий `IoPollingRunsInsideFiberTest` проверяет наличие fiber у
простого таймера, но не yield. Тест offload через TAP зависит от окружения
и не покрывает сохранность сетевого record. Реализация worker не менялась.

## TCP readiness вместо приёма данных через IOCP

Отдельный кандидат построен из того же `8dbeaed53`, без выравнивания.
Единственное функциональное изменение в `kernel::reconcile`:
`suitable` → `(suitable && !adaptive)` в условии вызова `post::fetch`.
Признак `adaptive` ограничивает его потоковым TCP IPv4/IPv6 у PEER/CLIENT,

## Копия события в worker вместо большого захвата лямбды

Опыт выполнен поверх точного `fac0f8a1a`: его backend SHA-256
`c4b3f8c22a623315f054eba833c3302afbf1842b5f1a80023468b1fd242657ed`
совпадает с итоговой readiness-сборкой. Baseline executable — сохранённый
`final-readiness/net.exe`, SHA-256
`90ebec74aa98eecde57f570dc3e6f5920bd8b67fb88c1f7b2d2e065ae3e58ab5`.
Основной C++ в ходе этого опыта не изменялся.

В стендовом кандидате внутренний `fibers::worker_t` хранит `record_t`
по значению, а его job принимает запись по ссылке. `fibers::run` копирует
запись до `resume`; лямбда `IO::poll` захватывает только `this`. Оба таймерных
callback принимают неиспользуемую запись. Публичный API волокон, момент
первого входа, `busy`, предел 64, thread-local пул, `clear` и прямой fallback
сохранены. Поля записи не владеют `node`: его удержание остаётся у прежнего
`local::guard_t`. Сам объект `IO` по-прежнему обязан жить до конца callback.

Кандидат source SHA-256:
`3840e9b62d01b94571732df8afd420a7812fa544bc5a08c50c89c7cb4b74903b`;
benchmark executable:
`b6a1b0f88153ce95f969b626a037c80171c9ba48442b782a655f6f61f564de7f`.
Сборка backend и три линковки публичных тестов прошли без предупреждений.
Direct-include пробник сохраняет прежнее предупреждение `-Wsubobject-linkage`
у `io::Origin::keys`; оно отмечено отдельно от чистой сборки backend.

Автономный пробник включает настоящий backend и проверяет:

- все поля записи до/после `yield`, перезапись исходной записи и 128 чужих dispatch;
- 64 одновременно занятых worker, отказ 65-й работы без её исполнения,
  настоящий таймерный fallback через `IO::poll` и независимые записи при
  пробуждении всех 64 worker в обратном порядке;
- сохранение busy worker при `clear`, `deinitialize()` из callback, уступку
  после разбора движка, возврат, очистку пула и повторную инициализацию с 16 poll.

Исправный probe завершился с exit0. Мутация общей записи вместо отдельных
worker-копий отказала с exit1 на `record survives yield and overwrite`;
мутация преждевременного `busy=false` — с exit1 на
`suspended worker remains busy`. Проверки действуют при NDEBUG.
Lifetime/teardown проверяются прямым вызовом настоящего `fibers::run`,
а через `IO::poll` — timer fallback. Пробник отдельно не доказывает lifetime
сетевого node guard или передачу сетевой записи самим `IO::poll` через yield.

## Частоты одного оборота IOCP: отдельная диагностическая сборка

На Windows-стенде выполнены три независимых запуска `net/io/echo/single`:

окне — 0. Скорость диагностической сборки не сравнивается с обычной.

| Чтение готового snapshot через `timer::now` | 200000 | 2 |
| `subscription` / поиск в registry внутри `flush` | 600000 / 200000 | 6 / 2 |
| `flush` / `reconcile` | 200000 / 200000 | 2 / 2 |
| Вход в lock перед ожиданием | 200000 | 2 |
| Подача readiness / SEND | 200000 / 200000 | 2 / 2 |

Каждый успешный забор GQCSEx возвращал ровно две записи; движок также
видел пачки по две. Все ожидания запрашивались с `INFINITE`: это параметр
вызова, а не доказательство фактического сна. Пустых пакетов, timeout,
ошибок, wake entries, остатков прошлой пачки и повторной подачи не было.
Работы simple/difficult timer, прямого fallback, создания новых workers,
`now` без snapshot и второго lock для `triggered` в этом окне тоже не было.
Все измеренные поиски registry успешны. Два `timer::release` на оборот
соответствуют существующим границам перед ожиданием и в конце оборота;
само количество не доказывает их избыточность.

Счётчики накопительные, принадлежат потоку ОС; begin/end снимают разность
после прогрева и при завершении измеряемых обменов. Печать выполняется
после выхода из цикла `poll`, до `collect/deinitialize`. Внутри горячего
пути не добавлены часы, атомики или явные выделения памяти. Границы лежат
в callback и могут пересекать первый/последний оборот; это частоты событий
в окне, а не универсальные равенства входов и выходов. Инструментация может
влиять на планирование и размер пакетов. Данные относятся только к этим
запускам single; переносить их на multi/stream или считать оценкой цены
функций нельзя. `timestamp` здесь — вызов helper, а не счётчик QPC.

Проверена цепочка исходник → объект → библиотека → EXE → отчёт. В копиях
`libawh.a` из 717 членов изменён только `iocp.cpp_55.obj`; в benchmark-архиве
из 10 членов — только `echo.cpp.obj`. Остальные payload побайтово совпали.
Использованы исходные Release flags и includes; у benchmark опущены только
два флага подавления предупреждений. Путь библиотеки в linker response
заменён на диагностическую копию. Идентичность объектов проверяется через
чтение файлов / `ar x`: `ar p` в этом MinGW искажает бинарный stdout и для
такой проверки непригоден.

Отрицательный контроль убирает только прибавление `GQCS` в отдельном
исходнике. Benchmark по-прежнему завершился с кодом 0 и выполнил 100000
обменов; валидатор завершился с кодом 1 по четырём ожидаемым нарушениям
обязательного счётчика и его балансов. У трёх положительных отчётов код
валидатора 0. Контроль доказывает чувствительность пути GQCS, а не каждого
из остальных 68 счётчиков. Незавершённый begin/end валидатор отклоняет;
сам отчёт при незавершённом окне не вычисляет unsigned-разность снимков.

WRITE dispatch нельзя считать лишним из-за отсутствия write-callback
в echo. SEND completion сохраняет результат в `drain`; `io::write` затем
снимает подтверждённые байты, обслуживает callbacks/таймауты и продолжает
оставшийся хвост. Пропуск этого пути или перенос очистки на следующий READ
нарушит контракт. Прямой вызов без worker требует отдельного доказательства
отсутствия всех достижимых callbacks, включая status/available/source,
а также ошибок, частичного SEND и ограничений; такой fast path не внедрён.

Следующий предлагаемый эксперимент уже по области изменения: сохранить
`std::this_thread::get_id()` один раз в `thread_local`, но присваивать
poll-owner на каждом входе `IO::poll`, сохранив перенос опроса между потоками
и сбросы состояния. Сейчас этот вызов выполняется дважды на обмен.
Ожидаемый резерв невелик: в повторном ETW для thread-id/helper было 41
exclusive sample из 10146; это не полная стоимость ветки. Стоимость доступа
к TLS может убрать выигрыш. Нужны отдельные A/B без диагностики и проверка
переноса потока; производственного изменения пока нет.
