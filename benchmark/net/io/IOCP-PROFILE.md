Дата: 08.10.2026. Исходный снимок: `685f89257`, ветка `v5`.

Уточнение условий сравнения, 09.10.2026: все новые замеры AWH против

## Итог этапа

- Базис AWH/libuv восстановлен; системные символы показали значимые затраты
  на страницы 64-КиБ буфера приёма, в том числе в стеке отправителя на loopback.
- Обход IOCP при синхронном успехе libuv даёт измеримый эффект, но не объясняет
  весь разрыв: его отключение снизило медиану скорости на 5,64 %.
- Приём AWH по 4 КиБ ускорил echo на 18,58 %, но снизил stream throughput
  на 49,08 %. Фиксированный лимит для основного кода отвергнут.
- Согласованный адаптивный приём перенесён в основной checkout: echo
  +16,54 %, CPU −14,43 %; stream −0,67 % при одинаковой медиане CPU.
  Семь регрессионных тестов и автономная проверка прошли; четыре мутации
  обнаружены. Реализация и инкапсуляция локальных объявлений теперь входят
  в HEAD `c9f62a454`; автономный probe также закоммичен в `4da45d467`.
- Профиль этого HEAD обновлён: AWH 24603,34 против libuv 44037,56 обменов/с.
  Эксперимент без зануления выходного массива IOCP не ускорил echo
  (−0,25%, CPU без изменения) и оставлен только на стенде.
- Выравнивание буфера по странице не ускорило обмен. Отдельное переключение
  обычного TCP на readiness + `recv` дало +25,23% echo и −20,37% CPU,
  выиграв все семь пар. TCP readiness принят в `fac0f8a1a`.
- Копия события внутри worker принята в `5784f194f`. Текущий backend
  повторно собран и проверен после оформления владельцем конструктора Worker:
  29/29 регрессий, пять smoke-проверок и оба отрицательных контроля прошли.
  Новый профиль подтверждает исчезновение основной heap-ветки dispatch;
  свежий повтор с libuv дал 27684,90 против 44166,49 обменов/с.
  Первый сравнительный профиль загрязнён фоновой нагрузкой и сохранён
  отдельно; повтор снят с существенно меньшим фоном.

## Метод проверки

1. Проверить код завершения сборки и предупреждения, дату и SHA-256 `net.exe`.
2. Запустить `datagram/single`, `datagram/multi` и `stream/throughput` с полными
   журналами и кодами завершения.
3. Снять `echo/single` отдельными процессами: один прогрев и семь измерений.
   Встроенный `--repeat` не использовать: часть сценариев кеширует результат
   в `static const` и не повторяет нагрузку.
4. Снять профиль CPU отдельным запуском. WPR и xperf установлены;
   начальная проверка `wpr -status` показала отсутствие записи.
   Наличие инструментов ещё не подтверждает успешный сбор профиля.
5. Только после профиля выбирать изменение и сравнивать с тем же базисом.
   Профилируемые запуски не включать в ряд измерений скорости.

Для xperf применимы события `PROC_THREAD+LOADER+PROFILE` и `-stackwalk Profile`.
Адреса MinGW следует сопоставлять с таблицей символов точного бинарного файла;
успешность раскрутки стеков и потери событий требуется проверить отдельно.
Справка Microsoft: [stackwalk](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/stackwalk),
[profile](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/xperf/profile).

## Уточнение по системным символам

Сохранённые ETL повторно выгружены с Microsoft PDB и локальным SymCache.
Первые выгрузки без символов сохранены. Данные относятся к тем же PID и
13980/7109 samples, новая нагрузка для этого анализа не запускалась.
Инструкция Microsoft: [поддержка символов](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/symbols).
Не разрешены до имени функции 297 samples AWH (2,124 %) и 55 libuv (0,774 %).

| Exclusive функция Windows | AWH | libuv |
|---|---:|---:|
| `MmUnlockPages` | 626 | 0 |
| `MiProbeLockFrame` | 463 | 0 |
| `MiFillSystemPtes` | 196 | 0 |
| `MiSetProbePagesAhead` | 142 | 0 |
| `MiProbeAndLockPrepare` | 67 | 0 |
| `MiProbeAndLockPages` | 59 | 0 |

Все 626 exclusive samples `MmUnlockPages` находятся в стеке завершения
ожидающего приёма: `IopfCompleteRequest` → `AfdTLCompleteBufferUserReceive`
→ `TcpSatisfyReceiveRequests` → loopback delivery → `AfdTLStartBufferedVcSend`.
Поэтому прежнюю формулировку «дорогая отправка» следует уточнить: отправитель
на loopback оплачивает в том числе завершение приёма другой стороны.
Это не доказательство самостоятельного дефекта `WSASend`.

Inclusive samples AWH: `AfdAllocateMdlChain` — 1060,
`MmProbeAndLockPages` — 1016, `MmUnlockPages` — 739. Эти числа перекрываются
по стеку и не складываются. Ветка `kernel::reconcile` содержит 1014 samples
под `MmProbeAndLockPages`. В libuv нулевой overlapped receive использует
другой путь завершения, без наблюдаемого page-lock/unlock.

В AWH полезная нагрузка echo — 64 байта, но `post::fetch` подаёт буфер
`pool::SIZE = AWH_EVENT_MAX_BUFFER_SIZE = 65536`. Уменьшение всего пула
недопустимо: UDP требует минимум 65527 байт. Следующий эксперимент ограничивает
только длину потокового `WSARecv`, сохраняя пул и остальные ветки.

Архив выгрузок на стенде: `system-symbol-analysis.tar.gz`.
Анализ: локальный `analyze_symbols.py`, `results/*-symbols-{analysis,nearest,detail}.json`.
Копии скриптов сохранены на стенде в `awh-iocp-analysis-tools.tar.gz`;
встроенный путь к каталогу результатов при переносе требуется изменить.

## Эксперимент с сигналом объекта сокета

Проверен только `FILE_SKIP_SET_EVENT_ON_HANDLE` (`0x2`) на подтверждённых
через `SO_TYPE` сокетах. Завершения IOCP не отключаются; режим
`FILE_SKIP_COMPLETION_PORT_ON_SUCCESS` (`0x1`) не используется. Microsoft
указывает, что явно заданное `OVERLAPPED.hEvent` сохраняет сигнал:
[SetFileCompletionNotificationModes](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setfilecompletionnotificationmodes).

Гипотеза: автоматическая сигнализация самого объекта сокета добавляет стоимость
kernel path. В libuv устанавливаются оба названных режима; это основание
проверить 0x2, а не доказательство его выигрыша.

Исходный бинарник сохранён в `baseline/net.exe`, вариант собран только
в staging из `iocp-event-candidate.cpp`. Успешная установка режима подтверждается
сообщением `IOCP_EVENT_SKIP_ENABLED` при привязке, вне горячего пути обмена.
Постоянной функциональной правки в репозитории пока нет. Для включения в
основной код недостаточно замера: режим необратим, поэтому отдельно требуются
проверки snapshot/restore, передачи сокета другому процессу и явного hEvent.

После одного прогрева каждой сборки выполнены семь чередующихся пар
`echo/single`, по 100000 обменов в каждом процессе. Это отдельный ряд:
его исходная AWH сравнивается с вариантом, а не с прежними замерами libuv.

| Метрика | Исходная AWH | Вариант 0x2 |
|---|---:|---:|
| Медиана, обменов/с | 21717,22 | 22092,69 |
| Минимум — максимум, обменов/с | 21513,78 — 22710,69 | 21099,57 — 22734,97 |
| Медиана CPU процесса, с | 4,640625 | 4,562500 |

Разница медиан скорости +1,73 %, но в отдельных парах изменение составило
−4,95 %, +2,64 %, +5,68 %, +2,58 %, −0,29 %, −2,84 % и +2,06 %.
Четыре пары быстрее, три медленнее; диапазоны сильно перекрываются.
Устойчивый выигрыш не установлен, поэтому режим в основной код не переносится.
Это не доказательство нулевого эффекта; для небольшого эффекта нужен более
точный отдельный эксперимент. Диагностическое логирование также остаётся
частью экспериментального бинарника и полного CPU процесса.

Все 16 echo-процессов, включая прогрев, завершились с кодом 0, без таймаутов
и stderr. В каждом из восьми запусков варианта зафиксированы три успешные
установки режима: слушатель, клиент и принятый сокет. На варианте также

## Адаптивный потоковый приём

Адаптивная реализация согласована отдельно после результатов фиксированных 4 КиБ.
Политика хранится в существующей `kernel::registry_t`:

- Начальный размер 4096; полный положительный приём увеличивает следующий
  запрос вчетверо, до `min(65536, pool::SIZE)`.
- Приём не более четверти поданного размера увеличивает счётчик; после
  16 таких завершений подряд длина уменьшается вчетверо, минимум 4096.
  Промежуточный по размеру приём сбрасывает эту последовательность.
- Только STREAM/TCP на IPv4/IPv6 участвует в адаптации. UDP/raw/metadata,
  именованные каналы, другие протоколы и сам пул не меняются.
- В inflight-записи сохраняются фактическая длина и владелец операции;
  копии снимаются до освобождения slot. Обучение проходит после отсева
  отмены, до сброса токена подписки, с проверкой token/sock/owner/длины.
- Ошибка и EOF не обучают. `forget` и смена владельца ADD/ENABLE сбрасывают
  состояние. Обычное перевзведение его сохраняет. Формат snapshot не меняется.

## Локализация четырёх выделений на echo-обмен

`IO::poll` захватывает `this` и копию `change::record_t` в `std::function`.
На измеренном Win64 record занимает 32 байта, захват — 40, что не помещается
во встроенный буфер libstdc++. В точном базисе `8dbeaed53` disassembly
подтверждает `mov $0x28,%ecx` по `0x1400d0c51`, вызов `operator new` по
`0x1400d0c94`, сохранение полей record/this и затем `fibers::run`.
Перемещение функции в `worker->job` второго выделения не создаёт;
освобождение происходит после возврата callback в `fibers::body`.

Два RECV и два SEND полного echo превращаются в четыре READ/WRITE события,
каждое проходит этот dispatch. Это согласуется с измеренными 400000
выделений на 100000 обменов; отдельный динамический счётчик только этого
callsite не ставился. Профиль прежнего HEAD также показывает allocation
и освобождение этой лямбды, но не определяет возможный выигрыш её устранения.

Возможный следующий опыт — хранить record по значению в worker, передавая
ему малую лямбду с `this`. Ссылку на запись текущей пачки брать нельзя:
волокно вправе заснуть, а следующий `poll` перезапишет массив. До такого

простого таймера, но не yield. Тест offload через TAP зависит от окружения

## Копия события в worker вместо большого захвата лямбды

Опыт выполнен поверх точного `fac0f8a1a`: его backend SHA-256
`c4b3f8c22a623315f054eba833c3302afbf1842b5f1a80023468b1fd242657ed`
совпадает с итоговой readiness-сборкой. Baseline executable — сохранённый
`final-readiness/net.exe`, SHA-256
`90ebec74aa98eecde57f570dc3e6f5920bd8b67fb88c1f7b2d2e065ae3e58ab5`.
Основной C++ в ходе этого опыта не изменялся.

В стендовом кандидате внутренний `fibers::worker_t` хранит `record_t`
по значению, а его job принимает запись по ссылке. `fibers::run` копирует
запись до `resume`; лямбда `IO::poll` захватывает только `this`. Оба таймерных
callback принимают неиспользуемую запись. Публичный API волокон, момент
первого входа, `busy`, предел 64, thread-local пул, `clear` и прямой fallback
сохранены. Поля записи не владеют `node`: его удержание остаётся у прежнего
`local::guard_t`. Сам объект `IO` по-прежнему обязан жить до конца callback.

Кандидат source SHA-256:
`3840e9b62d01b94571732df8afd420a7812fa544bc5a08c50c89c7cb4b74903b`;
benchmark executable:
`b6a1b0f88153ce95f969b626a037c80171c9ba48442b782a655f6f61f564de7f`.
Сборка backend и три линковки публичных тестов прошли без предупреждений.
Direct-include пробник сохраняет прежнее предупреждение `-Wsubobject-linkage`
у `io::Origin::keys`; оно отмечено отдельно от чистой сборки backend.

Автономный пробник включает настоящий backend и проверяет:

- все поля записи до/после `yield`, перезапись исходной записи и 128 чужих dispatch;
- 64 одновременно занятых worker, отказ 65-й работы без её исполнения,
  настоящий таймерный fallback через `IO::poll` и независимые записи при
  пробуждении всех 64 worker в обратном порядке;
- сохранение busy worker при `clear`, `deinitialize()` из callback, уступку
  после разбора движка, возврат, очистку пула и повторную инициализацию с 16 poll.

Исправный probe завершился с exit0. Мутация общей записи вместо отдельных
worker-копий отказала с exit1 на `record survives yield and overwrite`;
мутация преждевременного `busy=false` — с exit1 на
`suspended worker remains busy`. Проверки действуют при NDEBUG.
Lifetime/teardown проверяются прямым вызовом настоящего `fibers::run`,
а через `IO::poll` — timer fallback. Пробник отдельно не доказывает lifetime
сетевого node guard или передачу сетевой записи самим `IO::poll` через yield.

## Свежее сравнение текущего AWH с libuv

Текущий backend `933b95bf…`, object/library/EXE из `post-worker-profile`

## Частоты одного оборота IOCP: отдельная диагностическая сборка

На Windows-стенде выполнены три независимых запуска `net/io/echo/single`:
8 прогревочных и 100000 измеренных обменов по 64 байта в каждую сторону,
одно соединение, один поток опроса. Во всех трёх запусках все 69 счётчиков
совпали. Процессы завершились с кодом 0, stderr пуст, выделений в измеряемом
окне — 0. Скорость диагностической сборки не сравнивается с обычной.

| Работа | За 100000 обменов | На обмен |
|---|---:|---:|
| Входы `IO::poll` / вызовы GQCSEx | 200000 / 200000 | 2 / 2 |
| Записи Windows completion | 400000 | 4 |
| READ / WRITE dispatch | 200000 / 200000 | 2 / 2 |
| Повторное использование / запуск worker | 400000 / 400000 | 4 / 4 |
| `timer::capture` / `timestamp` | 200000 / 200000 | 2 / 2 |
| Чтение готового snapshot через `timer::now` | 200000 | 2 |
| `subscription` / поиск в registry внутри `flush` | 600000 / 200000 | 6 / 2 |
| `flush` / `reconcile` | 200000 / 200000 | 2 / 2 |
| Вход в lock перед ожиданием | 200000 | 2 |
| Подача readiness / SEND | 200000 / 200000 | 2 / 2 |

Каждый успешный забор GQCSEx возвращал ровно две записи; движок также
видел пачки по две. Все ожидания запрашивались с `INFINITE`: это параметр
вызова, а не доказательство фактического сна. Пустых пакетов, timeout,
ошибок, wake entries, остатков прошлой пачки и повторной подачи не было.
Работы simple/difficult timer, прямого fallback, создания новых workers,
`now` без snapshot и второго lock для `triggered` в этом окне тоже не было.
Все измеренные поиски registry успешны. Два `timer::release` на оборот
соответствуют существующим границам перед ожиданием и в конце оборота;
само количество не доказывает их избыточность.

Счётчики накопительные, принадлежат потоку ОС; begin/end снимают разность
после прогрева и при завершении измеряемых обменов. Печать выполняется
после выхода из цикла `poll`, до `collect/deinitialize`. Внутри горячего
пути не добавлены часы, атомики или явные выделения памяти. Границы лежат
в callback и могут пересекать первый/последний оборот; это частоты событий
в окне, а не универсальные равенства входов и выходов. Инструментация может
влиять на планирование и размер пакетов. Данные относятся только к этим
запускам single; переносить их на multi/stream или считать оценкой цены
функций нельзя. `timestamp` здесь — вызов helper, а не счётчик QPC.

Проверена цепочка исходник → объект → библиотека → EXE → отчёт. В копиях
`libawh.a` из 717 членов изменён только `iocp.cpp_55.obj`; в benchmark-архиве
из 10 членов — только `echo.cpp.obj`. Остальные payload побайтово совпали.
Использованы исходные Release flags и includes; у benchmark опущены только
два флага подавления предупреждений. Путь библиотеки в linker response
заменён на диагностическую копию. Идентичность объектов проверяется через
чтение файлов / `ar x`: `ar p` в этом MinGW искажает бинарный stdout и для
такой проверки непригоден.

Отрицательный контроль убирает только прибавление `GQCS` в отдельном
исходнике. Benchmark по-прежнему завершился с кодом 0 и выполнил 100000
обменов; валидатор завершился с кодом 1 по четырём ожидаемым нарушениям
обязательного счётчика и его балансов. У трёх положительных отчётов код
валидатора 0. Контроль доказывает чувствительность пути GQCS, а не каждого
из остальных 68 счётчиков. Незавершённый begin/end валидатор отклоняет;
сам отчёт при незавершённом окне не вычисляет unsigned-разность снимков.

WRITE dispatch нельзя считать лишним из-за отсутствия write-callback
в echo. SEND completion сохраняет результат в `drain`; `io::write` затем
снимает подтверждённые байты, обслуживает callbacks/таймауты и продолжает
оставшийся хвост. Пропуск этого пути или перенос очистки на следующий READ
нарушит контракт. Прямой вызов без worker требует отдельного доказательства
отсутствия всех достижимых callbacks, включая status/available/source,
а также ошибок, частичного SEND и ограничений; такой fast path не внедрён.

По результатам диагностики был предложен более узкий эксперимент: сохранить
`std::this_thread::get_id()` один раз в `thread_local`, но присваивать
poll-owner на каждом входе `IO::poll`, сохранив перенос опроса между потоками
и сбросы состояния. Сейчас этот вызов выполняется дважды на обмен.
Ожидаемый резерв невелик: в повторном ETW для thread-id/helper было 41
exclusive sample из 10146; это не полная стоимость ветки. Стоимость доступа
к TLS может убрать выигрыш. Нужны отдельные A/B без диагностики и проверка
переноса потока; производственного изменения пока нет.

`933b95bfa7952e15fcf723fce94381d3037ea1ccfa4d10eb159cb0cd9cca8396`.
Исходные benchmark, библиотека и EXE на стенде также не изменились.
За время работы HEAD основного checkout перешёл с `2a0aca0d4` на

возврата `+0x3a`). Кандидат реально меняет горячий путь, но это само по себе
не доказывает выигрыш скорости.

Корректность проверена отдельно:

- 33 регрессионных теста: 30 public, 2 TLS и 1 IPv6, без пропусков;
- 5 smoke: echo single/multi, stream, datagram single/multi;
- два положительных direct-include probe — исходник и кандидат;
- две мутации: общий `static` вместо `thread_local` пойман на `owner B after A`,

повторную инициализацию и явный сброс owner/known. Затем прежний владелец
пинает новый поток, ожидающий в настоящем GQCS. Отдельный handshake после
короткого `poll(0)` привязывает пинок именно к следующему блокирующему poll;
предел 1500 мс не позволяет таймауту 5000 мс выдать себя за пробуждение.

## A/A: путь EXE и фактические адреса загрузки, 2026-10-09

Небольшой выигрыш кеша thread ID остаётся **неподтверждённым**.
Повтор с записью адресов загрузки показал изменение знака A/A после
копирования EXE, различия побайтово одинаковых копий и остаточную разницу
даже у одного файла по одному пути. Из этих данных нельзя приписать всю
причину одному ASLR или считать 1–1,5% доказанным эффектом оптимизации.

Обозначения: A — прежний `post-worker-profile/net.exe` с SHA `6f66c65e…`,
C — неизменённый backend, повторно собранный в `thread-id/control/net.exe`
с SHA `fc6b9a9f…`. Оба исторических файла сохранены. Побайтовый аудит нашёл
ровно 17 отличающихся байт в трёх диапазонах:

- offset 136, 3 байта — COFF timestamp;
- offset 216, 2 байта — PE checksum;
- offset 3677138, 12 байт — `iocp.cpp` / `baseline.cpp` в таблице символов.

Все диапазоны вне raw-секций; все 19 секций совпадают вместе с RVA,
размерами и characteristics. Размер обоих файлов — 6271061 байт,
предпочтительная база `0x140000000`, `DllCharacteristics=0x160`.
Полные хеши, заголовки и диапазоны сохранены в `pe-file-audit.json` архива.
Метаданные не патчились; системные настройки ASLR и безопасности не менялись.

- Исторический A загружался в `0x00007ff6142b0000`, C — в

  фактических баз наблюдалось только у `libwinpthread-1.dll`; во всех
  42 оставленных парах её база у двух процессов совпадала на момент снимка.

  и частота CPU не фиксировались. Снимок Modules сам занимает около 8 мс
  в оставленных запусках и является вмешательством в диагностику.

Ограничения фона сохранены явно, без выбора удачных пар. В паре 07 первого
ряда одинаковых копий появились `updater`/`TiWorker`; `right-07` сообщил
одно выделение. Следующая попытка `cross` была остановлена idle-проверкой
до запуска benchmark: updater потребил 2,03125 CPU-секунды за двухсекундное
окно. После его завершения начат отдельный `cross-02`; прежние результаты
не перезаписывались. В полном повторе одинаковых копий также были всплески
на парах 02/03: SearchApp, backgroundTaskHost, RuntimeBroker и другие службы.
Его +3,54% — диагностическое наблюдение, не оценка чистой цены ASLR.

Перед каждым рядом записаны idle-снимки; для каждой пары — дельты CPU
фоновых процессов. Они не видят уже завершившиеся процессы и гипервизор.
Последовательные ряды подвержены временному дрейфу, а путь, файловый объект
и база загрузки менялись совместно. Поэтому причинность ASLR отдельно не
установлена. Process CPU включает подготовку/завершение и не равен времени

## Проверка completion-контекста на libuv и условие allocator-OFF, 2026-10-09

По указанию владельца дальнейшие сравнения производительности AWH с
конкурентами выполняются с отключённым встроенным аллокатором. Штатная
настройка — `-DCMAKE_BUILD_ALLOCATOR=OFF`: CMake определяет
`AWH_ALLOC_DISABLED`, startup перестаёт вызывать `seize()`, явный `capture()`
возвращает false. `CMAKE_BUILD_ALLOCATOR_ACCOUNTING` и `MANGLE` не заменяют
этот режим. Сам код аллокатора остаётся в библиотеке; наличие частных
`__awh_alloc_*` символов на Windows не является проверкой отключения.

Сохранённый `awh-flags.txt` предыдущего AWH/libuv сравнения имеет пустой
`CXX_DEFINES`, без `AWH_ALLOC_DISABLED`. Его SHA-256 совпадает с прежним
manifest: `bd99582b7358193b3b61838bf1aca4611d3f742674eff75ae3417153cdc53928`.
В старом повторном ETW есть inclusive samples `Allocator::capture` (3),
`PECapture::apply` (2), `PECapture::acquire` (2): исполнялась попытка захвата.
Эти samples сами по себе не доказывают успешное возвращаемое значение.
Прежние числа сохраняются как исторические; они не переименованы в OFF.

Новый опыт проверяет механизм на двух сохранённых libuv 1.52.1 DLL и вообще
не запускает AWH. Использованы исключительно `libuv-{control,completion}/benchmarks`,
без диагностических счётчиков. Исходный сетевой diff прежнего опыта:
flags `0x3 → 0x2` и отсутствие установки `UV_HANDLE_SYNC_BYPASS_IOCP`.

## Неблокирующий send: самостоятельная проверка механизма (2026-10-09)

На Windows-стенде `forman@192.168.53.177` в двух случаях обычного
неблокирующего `send()` (IPv4/IPv6) SEND-пакетов IOCP не было. Оба контрольных
overlapped `WSASend` дали по одному SEND-пакету; независимое READ-уведомление
сохранилось во всех четырёх случаях.
Это самостоятельный Winsock-пробник без линковки AWH, а не измерение
производительности или готовая замена `drain::transmit`.

Мотивом проверки были 227 samples контекста completion в прежнем OFF-профиле:
109 на spinlock, 39 на `KeInsertQueueEx`, 16 на выделение mini-packet.
Это samples CPU, не число пакетов и не доля немедленно завершённых отправок.

Пробник владеет loopback TCP-сокетами; для каждого успешно устанавливает
`FIONBIO=1`. На обоих соединённых сокетах пустое чтение дополнительно
проверяется через `WSAEWOULDBLOCK`. Режим далее не меняется. `SetFileCompletionNotificationModes` не применяется.
Сначала ставится zero-byte `WSARecv` со стабильным OVERLAPPED, затем
отправляются 64 проверяемых байта. После проверки SEND-пакета/его отсутствия
peer отправляет ACK; проверяются точные OVERLAPPED, ключ, число байт READ
и сам ACK. Дополнительные пакеты проверяются ещё в течение 100 мс.

| Семейство | Отправка | SEND-пакеты | READ-пакеты | Данные / ACK |
|---|---|---:|---:|---|
| IPv4 | overlapped `WSASend` | 1 | 1 | 64 / 1 байт, точное совпадение |
| IPv4 | обычный `send` | 0 | 1 | 64 / 1 байт, точное совпадение |
| IPv6 | overlapped `WSASend` | 1 | 1 | 64 / 1 байт, точное совпадение |
| IPv6 | обычный `send` | 0 | 1 | 64 / 1 байт, точное совпадение |

Все четыре отправки завершились немедленно. Положительный процесс завершился
с exit 0. Мутация убирает OVERLAPPED из первой IPv4-отправки, сохраняя
проверку ожидаемого SEND-пакета: exit 1,
`missing-send-completion win32=258 wsa=258`. Это внутренний timeout ожидания
пакета, не срабатывание внешнего watchdog. Проверяющий скрипт дополнительно
отвергает подменённую причину отказа и запись с watchdog timeout.

### Граница применимости к AWH

Overlapped-сокет сам по себе не гарантирует неблокирующий режим:
это отдельное свойство, описанное в
[документации Microsoft](https://learn.microsoft.com/en-us/windows/win32/winsock/overlapped-i-o-and-event-objects-2).
Обычный `send()` допускает частичную отправку и `WSAEWOULDBLOCK`; результат
успешной отправки не является общей гарантией доставки —
[контракт send](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-send).

Benchmark AWH запрашивает `NO_IO_BLOCK`, но `drain::usable` проверяет порт,
поток и подписку, не фактический режим сокета. Публичные опции могут отключать
неблокирующий режим, а `SM_IO_BLOCK` временно включает блокировку.
Общая замена отправки по одному признаку IOCP поэтому недопустима.

Текущий AWH сначала сохраняет SEND token/armed и возвращает `EAGAIN`.
Обработка completion вызывает `drain::keep` и WRITE с `COMPLETED`;
повторная запись потребляет подтверждённое число байт, сдвигает очередь
и запускает связанные callbacks. Этот порядок необходимо сохранить.

Следующий отдельный эксперимент — локальная очередь результатов отправки
для принадлежащих движку plain TCP-сокетов с проверенным стабильным
неблокирующим режимом. До `send()` необходимо зарезервировать inflight slot
и место в очереди: после принятия байт ошибка выделения памяти не должна
терять результат или приводить к повторной отправке. Результат проходит
прежний разбор completion/WRITE на следующем обороте с сохранением token,
поколения и armed. Локальные результаты не должны портить текущую пачку,
допускать бесконечное ожидание IOCP или вытеснять реальные READ-события.

Положительная частичная отправка должна дать ровно один результат с её
числом байт; только `WSAEWOULDBLOCK` без отправленных байт допускает возврат
к прежнему overlapped-пути. Отмена, закрытие и повторное использование
дескриптора должны освобождать slot без доступа к уничтоженному узлу.
`kernel::triggered` создаёт USER, поэтому не заменяет WRITE-dispatch.

Интеграция пока не реализована. До замеров нужны принудительные partial/
would-block, повторная отправка до dispatch, close/cancel/reset, reuse,
границы очереди/пачки, READ/WRITE fairness и deinitialize. Пробник этих
контрактов не проверяет. Сравнения AWH с конкурентами и последующие парные
замеры выполняются с отключённым аллокатором; данный API-пробник не даёт
новых данных для аудита аллокатора.

## Локальные SEND-завершения: изолированный прототип AWH (2026-10-09)

Прототип прошёл 13 контрактных сценариев в настоящем AWH на Windows AMD64.
В рабочий `iocp.cpp` он не перенесён; скорость этим комплектом не измерялась.
Кандидат работает только с явно включённым диагностическим признаком,
собственными plain TCP-сокетами с установленным и неизменным `FIONBIO=1`
и на потоке опроса. Тип и стабильный режим сокета обеспечивает fixture;
helper кандидата самостоятельно их не определяет. Это проверка механизма,
а не готовая общая оптимизация.

Перед обычным `send()` резервируются inflight slot и место в локальной
очереди на 256 записей. Успех и терминальная ошибка проходят прежний
разбор completion; token, поколение и armed сохраняются до обработки.
Только would-block без принятых байт и заполненная очередь возвращают
отправку к прежнему overlapped-пути. Неразобранная пачка сохраняется;
при локальной очереди новый опрос не блокируется и оставляет место
нативным событиям, включая READ.

### Проверенные контракты

| Сценарий | Наблюдение |
|---|---|
| IPv4 / IPv6 | По 64 точных байта; положительный WRITE после poll, slot освобождён |
| Ограничение syscall до 7 байт | 64 байта, 10 локальных результатов, точный поток без дублирования |
| Повторный send до dispatch | Сохранён исходный token/armed; затем подтверждены все 128 байт |
| Отмена / destroy до dispatch | Положительных WRITE нет, slot освобождён |
| Повторное использование slot | Старое поколение не доставлено новому владельцу |
| Настоящий WSAEWOULDBLOCK | Подтверждены would-block и overlapped fallback; 32768 байт дошли без новых send |

В смешанной пачке наблюдались 239 локальных SEND и 16 нативных SEND;
это состав конкретной пачки, не квота и не показатель производительности.
Встречный READ доставлен в пределах 100 poll; общей гарантии отсутствия
голодания этот опыт не устанавливает.
Teardown в обоих случаях освободил запись через внутренний poll:
`released=1, discarded=0`. Принудительное выполнение резервного
`discardLocal` этими сценариями не доказано.

Штатный публичный `send()` вызывает WRITE(0) ещё до постановки в очередь.
Пробник учитывает эти уведомления отдельно от положительного подтверждения
байт. Первые версии fixture неверно требовали отсутствия любого inline WRITE
и исключительно `discarded++` при teardown; исходники, отказы и точные
исправления сохранены. Сам кандидат IOCP при этих исправлениях не менялся.

## Применимость локальных SEND к echo: отрицательный gate (2026-10-09)

Текущий прототип **не участвует в echo/single**: в B1 за 250000 обменов
выполнено 500000 штатных `WSASend`, а локальных результатов — ноль.
Контрольная отправка с тем же новым исходником backend успешно проходит
локальный путь. Это ограничение применимости кандидата, не измерение
выигрыша или проигрыша скорости. Timed-сборка и заранее подготовленная
матрица из 78 процессов не запускались.

На том же Windows AMD64-стенде использованы Release GCC 16.1.0 Rev6,
`AWH_ALLOC_DISABLED` и диагностические счётчики. A0/A1 — local OFF,
B1 — local ON; все три режима запускают один EXE, один сценарий,
64-байтный обмен на одном соединении, 8 обменов прогрева и 250000 учтённых
обменов. Изменение числа обменов сделано в staging-копии `echo.cpp`;
`--repeat` не использован, поскольку исходный benchmark кеширует результат.

Hook после первого прогревочного обмена получает точные ID клиента и
accepted, проверяет владельца, registry, порт и опции, успешно устанавливает
`FIONBIO=1` на обоих сокетах. В B1 устанавливаются два opt-in признака;
в A0/A1 выполняется такая же подготовка без их включения. Исходный
`localSendable` не менялся. Идентичность владельцев и признаки повторно
проверены до/после окна. Дополнительных hook-вызовов в измеряемом цикле нет.

| Режим | Native SEND в окне | Local attempts / queued / delivered | Native SEND прогрева |
|---|---:|---|---:|
| A0 | 500000 | 0 / 0 / 0 | 16 |
| A1 | 500000 | 0 / 0 / 0 | 16 |
| B1 | 500000 | 0 / 0 / 0 | 16 |

Остальные локальные счётчики также нулевые. B1 завершил окно обмена,
после чего диагностическая проверка остановила процесс с exit 1 и точной
причиной `candidate-unused-in-measured-window`; watchdog не срабатывал.
Классификация — `NO_APPLICABILITY`, `approved_for_timed=false`.
Диагностические строки длительности A0/A1 не используются для сравнения скорости.

Положительный контроль `immediate4` подтвердил 64 точных байта и
`queued=delivered=released=1`. Контроль `cancel` подтвердил отмену без
положительного WRITE. Пробник аллокатора подтвердил
`initialized_captured=false capture_result=false final_captured=false`.
Тем самым нулевой результат echo отделён от неисправности счётчиков
или отсутствия нужного backend в бинарнике.

### Причина и следующий кандидат

В точном staging `iocp.cpp` состояние `registered` и привязка `attached`
хранятся раздельно (строки 10968–10991). Завершение POLL/RECV снимает
`registered`, token и applied (79333–79343). READ callback выполняется
до повторного взведения TCP через `kernel::flush` следующего poll.
Его отправка доходит до `post::send`, но требование `registered=true`
в `localSendable` (11276) исключает локальный путь. Штатный `WSASend`
(10403–10404) этого условия не требует. Нативные счётчики согласуются
с этим разбором. Условие не ослаблялось ради получения измерений.

Следующий отдельный кандидат — отделить право SEND от активности
READ-ожидания, сохранив точного живого владельца node/registry/socket,
текущий порт, поток опроса, явный opt-in только собственных plain TCP
с неизменным неблокирующим режимом и сброс opt-in при forget/смене владельца.
`registered=false` встречается также при снятии подписки и закрытии;
одного удаления проверки недостаточно для доказательства безопасности.
До benchmark нужны actual READ callback → public send с точными байтами
и отложенным положительным WRITE, cancel/destroy/reuse именно при
`registered=false`, положительные контроли и мутации. Затем повторяется gate.
Этот следующий кандидат ещё не реализован.

## Исправление допуска SEND из READ-callback, 17.10.2026

**Исправлен изолированный прототип; диагностический gate — PASS.**
Предыдущий `NO_APPLICABILITY` от 09.10 остаётся достоверным результатом старого
кандидата. Рабочий IOCP не содержал этого прототипа и в этой правке не менялся.
Текущий HEAD при начале работы — `bd5ac544c16071603e2da1b4005cea552cdb1b09`;
имеющиеся незакоммиченные изменения рабочего backend сохранены.

`registered` обозначает активное ожидание READ: завершение снимает его перед
вызовом обработчика чтения. Право SEND теперь определяется явным допуском,
идентификатором живого владельца, совпадением узла/сокета/порта, потоком опроса,
состоянием узла, TCP-транспортом и неблокирующими опциями. `udata` не разыменовывается
для получения идентификатора: сначала выполняется поиск в таблице живых событий.
При forget и смене владельца идентификатор сбрасывается вместе с допуском.

Правка и новая регрессия находятся в
[experiments/local-send-fix-20261017](experiments/local-send-fix-20261017/README.md).
Patch предназначен для сохранённого прототипа, не для применения к рабочему IOCP.

На Windows x86-64 `.177` с отключённым аллокатором подтверждено:

- Пять сценариев настоящего READ при `registered=false`: send, cancel, destroy,
  generation, forget. Обычный send доставляет точные 64 байта и отложенный
  положительный WRITE; остальные сценарии не доставляют положительный WRITE.
- 12 прежних контролей прошли. Искусственный partial-cap не запускался:
  этот вариант прототипа уже не ограничивает длину системного send.
- Возврат старого registered-условия даёт exit=1 строго с
  `LOCAL_SEND_FAIL: read-callback-send-eligible`, без внешнего watchdog.
- По шесть публичных регрессий прошли на baseline и fixed:
  destroy-in-flight, queue-tail, client/accepted/datagram semi-blocking,
  deliver-before-hangup.
