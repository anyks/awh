# Средства сборки и проверки AWH

Каталог этот держит всё, что делается **вокруг** сборки: подготовку зависимостей,
слияние архивов, сквозные проверки модулей, сборку пакетов и вспомогательные приёмы
разработки. Сама сборка ведётся CMake из корня дерева.

Средства писаны для оболочки POSIX. Двойник для машин без MSYS2, на чистой оснастке
Microsoft Visual Studio, лежит в [`bat/`](../bat/README.md).

---

## С чего начинают

```sh
git submodule update --init --recursive
sh/build_third_party.sh
```

Первое собирает зависимости в `third_party/`, без них сборка AWH не настроится:
`cmake/FindDependence.cmake` ищет там `libdependence` и отвечает отказом, если её нет.

---

## Зависимости

| средство | что делает |
|---|---|
| `build_third_party.sh` | окружение и перебор сценариев `third_party/`; принимает `--clean`, `--reset`, `--update` |
| `third_party/NNN_*.sh` | по сценарию на зависимость, порядок задан числовой приставкой |
| `third_party/010_static.sh` | последний шаг: зовёт слияние всех собранных зависимостей в одну |
| `merge_static_libs.sh` | само слияние в `libdependence.a` (у MS Windows — `.lib`) |
| `patches/` | заплаты к исходникам зависимостей (`lizard`, `lzma`), накладываются сценариями |

Собираются десять: `boringssl`, `zlib`, `snappy`, `bz2`, `lz4`, `zstd`, `lzma`,
`brotli`, `density`, `lizard`.

**Версии задаются `Requirements.txt` в корне дерева**, по строке на зависимость:

```
zlib --version 1.3.1
bz2 --branch master
```

Принимаются `--version`, `--tag`, `--branch`, `--commit` и `--none`. Файла нет — каждая
зависимость берётся на версии, зашитой в её собственный сценарий. Это и есть место, где
версии меняют: править сценарии ради иной версии не нужно. Этим же файлом управляется и
сборка оснасткой Visual Studio (`bat/`) — список один на обе оснастки.

**Слияние однопоточное и с разбором архивов** — это устройство, а не недоделка:
архиватор POSIX принимает только объектные файлы, оттого чужие архивы приходится
разбирать и собирать заново. Прерванный на полпути архиватор оставляет рваный хвост,
причём счёт членов в таком архиве лжёт.

## Сборка библиотеки

| средство | что делает |
|---|---|
| `build_static_lib.sh` | присоединяет зависимости к собранной `libawh.a`, чтобы потребитель связывал ОДНУ библиотеку; зовётся CMake после сборки |

| `core_dump.sh` | права на снятие образа памяти у macOS; файл прав здесь только читается |

## Сквозные проверки

Каждая прогоняет всю цепочку, накопленную вокруг модуля, и **падает на первом же
расхождении**: набор проверок, ворошитель, сличение с эталоном.

| средство | предмет |
|---|---|
| `verify_codec_json.sh` | кодек JSON |
| `verify_codec_xml.sh` | кодек XML |
| `verify_http2.sh` | подмодуль HTTP/2 |
| `verify_http3.sh` | подмодуль HTTP/3 |
| `verify_performance.sh` | скорость против сохранённого эталона |

**Зачем проверка скорости отдельно от набора замеров.** Пороги замеров откалиброваны с
четырёхкратным запасом: они ловят падения на порядок и по устройству не способны
заметить просадку в десять-пятнадцать процентов. Именно такая однажды и прошла
незамеченной — принудительное встраивание одной посимвольной проверки было потеряно
появлением второго вызывающего, и стоило это 13 % разбора запросов. Проверка эта
закрывает как раз проценты.

| файл | что держит |
|---|---|
| `performance.baseline` | сохранённый эталон скорости |
| `performance.py` | сверка свежего замера с эталоном |
| `unicode.accepted` | принятые названия свойств Юникода для ворошителя выражений |

## Эталоны для сличения

Framework их не использует — они нужны, чтобы сличать **свой** разбор с чужим.

| средство | что собирает |
|---|---|
| `reference/idn.sh` | GNU libiconv и GNU libidn2 — эталон для `awh::charset` и `awh::idna` |
| `reference/pcre2.sh` | PCRE2 — эталон для `awh::regex` |
| `benchmark_party.sh` | заново заводит подмодули libev, libevent, libuv, boost и seastar — стороны сличения скорости сетевых движков |

**`benchmark_party.sh` их не собирает**, а лишь обновляет исходники: сносит подмодуль и
заводит заново с хранилища. Сборка каждой стороны ведётся своим порядком при самом
сличении.
