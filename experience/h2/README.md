# AWH HTTP/2 (h2) — собственная реализация протокола HTTP/2

Чистая C++17-реализация ядра HTTP/2 (RFC 9113) + HPACK (RFC 7541),
задуманная как замена зависимости от `nghttp2`.

Идея: **не порт C-кода nghttp2 один-в-один**, а чистая реализация в стиле
`experience/http` (zero-copy, конечный автомат, callback-API без накладных
расходов), где nghttp2 используется как **референс-учебник** — смотрим, как
там решены краевые случаи и защиты от атак, но архитектуру пишем заново на C++17
без C-инфраструктуры (`nghttp2_map`/`nghttp2_pq`/`nghttp2_queue`/memory pool),
заменяя её на `std::`-контейнеры и RAII.

> Лицензия nghttp2 — **MIT**. Читать, адаптировать и копировать таблицы-константы
> (Huffman, статическая таблица HPACK) можно при указании авторства.

## Дорожная карта (этапы)

Каждый этап завершается прогоном против `h2spec` и differential-теста против nghttp2.

- [x] **Этап 0. Каркас и типы.** Все enum'ы, константы, структуры фреймов.
- [x] **Этап 1. Framing-слой.** Разбор/сборка всех фреймов, валидация размеров.
- [x] **Этап 2. HPACK.** Huffman (таблица кодов из nghttp2, декодер написан заново),
      целочисленный/строковый кодек, динамическая таблица с вытеснением, лимит на
      размер списка (защита от bomb). Индексация кодера: полное совпадение → Indexed
      (§6.1), совпадение имени → Literal с инкрементальной индексацией (§6.2.1), новое
      имя → литерал + добавление в таблицу; таблицы кодера/декодера синхронны.
- [x] **Этап 3. Stream state machine.** Переходы `idle→open→half-closed→closed`,
      проверка допустимости фреймов по состоянию (DATA/HEADERS на idle/closed),
      правила идентификаторов потоков (чётность + строгая монотонность),
      трейлеры с обязательным END_STREAM.
- [x] **Этап 4. Flow control.** Окна соединения и потоков; `pump()` нарезает DATA по
      `min(окно_соединения, окно_потока, MAX_FRAME_SIZE)`; bounded `sendBuffer` с high/low-water
      и сигналом `onStreamWritable`; авто-`WINDOW_UPDATE` на приём; дельта окон при изменении
      `INITIAL_WINDOW_SIZE`; опциональный pull-провайдер тела; backpressure выходного буфера.
- [x] **Этап 5. Безопасность.** Token-bucket (как в `nghttp2_ratelim`) против Rapid Reset
      (CVE-2023-44487, лимит частоты RST_STREAM); лимиты размера блока заголовков и числа
      CONTINUATION-фреймов (flood 2024); rate-лимит SETTINGS/PING/пустых DATA; пополнение
      токенов по времени через `updateTime()`. Нарушение → GOAWAY с ENHANCE_YOUR_CALM.
- [x] **Этап 6. HTTP-семантика.** Валидация блока заголовков (RFC 9113 §8): псевдо-заголовки
      (`:method`/`:path`/`:scheme`/`:authority`/`:status`) обязаны идти до обычных и не
      повторяться; обязательный набор для запроса/ответа (плюс правила CONNECT: только
      `:authority`); имена — строго в нижнем регистре; запрет connection-specific заголовков
      (`Connection`/`Transfer-Encoding`/`Keep-Alive`/`Upgrade`/`Proxy-Connection`), `TE` только
      `trailers`; запрет псевдо-заголовков в трейлерах. Малформированный блок → потоковая ошибка
      RST_STREAM(PROTOCOL_ERROR), соединение остаётся живым. Референс — `nghttp2_http.c`.
- [x] **Этап 7. Server push (RFC 9113 §6.6/§8.4).** `submitPushPromise()` на сервере
      резервирует чётный поток (`reserved(local)`), кодирует обещанный запрос и шлёт
      PUSH_PROMISE на ассоциированном потоке клиента; ответ отправляется обычным
      `submitHeaders/submitData` (авто-переход `reserved(local)→half-closed(remote)`).
      Клиент принимает PUSH_PROMISE (`reserved(remote)`), декодирует обещанный запрос в
      общую HPACK-машину, отдаёт его через `onPushPromise()` + `onHeader()`; отказ — через
      `submitRstStream(promisedId, CANCEL)`. Учитывается `SETTINGS_ENABLE_PUSH`: при 0 сервер
      не пушит, а присланный пиром PUSH_PROMISE при нашем запрете — PROTOCOL_ERROR. Сервер,
      получивший PUSH_PROMISE, рвёт соединение (push шлёт только сервер). Малформированный
      обещанный запрос — потоковая ошибка RST_STREAM.

## Маппинг на файлы nghttp2 (`submodules/nghttp2/lib/`)

Что и как использовать из nghttp2 при работе над каждым компонентом:

### Копировать дословно (это данные из RFC, не логика)
- `nghttp2_hd_huffman_data.c` (~5000 строк) → таблица Huffman. **Не перепечатывать руками.**
- Статическая таблица HPACK (61 запись) — внутри `nghttp2_hd.c`.

### Портировать логику краевых случаев (тут «опыт 10 лет»)
- `nghttp2_hd.c` — bounds-check декодера HPACK, защита от decompression bomb.
- `nghttp2_session.c` — таблица переходов состояний потока, правила допустимости
  фреймов (самый плотный кусок, ~8000 строк — читать внимательно).
- `nghttp2_ratelim.c` — token-bucket лимиты против Rapid Reset / CONTINUATION flood.
- `nghttp2_http.c` — валидация HTTP-семантики и псевдо-заголовков.

### Писать заново на C++17 (C-инфраструктуру выкидываем)
- `nghttp2_map` / `nghttp2_pq` / `nghttp2_queue` → `std::unordered_map` /
  `std::priority_queue` / `std::deque`.
- `nghttp2_mem` (memory pool), `nghttp2_rcbuf` (refcounted buf) → RAII / `std::string` / `std::vector`.
- `nghttp2_buf` → `experience/http`-подход (zero-copy `string_view` + свой буфер).
- Callbacks-указатели → структура function-pointer'ов (как в `experience/http`).

### Можно НЕ реализовывать (упрощение свежей реализации)
- Приоритеты RFC 7540 (дерево зависимостей потоков) — **deprecated**. nghttp2 тащит
  их как legacy. Новый RFC 9218 опционален; на старте игнорируем (поле weight храним,
  но дерево не строим). Следовательно `sfparse.c` тоже не нужен.

## Сборка (CMake)

Сборка состоит из двух независимых частей: **ядро HTTP/2** (чистый C++17, без
зависимостей) и **транспортная интеграция поверх AWH** (опционально).

### 1. Ядро + тесты + демо

Никаких внешних зависимостей, собирается любым C++17-компилятором:

```bash
cd experience/h2
cmake -S . -B build
cmake --build build -j
ctest --test-dir build --output-on-failure   # юнит-тесты ядра
./build/h2-demo                               # демо разбора фреймов (без сети)
```

Цели: статическая библиотека `h2`, тест `h2-test` (`ctest`-цель `h2-unit`), демо `h2-demo`.

### 2. HTTP/2 поверх TCP-транспорта AWH (опция `H2_WITH_AWH`)

Собирает примеры реального сервера/клиента HTTP/2 (`experience/h2/awh/`),
подключённые к низкоуровневому транспорту AWH (`server_t` / `client_t`). Это
«h2c с прямым знанием»: preface шлётся сразу, без HTTP/1.1 Upgrade и без TLS.

Требования:

1. **Зависимости AWH** — в репозитории должен лежать собранный единый архив
   `third_party/lib/libdependence.a` и заголовки `third_party/include/*`. Если их
   нет, в корне AWH выполните:
   ```bash
   ./build_third_party.sh
   ```
2. **Компилятор.** Подходят AppleClang (по умолчанию на macOS) и GCC 13/14.
   GCC 15+ не годится: в libstdc++-15 ужесточена SFINAE-проверка
   `ostream::operator<<`, и часть логирующих шаблонов AWH под ним не собирается.
   Сама `libawh` собирается здесь из исходников в режиме `DEBUG_MODE` — как в
   штатной Debug-сборке AWH (релизные ветки кода AWH содержат компиляционные
   дефекты). Нужные различия диагностик по компиляторам CMake выставляет сам.

```bash
cd experience/h2
cmake -S . -B build-awh -DH2_WITH_AWH=ON      # AppleClang по умолчанию
# либо явный GCC 13/14:
# cmake -S . -B build-awh -DH2_WITH_AWH=ON -DCMAKE_CXX_COMPILER=g++-14
cmake --build build-awh -j
```

Запуск (в двух терминалах):

```bash
./build-awh/h2-awh-server      # слушает 127.0.0.1:2222
./build-awh/h2-awh-client      # шлёт GET / и печатает ответ
```

Клиент выводит ответ сервера: `:status: 200`, заголовки и тело
`Hello from AWH transport + own HTTP/2!`, после чего поток закрывается
(подтверждение полного round-trip HPACK + framing + flow control по сокету).

> Это «прямое знание» (preface сразу, без HTTP/1.1 Upgrade и без TLS), поэтому
> проверять сервер нужно именно этим клиентом, а не браузером.
>
> На платформах, отличных от macOS/BSD, опция `H2_WITH_AWH` пока не настроена
> (нужен соответствующий backend ввода-вывода AWH).

## Тестирование (план)

- **h2spec** — эталонный набор тестов соответствия RFC 9113.
- **Differential fuzzing против nghttp2**: один и тот же поток фреймов скармливаем
  своей реализации и nghttp2, сравниваем поведение/ошибки. Главный множитель надёжности.
- **h2load** — нагрузочное тестирование.
