## Конкретные ошибки в аналоге

Я реально попытался собрать `example.cpp` — компилятор выдал 17 ошибок. Разберу по категориям.

**1. Падает `static_assert` (фатально).**

```171:171:experience/http-2/http_parser.hpp
    static_assert(sizeof(context_t) <= 128, "context_t should fit in 2 cache lines");
```
В `context_t` лежит `char fold_buffer[8192]` (строки 166–167), поэтому реальный размер — **8320 байт**, а не «2 cache line». `Readme.md` утверждает «умещается в 2 cache lines» — это неправда. Структуру на 8 КБ нельзя дёшево копировать/ресетить, и это убивает заявленную cache-friendly идею.

**2. Дублирование определений `simd::*` (8 ошибок redefinition).**
`http_parser.hpp` заново определяет `is_token_char`, `is_hex_digit`, `is_digit`, `hex_to_nibble`, `find_crlf`, `find_char`, `validate_token`, `validate_uri`, `validate_header_value`, `skip_lws` в том же namespace `http_parser::simd`, где они уже определены в `http_parser_simd.hpp`. Прямой конфликт.

**3. Несуществующий член `ctx.method_start` (4 ошибки).**
```672:672:experience/http-2/http_parser.hpp
            ctx.method_start = p;
```
В `context_t` (строки 131–168) **нет поля `method_start`** — есть `url_start`, `current_mark` и т.д., но не это. Используется в 4 местах при разборе метода.

**4. `state_res_status_line` объявлена, но не определена.**
```638:638:experience/http-2/http_parser.hpp
    static parse_result_t state_res_status_line(context_t& ctx, const char*& p, const char* end, const handler_t& h) noexcept;
```
Вызывается в диспетчере (строка 1221), но тела нет нигде. **Разбор HTTP-ответов вообще не реализован**, хотя Readme заявляет «HTTP/1.0 и HTTP/1.1 совместимость» и есть `on_status` callback.

**5. `example.cpp` не включает `<string>`** (2 ошибки undefined `std::basic_string`) — мелочь, но показывает, что пример никогда не собирали.

### Логические/архитектурные ошибки (даже если починить сборку)

**6. Висячие указатели при инкрементальном разборе.** Дизайн zero-copy хранит указатели в исходный буфер (`url_start`, `header_name_start`, `header_value_start`...). При разрыве сообщения между двумя `parse()` (а это норма для TCP) эти указатели ссылаются на **предыдущий буфер**, которого уже нет. В `state_header_value` при возврате `INCOMPLETE` и повторном входе `header_value_start` переустанавливается на новый буфер — **частично принятое значение теряется/портится**. То есть заявленная «incremental parsing» фактически безопасна только если всё сообщение целиком в одном буфере. Моя реализация копит токены в `std::string`, поэтому работает при разрыве на любом байте (демонстрирую это в Примере 4 — побайтная подача).

**7. Нет защиты от request smuggling.** При одновременных `Content-Length` и `Transfer-Encoding: chunked` аналог не отвергает запрос (проверяет лишь дублирование CL), а в диспетчере молча выбирает chunked. Это классическая дыра. Мой парсер возвращает `CONTENT_LENGTH_CONFLICT` (Пример 6).

**8. Неверная логика тела ответа.**
```851:853:experience/http-2/http_parser.hpp
                if (ctx.type == message_type_t::RESPONSE && 
                    ctx.status_code != 204 && ctx.status_code != 304 &&
                    ctx.status_code < 200) {
                    ctx.state = state_t::BODY_EOF;
```
Условие `status < 200` означает «читать тело до EOF только для 1xx» — а у 1xx тела как раз нет. Обычный `200 OK` без `Content-Length`/chunked, наоборот, уйдёт в `DONE` без чтения тела. Логика инвертирована.

**9. Слабый разбор `Transfer-Encoding`.** Сопоставляется строго `value == "chunked"` (строка 963), поэтому `gzip, chunked` не распознаётся как chunked, нет проверки «chunked должен быть последним», нет накопления по нескольким TE-заголовкам.

**10. SIMD де-факто не используется.** Хотя в `http_parser_simd.hpp` есть настоящие AVX2/SSE-реализации (`find_crlf_avx2` и т.д.), парсер в горячем пути зовёт **скалярный** `simd::find_crlf_scalar` напрямую (строки 905, 1160) и переопределённый скалярный `validate_token`. Плюс SIMD только x86 — на этой машине (arm64) всё равно был бы fallback. Заявленные в Readme «4–8x ускорение» в реальном пути не достигаются.

## Где аналог объективно лучше / сильнее по задумке

Честно отмечу плюсы — идея местами амбициознее моей:

- **Богаче список методов**: WebDAV (`PROPFIND`, `MKCOL`, `LOCK`...), `M-SEARCH`, `NOTIFY` и т.д. (~35 против моих 9). Это легко добавить и мне.
- **Zero-copy через `string_view`**: при цельном буфере не копирует тело/заголовки — потенциально быстрее и меньше аллокаций, чем мой подход с `std::string`. Но реализовано небезопасно (см. п.6).
- **Callback-API** (как у nodejs http_parser/llhttp) — удобно для стриминга больших тел без буферизации. Мой API проще (собирает готовое `Message`), что удобно для применения, но менее гибко для гигабайтных тел.
- **Таблица «известных заголовков»** для быстрой диспетчеризации и **настоящий SIMD-код** (пусть и не подключённый) — хороший задел.
- **Compile-time конфиг** лимитов (у меня лимиты рантайм-настраиваемые в `Limits` — это, наоборот, гибче).

## Производительность

Прямое сравнение невозможно — аналог не собирается. Концептуально:
- Аналог при исправлении **может стать быстрее на больших телах/заголовках** за счёт zero-copy и (если правильно подключить) SIMD-поиска CRLF.
- Моё решение быстрее «из коробки» на типичных мелких запросах: посимвольный автомат + bulk-`memcpy` тела даёт ~1.7M req/s без какого-либо SIMD, и работает кросс-платформенно (включая arm64, где SIMD-аналог деградирует в скаляр).

## Вывод

- **Моё решение** — рабочее, безопасное, кросс-платформенное и сразу применимое; компилируется, тестируется, защищено от smuggling и корректно переживает разрыв данных.
- **Аналог** — это, по сути, **непротестированный черновик/скелет**: красивая архитектура и амбициозный Readme, но он не компилируется (несуществующее поле, неопределённая функция, дублирование символов, падающий static_assert), не реализует ответы и небезопасен при инкрементальном вводе и при smuggling.

Если хочется взять лучшее из обоих — могу: (а) добавить в моё решение WebDAV-методы и опциональный zero-copy/callback-режим для больших тел, либо (б) починить аналог (убрать дубликаты в `simd`, добавить `method_start`, реализовать `state_res_status_line`, исправить `fold_buffer`/static_assert, подключить SIMD и решить проблему висячих указателей).
